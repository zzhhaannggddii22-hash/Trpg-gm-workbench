## 1. 目标与边界

将三角机构掷骰从临场记忆改为固定、可调用、可核验的结算管线。不创造新骰子机制，不把本桌适配冒充官方规则。

- 官方规则以当前 Campaign 指定的中文 v22 原文为准。
- 用户批准桌规只在对应 Campaign / 适用范围内生效。
- 角色 ARC、Quality、已确认资格、能力、装备和补给决定资格与选项。Playwall 专属分支本轮明确暂缓；不得因本协议提及资格检查就假定已实现。
- 具体能力条文对骰型、Quality、成本、触发、成功/失败或特殊骰面另有规定时，以条文为准。
- 不存在通用技能检定、通用先攻、默认闪避或“凡有不确定性就掷骰”的流程。

## 2. 检定入口：先判断是否应掷骰

1. 玩家实际声明什么行动/效果？是在询问可行性，还是请求执行？
2. 当前世界条件下属于普通可行行动、危险/困难的常人行动，还是明确调用机构/异常能力？
3. 当前规则是否允许/要求掷骰？掷骰是否由玩家发起？
4. 该行动属于哪一种明确机制？

### 2.1 不应创建的伪检定

- 普通可行行动不因“可能失败”自动掷骰。
- 普通人的危险/困难行动按 Default Failure 原则处理，不改造成通用技能检定。
- GM 不得为增加戏剧性或制造失败而强迫玩家掷骰。
- 玩家询问“能不能做”而没有声明执行时，先说明可行性、限制和路径，不自动掷骰。
- 玩家选择不调用机构/能力时，不替其启动检定。

### 2.2 机制路由

| 机制 | 必须调用的资料 |
|---|---|
| Ask the Agency | 中文 v22 原文；基础规则速查；当前 Campaign 桌裁；相关 Quality / QA / Burnout / Chaos 状态 |
| Anomaly Ability（基础路径限定） | 仅处理不依赖 Playwall 专属解锁或专属覆盖、且其完整基础条文已核验的异常能力；其他一律 `UNSUPPORTED_PENDING_RULE_REVIEW` |
| Conflict Resolution | 冲突解决章节原文；双方目标、参与者、当前状态、触发条件和结算效果 |
| Harm / Life Insurance 防护 | Harm 与保障条文；角色保障项目、可用 QA、装备/能力防护；不得误用普通检定的 QA 限制 |
| 其他明确掷骰机制 | 从中文 v22 规则索引定位；先确认机制确实存在，不以其他 TRPG 惯例补齐 |

路由后必须读取完整适用条文。速查索引只用于定位，不能替代规则原文。

### 2.3 Ask the Agency 基础请求门槛

进入 Ask 流程前，逐项核验请求效果、是否存在可信常人因果链、相关 Quality、已确立事实与自由意志限制。不得把 Ask 当成“任何问题都能问”的通用占卜，也不得用掷骰替代对请求是否合法、可实现的规则判断。

只有通过请求门槛后才进入基础 6d4。失败导致的地点力竭必须绑定失败发生时的当前位置与任务剩余时间；不得把它泛化成全局资源惩罚，也不得在没有当前地点/任务时间状态证据时编造层数或持续时间。

### 2.4 Conflict Resolution 独立路径

Conflict Resolution 是独立的多人/多轮机制，不得塞入普通单次检定的单一骰池结构，也不适用普通 Ask / Anomaly Ability 的 QA、Burnout、Chaos 或自然三重升华流程。

按参与者分别保存每轮原始骰面与结果，保留同步轮次和累计值。规则要求平局续掷时，继续下一轮；只有累计至少六个 3 且其中一方独占第一时才满足结束条件。必须记录每位参与者每轮的骰面、累计 3 数、领先关系与是否续掷。玩家同意/发起边界按该机制原文执行，不得因 GM 方便替玩家启动冲突或替玩家接受结果。

此路径在 UI / Schema 中应表达为多参与者与多轮数据；当前单骰池 Schema 不足以承载完整 Conflict Resolution，因此在专用多轮投影完成前，只允许文本回退，不得把冲突伪装成普通单次骰池事件。

## 3. 统一执行管线

### A. 建立检定事件
内部创建稳定 roll_event_id，并关联当前 Session Event ID。锁定玩家行动、目标与效果范围、机制、规则版本、掷骰发起权、角色资格和依赖规则。纯可行性询问不创建检定事件。

### B. 核验规则与状态
从 Rule_Reference 索引和规则导航定位，再读取中文 v22 原文。核对：
- 触发条件与行动主体；
- 骰型、数量、掷骰次数；
- 指定 Quality 与角色资格；
- QA、Burnout、Chaos、Harm 或其他资源；
- 资源成本、生成、费用调整与公开要求；
- 自然骰面触发条件；
- 修正、移除、重掷、替代效果；
- 规则规定的先后顺序；
- 成功/失败/特殊结果与后果；
- 持续时间、范围和例外；
- 当前 Campaign 桌裁及模组特例。

参考资料：
- Rule_Reference/01_基础规则与现场裁定.md §1–4
- Rule_Reference/04_规则疑点与裁定记录.md
- Research/triangle-agency-rules-index.md
- 当前 Campaign 的 RULE_ADJUDICATIONS.md（只对其绑定范围生效）

### C. 掷骰前说明
向玩家说明角色能够知道的机制、掷骰原因、相关 Quality/能力、玩家选择、可见成本与风险。不展示隐藏机制、未解锁 Playwall、GM-only 模组事实或角色尚未获知的成功/失败解释。

### D. 取得原始骰面
- 用户未声明自己掷骰：由 GM 助手执行。
- 用户明确说自己掷骰：等待完整骰面，不自行补骰或重掷。
- 记录实际 roll_source；MODEL_GENERATED 不得伪装成外部公平随机源。
- 原始骰面按掷出顺序固定编号，后续不得重排或压缩。
- Ask the Agency 基础流程为 6d4；普通需要掷骰的异常能力基础同样为 6d4，但具体能力条文若有已核验覆盖则按该条文。Conflict Resolution 虽使用 6d4，仍属于独立的多人/多轮路径。其他机制不得未经原文核对就套用 6d4。

### E. 先检查原始骰面特例
对明确要求使用未修改骰面的自然结果/特殊触发，先按原始骰面核验并记录。区分：
- 原始骰面本身满足的特殊触发；
- 后续调整骰面后才形成的组合；
- 规则只看最终有效骰面才触发的效果。

**基础机构掷骰若原始骰面恰好出现三个 3，立即进入独立的 `NATURAL_TRIPLE_ASCENSION` 分支：确认成功、Chaos 为零，并暂停等待玩家选择升华奖励；不得继续进入普通 Burnout、QA 或普通失败/Chaos 路径。** 奖励选择完成前，规则结果与奖励应用状态分开记录。额外添加的 3 必须记录为规则效果，不得伪装成原始骰面。若具体能力条文明确覆盖该结果，只有在该条文已核验且资格已确认时才进入专属覆盖分支；未核验则标记 `UNSUPPORTED_PENDING_RULE_REVIEW`。调整后才形成三个 3 不触发自然升华。

### F. 普通基础路径：按规则顺序处理 Burnout 与 QA
仅在当前机制适用且未命中 E 节自然三重升华分支时执行。当前 Zarek Campaign 的 Q04 桌裁明确：
1. 先检查 Burnout；
2. 再检查 QA；
3. 同一次检定消耗 QA 不会在该次检定即时产生 Burnout。

QA 一般限制：
- 普通检定只能使用本次检定所用 Quality 的 QA；
- Ask the Agency 按请求效果/因果链确定相关职业素质；
- Anomaly Ability 使用能力条文指定的 Quality；
- 只有具体条文明确授权时才能跨 Quality 使用 QA；
- Life Insurance Policy 的跨 Quality QA 防护是 Harm 特例，不得推广到普通检定。

玩家看到原始骰面后，是否花费 QA、花费多少、选择哪些骰位，按规则由玩家决定。助手不得默认花费或自行挑选骰位。需要玩家选择时暂停在此阶段。

### G. 逐骰应用修改
每枚骰子保留固定位置（6d4 为 1–6；其他机制按实际骰数编号）。每次修改记录骰位、修改类型、规则依据/玩家选择、修改前后值、顺序、是否移除、效果读取原骰还是修改后骰。

- 不重排、不压缩骰位；
- 未修改骰面保持原值；
- 多次修改按规则顺序逐次记录；
- 移除骰保留原位置和历史值；
- 玩家选择无法唯一定位时先询问骰位；
- 不得把一枚骰子的修改应用到其他骰位。

### H. 结算最终骰面与适用效果
普通基础路径按原文检查最终有效骰面、成功数量/结果算法、Stability、Burnout 相关效果、Chaos 生成/消耗及成功/失败和代价。自然三重升华已在 E 节独立结算，不得再次进入普通 Chaos 计算。任何依赖 Playwall 专属能力、特殊骰型、额外骰、特殊费用时点或其他能力覆盖的效果，本轮不实现；标记 `UNSUPPORTED_PENDING_RULE_REVIEW` 并停止受影响分支。

每个效果都必须对应自己的触发条件、骰面来源和规则依据。未核实的连带效果单独标记 PENDING，并隔离其依赖字段；独立可确认的结果继续结算。

### I. 资源交易与状态应用
复用现有资源权威，不另建骰子账本。桌内裁定、账本应用、批次发布和读回核实是不同状态，不得合并为一个“已结算”标记：
- 每个实际改变的资源字段独立形成交易条目；
- 当前模组 Resource Ledger 是 Session 进行期间所有角色资源与模组公共资源的唯一交易流水和余额依据；具有机制意义的装备充能/次数等资源字段也按账本规则记录；
- Session Log 记录事件与玩家看到的资源说明，引用 Resource Ledger Entry ID，不复制资源流水；
- Runtime State 只保留场景连续性和必要关键物品快照，不保存资源余额，也不承担账本引用/计算；
- Campaign 正式人物卡是 Session 边界状态快照：Session 开始时用于建立/核对账本开局基线；Session 结束对账后一次性更新，不在 Session 中逐笔更新；
- 同一轮完成规则结算、账本交易、余额更新和玩家可见说明；
- 前值 UNKNOWN / PENDING 时只记录可确认增量，不推算后值；冻结依赖该余额的效果，不冻结无关互动；
- 每字段交易绑定 `roll_event_id + adjudication_revision + transaction_batch_id + resource_field + idempotency_key`；Entry ID 仅作定位引用，必须另有账本应用回执/读回证明。
- 发布回执丢失或部分写入时，沿用原骰面和玩家选择，按既有批次查询并读回；不得盲目重发。证据不足标记 `PENDING_EVIDENCE`，只冻结相关字段。

### J. 输出与复核
输出前核对检定名称、机制、原始/最终骰位、自然结果时点、Burnout/QA 顺序、资源交易唯一性、余额状态、特殊效果结算状态、信息权限，以及事件/UI/正文是否一致。

## 4. 玩家可见输出

最终输出包含：
1. 行动：本次检定要实现什么；
2. 机制：Ask the Agency / 具体 Anomaly Ability / Conflict Resolution 等；
3. 骰面：原始骰面与固定骰位；
4. 修正：Burnout、QA 或其他效果，逐骰展示；
5. 最终骰面：未移除骰按原位置列出；
6. 结果：按该机制的准确规则解释；
7. 资源变化：逐字段列出增减量与当前余额，待核显示“当前待核”；
8. 后续状态：只列本次实际发生的状态变化。

需要玩家选择时使用中间态：展示原始骰面、规则允许的选项、相关 Quality 的可用 QA、等待选择的骰位；不得提前宣布最终成功/失败或把待结算资源写成已应用。

## 5. 与 Dice UI 的接口

UI 只接收由 Runtime 按接收者授权生成的 `player_reply_payload`。不得传入内部 `roll_event_id`、Session Event ID、Resource Ledger Entry ID、交易批次或 GM 审计编号。UI 如需局部更新，只使用接收者隔离的 `view_id` 与单调递增 `revision`；不得把内部关联键暴露给客户端。

UI 不掷骰、不判断规则、不选择 QA/骰位、不计算资源、不写 Resource Ledger / Session Log / Runtime State、不读取 GM-only 字段。

组件契约见 Systems/Triangle_Agency/Dice_UI/README.md。

## 6. 本轮支持范围与明确暂缓

### 本轮可处理（仍须逐次核验适用原文）
- 不应掷骰的行动路由与 Default Failure；
- Ask the Agency 基础请求门槛与基础 6d4 流程；
- 不依赖 Playwall 专属解锁/覆盖、且完整条文已核验的普通异常能力基础路径；
- 原始骰面自然三重升华独立分支；
- 未命中自然三重升华后的普通 Burnout / QA / 最终骰面 / Chaos 路径；
- Conflict Resolution 独立机制路径；
- 现有账本逐字段交易、证据化恢复与玩家投影边界。

### 明确暂缓（后续不得遗忘）
状态统一标记 `UNSUPPORTED_PENDING_RULE_REVIEW`，并登记为后续工作项：
1. 所有依赖 Playwall 解锁/层级/专属条文的能力与资格分支；
2. Playwall 能力造成的特殊骰型、骰数变化、替代骰、额外骰或额外 3；
3. Playwall 能力的先付成本、延后成本、免掷、替代成功条件及特殊失败后果；
4. Playwall 能力对自然三重升华、Burnout、QA、Stability、Chaos 或结算时序的覆盖；
5. 未逐条核验的能力专属互动与例外。

重新接入前必须逐条读取 v22 对应完整原文、核对角色 ARC/Playwall 状态与当前 Campaign 绑定，建立单独夹具并通过独立审核。基础流程不得作为这些能力的默认回退。
