# 《三角机构》掷骰检定执行协议（设计稿）

> 状态：DESIGN / 待高级模型独立审核
> 绑定：system_id = triangle_agency；规则版本 = 中文 v22
> Campaign 桌裁仅在当前 Campaign Binding 明确选中时适用
> 通用流程：GM_Training/ROLL_RESOLUTION_PROTOCOL.md
> 设计基线：main@5d19ab9188ac0f02b1b5ecf762f0d4b5f8642ae5

## 1. 目标与边界

将三角机构掷骰从临场记忆改为固定、可调用、可核验的结算管线。不创造新骰子机制，不把本桌适配冒充官方规则。

- 官方规则以当前 Campaign 指定的中文 v22 原文为准。
- 用户批准桌规只在对应 Campaign / 适用范围内生效。
- 角色 ARC、Quality、Playwall 解锁、能力、装备和补给决定资格与选项。
- 具体能力条文对骰型、Quality、成本、触发、成功/失败或特殊骰面另有规定时，以条文为准。
- 不存在通用技能检定、通用先攻、默认闪避或“凡有不确定性就掷骰”的流程。

## 2. 检定入口：先判断是否应掷骰

1. 玩家实际声明什么行动/效果？是在询问可行性，还是请求执行？
2. 当前世界条件下属于普通可行行动、危险/困难的常人行动，还是明确调用机构/异常能力？
3. 当前规则是否允许/要求掷骰？掷骰是否由玩家发起？
4. 该行动属于哪一种明确机制？

### 2.1 不应创建的伪检定

- 普通可行行动不因“可能失败”自动掷骰。
- 普通人的危险/困难行动按 Default Failure 原则处理，不改造成通用技能检定。
- GM 不得为增加戏剧性或制造失败而强迫玩家掷骰。
- 玩家询问“能不能做”而没有声明执行时，先说明可行性、限制和路径，不自动掷骰。
- 玩家选择不调用机构/能力时，不替其启动检定。

### 2.2 机制路由

| 机制 | 必须调用的资料 |
|---|---|
| Ask the Agency | 中文 v22 原文；基础规则速查；当前 Campaign 桌裁；相关 Quality / QA / Burnout / Chaos 状态 |
| Anomaly Ability | 具体能力原文；角色 ARC / Playwall 解锁与资格；Trigger / Cost / Quality / Roll / Success / Failure / Extra 3 等条文；相关资源 |
| Conflict Resolution | 冲突解决章节原文；双方目标、参与者、当前状态、触发条件和结算效果 |
| Harm / Life Insurance 防护 | Harm 与保障条文；角色保障项目、可用 QA、装备/能力防护；不得误用普通检定的 QA 限制 |
| 其他明确掷骰机制 | 从中文 v22 规则索引定位；先确认机制确实存在，不以其他 TRPG 惯例补齐 |

路由后必须读取完整适用条文。速查索引只用于定位，不能替代规则原文。

## 3. 统一执行管线

### A. 建立检定事件
内部创建稳定 roll_event_id，并关联当前 Session Event ID。锁定玩家行动、目标与效果范围、机制、规则版本、掷骰发起权、角色资格和依赖规则。纯可行性询问不创建检定事件。

### B. 核验规则与状态
从 Rule_Reference 索引和规则导航定位，再读取中文 v22 原文。核对：
- 触发条件与行动主体；
- 骰型、数量、掷骰次数；
- 指定 Quality 与角色资格；
- QA、Burnout、Chaos、Harm 或其他资源；
- 资源成本、生成、费用调整与公开要求；
- 自然骰面触发条件；
- 修正、移除、重掷、替代效果；
- 规则规定的先后顺序；
- 成功/失败/特殊结果与后果；
- 持续时间、范围和例外；
- 当前 Campaign 桌裁及模组特例。

参考资料：
- Rule_Reference/01_基础规则与现场裁定.md §1–4
- Rule_Reference/04_规则疑点与裁定记录.md
- Research/triangle-agency-rules-index.md
- 当前 Campaign 的 RULE_ADJUDICATIONS.md（只对其绑定范围生效）

### C. 掷骰前说明
向玩家说明角色能够知道的机制、掷骰原因、相关 Quality/能力、玩家选择、可见成本与风险。不展示隐藏机制、未解锁 Playwall、GM-only 模组事实或角色尚未获知的成功/失败解释。

### D. 取得原始骰面
- 用户未声明自己掷骰：由 GM 助手执行。
- 用户明确说自己掷骰：等待完整骰面，不自行补骰或重掷。
- 记录实际 roll_source；MODEL_GENERATED 不得伪装成外部公平随机源。
- 原始骰面按掷出顺序固定编号，后续不得重排或压缩。
- Ask the Agency 基础流程为 6d4；其他机制不得未经原文核对就套用 6d4。

### E. 先检查原始骰面特例
对明确要求使用未修改骰面的自然结果/特殊触发，先按原始骰面核验并记录。区分：
- 原始骰面本身满足的特殊触发；
- 后续调整骰面后才形成的组合；
- 规则只看最终有效骰面才触发的效果。

现有速查记录：三重升华要求任何调整前原始骰面恰好三个 3；调整成三个 3 不触发原骰升华。具体场景仍须按当前规则原文核验。

### F. 按规则顺序处理 Burnout 与 QA
仅在当前机制适用时执行。当前 Zarek Campaign 的 Q04 桌裁明确：
1. 先检查 Burnout；
2. 再检查 QA；
3. 同一次检定消耗 QA 不会在该次检定即时产生 Burnout。

QA 一般限制：
- 普通检定只能使用本次检定所用 Quality 的 QA；
- Ask the Agency 按请求效果/因果链确定相关职业素质；
- Anomaly Ability 使用能力条文指定的 Quality；
- 只有具体条文明确授权时才能跨 Quality 使用 QA；
- Life Insurance Policy 的跨 Quality QA 防护是 Harm 特例，不得推广到普通检定。

玩家看到原始骰面后，是否花费 QA、花费多少、选择哪些骰位，按规则由玩家决定。助手不得默认花费或自行挑选骰位。需要玩家选择时暂停在此阶段。

### G. 逐骰应用修改
每枚骰子保留固定位置（6d4 为 1–6；其他机制按实际骰数编号）。每次修改记录骰位、修改类型、规则依据/玩家选择、修改前后值、顺序、是否移除、效果读取原骰还是修改后骰。

- 不重排、不压缩骰位；
- 未修改骰面保持原值；
- 多次修改按规则顺序逐次记录；
- 移除骰保留原位置和历史值；
- 玩家选择无法唯一定位时先询问骰位；
- 不得把一枚骰子的修改应用到其他骰位。

### H. 结算最终骰面与适用效果
按原文分别检查最终有效骰面、成功数量/结果算法、Stability、Burnout 相关效果、Chaos 生成/消耗、三重升华或其他特殊结果、能力专属额外 3、成功/失败和代价，以及实际状态影响。

每个效果都必须对应自己的触发条件、骰面来源和规则依据。未核实的连带效果单独标记 PENDING，并隔离其依赖字段；独立可确认的结果继续结算。

### I. 资源交易与状态应用
复用现有资源权威，不另建骰子账本：
- 每个实际改变的资源字段独立形成交易条目；
- 当前模组 Resource Ledger 是 Session 进行期间所有角色资源与模组公共资源的唯一交易流水和余额依据；具有机制意义的装备充能/次数等资源字段也按账本规则记录；
- Session Log 记录事件与玩家看到的资源说明，引用 Resource Ledger Entry ID，不复制资源流水；
- Runtime State 只保留场景连续性和必要关键物品快照，不保存资源余额，也不承担账本引用/计算；
- Campaign 正式人物卡是 Session 边界状态快照：Session 开始时用于建立/核对账本开局基线；Session 结束对账后一次性更新，不在 Session 中逐笔更新；
- 同一轮完成规则结算、账本交易、余额更新和玩家可见说明；
- 前值 UNKNOWN / PENDING 时只记录可确认增量，不推算后值；冻结依赖该余额的效果，不冻结无关互动；
- 重试先检查原 roll_event_id、Entry ID 和应用状态，防止重复掷骰或重复入账。

### J. 输出与复核
输出前核对检定名称、机制、原始/最终骰位、自然结果时点、Burnout/QA 顺序、资源交易唯一性、余额状态、特殊效果结算状态、信息权限，以及事件/UI/正文是否一致。

## 4. 玩家可见输出

最终输出包含：
1. 行动：本次检定要实现什么；
2. 机制：Ask the Agency / 具体 Anomaly Ability / Conflict Resolution 等；
3. 骰面：原始骰面与固定骰位；
4. 修正：Burnout、QA 或其他效果，逐骰展示；
5. 最终骰面：未移除骰按原位置列出；
6. 结果：按该机制的准确规则解释；
7. 资源变化：逐字段列出增减量与当前余额，待核显示“当前待核”；
8. 后续状态：只列本次实际发生的状态变化。

需要玩家选择时使用中间态：展示原始骰面、规则允许的选项、相关 Quality 的可用 QA、等待选择的骰位；不得提前宣布最终成功/失败或把待结算资源写成已应用。

## 5. 与 Dice UI 的接口

UI 只接收已确认的玩家可见数据：阶段、机制、Quality、骰型、原始骰面、逐骰修改历史、最终骰面、结果、玩家可见资源变化和待选择/待核状态。

UI 不掷骰、不判断规则、不选择 QA/骰位、不计算资源、不写 Resource Ledger / Session Log / Runtime State、不读取 GM-only 字段。

组件契约见 Systems/Triangle_Agency/Dice_UI/README.md。

|---|---|---|
| TA-DICE-01 | 普通可行行动 | 不创建无依据检定 |

| TA-DICE-06 | 助手代掷 | 默认由助手执行并保留原骰 |
| TA-DICE-07 | 玩家自行掷 | 不补骰、不重掷，正确接收骰面 |
| TA-DICE-08 | QA 匹配 | 普通检定只用本次 Quality QA |
| TA-DICE-09 | Burnout / QA 时序 | Q04 生效时先 Burnout 后 QA |
| TA-DICE-10 | 玩家骰位选择 | 不替玩家选择 QA 数量或骰位 |
| TA-DICE-11 | 原始三重升华 | 只检查修改前原始骰面 |
| TA-DICE-12 | 修改后形成三个 3 | 不误触发原骰三重升华 |
| TA-DICE-13 | 骰子移除/多次修改 | 保留固定骰位和完整变更链 |
| TA-DICE-14 | Chaos 资源变化 | 同事件写入 Resource Ledger，不重复建流水 |
| TA-DICE-15 | 当前余额待核 | 不伪造后值，只冻结依赖字段 |
| TA-DICE-16 | 重试/输出纠错 | 沿用原骰面和已应用交易，不重新掷骰 |
| TA-DICE-17 | UI 中间态 | 等待选择时不显示伪最终结果 |
| TA-DICE-18 | UI 权限隔离 | 不呈现 GM-only 规则、能力或模组内容 |

静态检查或单次模型自测不等于真实运行验收。
