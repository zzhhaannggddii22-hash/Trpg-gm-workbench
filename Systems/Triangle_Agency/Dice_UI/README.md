# Triangle Agency Dice UI｜独立骰子结果展示组件

> 状态：DESIGN SPEC / 待高级模型审核；当前不是已部署插件
> 版本：0.1.0-draft
> 适用系统：triangle_agency / 中文 v22
> 规则执行来源：Rule_Reference/02_DICE_RESOLUTION_PROTOCOL.md
> 设计基线：PR #52 review head d600e24；本修订仍为 DESIGN，未获运行批准。

## 1. 定位

这是独立的结果展示组件（Renderer），专门把三角机构骰子检定结果清晰、美观地呈现给玩家。

它不是规则引擎、随机数生成器、资源账本、Session Log、Runtime State 或 GM 自动决策器。检定协议负责规则、骰面、玩家选择和状态结算；Resource Ledger 负责资源交易；UI 只展示已经确定或明确处于中间态的数据。

组件应可独立复用，不依赖 Bower Street 或扎雷克的特定 Campaign 内容。

## 2. 设计原则

1. 骰面优先：玩家第一眼能看清每枚骰子的原始结果和最终有效结果。
2. 过程透明：每枚骰子的修改轨迹可追溯，不能只展示最后一个数字。
3. 自然结果与调整结果分离：原始骰面特殊触发与修改后结果必须分区。
4. 不伪造结算：未完成玩家选择或规则核验时显示“等待选择 / 待核”，不提前显示成功/失败。
5. 不承担状态权威：资源数据按上游已确认事件渲染；余额待核就明确显示待核。
6. 权限最小化：只接收经过玩家可见过滤的数据，不接收 GM-only 原文、隐藏机制或备团信息。
7. 简洁有辨识度：独立骰子卡片、清晰数字、阶段标签和轻量动效；不做赌场式动画。
8. 响应式与可访问：桌面/移动端均可读；颜色不是唯一状态编码，骰位和状态必须有文字标签。

## 3. 推荐布局

### 顶栏
- 检定名称 / 行动目标；
- 机制类型：Ask the Agency / Anomaly Ability / Conflict Resolution / 其他已核实机制；
- 当前阶段：已声明、已掷骰、等待玩家选择、结算完成、部分待核。

### 骰面区域
Ask the Agency 的 6d4 固定显示 1–6 六个骰位。每枚骰子使用独立四面骰视觉卡片，显示骰位编号、原始骰面、是否修改、最终有效骰面、是否移除。

若机制使用其他骰型或骰数，按事件输入渲染，不得把 6d4 强制套用到所有机制。

### 修改轨迹
每枚被修改骰子可展开查看原始值、修改顺序、玩家可见的修改原因摘要、修改前后值、最终有效值/移除状态。未修改骰子不展示冗余轨迹。所有骰位始终保持原顺序，不因移除而重新编号。

### 结果区
- 只展示结算协议已确认的结果；
- 自然骰面触发与最终骰面结果分开显示；
- 特殊结果显示“已触发 / 未触发 / 待核”；
- AWAITING_PLAYER_CHOICE 时显示“等待玩家选择”，不显示最终成功/失败。

### 资源区
按事件输入显示本次实际涉及的资源：Quality 与相关 QA、Burnout、普通 Chaos Pool（公开资源）及其他明确改变的资源字段。

每项资源只显示经授权的资源名称、玩家可见变化量、已核验的公开余额及核验状态。不得显示 Resource Ledger Entry ID、内部事件编号或交易批次。当前余额待核时主状态显示“当前待核”，不得用历史值或本次增量冒充当前余额。UI 不生成 Entry ID，也不写账本。

## 4. 组件状态机

| 状态 | 显示内容 | 禁止显示 |
|---|---|---|
| DECLARED | 行动、机制、骰型、已说明风险/成本 | 骰面、最终结果 |
| ROLLED | 原始骰面、固定骰位、已确认的自然触发检查 | 未结算的最终成功/失败 |
| AWAITING_PLAYER_CHOICE | 原始骰面、可用选项、相关 Quality QA、等待选择 | 自动花费 QA、最终结果 |
| RESOLVING | 已确认修改轨迹、尚待核验项目 | 将待核效果标成已完成 |
| RESOLVED | 原始骰面、修改轨迹、最终骰面、结算结果、已确认资源变化 | 与事件记录不一致的数据 |
| PENDING | 已确认部分、具体待核字段及依赖 | 猜测余额、猜测效果、虚构骰面 |

组件状态由调用方传入。UI 不根据骰面自行推导状态。

## 5. 数据接口

组件接收经过过滤的 player_view 对象。不要把完整 GM 事件对象直接传给 UI，再依靠前端隐藏字段。

核心字段：
- view_id：接收者隔离、不可反推内部编号的视图标识；
- revision：单调递增的视图修订号；
- recipient_scope：固定为 PLAYER 的授权范围；
- system_id / ruleset_version：系统与规则版本；
- mechanic：已确认机制；
- status：组件状态机；
- roller / roll_source：掷骰执行者与来源；
- dice[]：骰位、骰型、原始值、修改轨迹、最终值、移除状态；
- natural_triggers[]：依赖原始骰面的触发检查；
- outcome：已确认结果；
- resources[]：已确认且允许玩家看到的资源变化；
- pending_items[]：待玩家选择或待核项目。

数值均为调用方已核验数据。缺失字段显示未知/不适用，不得用默认值补齐。字段契约见同目录 roll-event.schema.json（v2 玩家投影契约）。

## 6. 视觉语言

- 每枚骰子使用清晰的四面骰卡片，突出数字和骰位编号。
- 原始值和最终值同时可见；修改后以箭头/轨迹表示，不覆盖原始结果。
- 被移除骰使用低对比度、删除线和“已移除”文字；仍保留原骰位。
- 自然骰面触发采用独立标签，明确标注“原始骰面”。
- 资源变化用紧凑行显示“前值 → 变化 → 后值”；未知余额使用“当前待核”。
- 颜色采用中性底色，少量强调色用于已确认结果或警告；所有状态同时提供文字。
- 动画只用于短暂进入/揭示，不允许动画结束后改变已确认骰面；不得用动画模拟真实随机性。

## 7. 权限与安全

- UI 输入必须是 Runtime 按接收者授权生成的 `player_reply_payload`，不得接收 GM-only 资料或内部关联编号。
- 不显示未解锁 Playwall 能力、隐藏机制、NPC 秘密或模组后台事实。
- 规则来源、内部检索路径、GM 推论和隐藏触发不进入玩家视图。
- 若玩家有权看到当前 Chaos Pool，展示经核验的公开余额；待核时显示“当前待核”。
- UI 不提供猜测/补齐结果按钮，不允许直接编辑骰面或资源余额。
- 玩家选择 QA 或骰位时，由 GM 对话流程收集并核验；UI 只显示等待状态，不能直接写账本或改变事件。

## 8. 故障与回退

- 缺少原始骰面：显示“骰面资料不完整”，不渲染虚构骰子。
- 骰位重复/越界：显示数据错误，拒绝显示最终结算。
- 原始骰面与修改轨迹不一致：显示“结算待核”，不自行修复。
- 事件未 RESOLVED：不展示最终成功/失败。
- 资源字段 PENDING：显示“当前待核”，仍可显示已确认的独立增量。
- UI 无法加载：退回通用掷骰文本格式；游戏流程不得依赖 UI。
- 同一 view_id 的新修订更新同一接收者视图；拒绝旧修订覆盖新修订；相同 revision 不同内容视为冲突。view_id 不得编码内部事件或账本编号。

## 9. 实施边界与非目标

当前仓库没有既有前端组件框架或已部署 ChatGPT 插件运行时，因此本文件先定义独立组件契约和验收要求，不声称已有可安装插件。实现阶段由高级模型审核后选择与当前产品环境兼容的封装方式（例如独立 HTML/JS 视图或平台支持的 UI 组件），不得改变纯展示职责。

第一版只支持 Triangle Agency 所需骰型与流程，优先保证 6d4、逐骰修改、自然骰面与最终骰面区分、等待玩家选择、资源状态显示。其他系统适配不在本版范围。

## 10. UI 验收标准

- 六枚 6d4 按 1–6 固定位置显示；
- 原始值和最终值同时辨认；
- 多次修改逐步展示，未修改骰保持原值；
- 移除骰保留位置，不压缩数组；
- 原始自然触发与修改后组合明确区分；
- 中间态不会出现虚假最终结果；
- QA / Burnout / Chaos 只显示调用方提供的已确认数据；
- 当前待核不显示猜测数值；
- UI 不生成随机数、不裁定规则、不修改资源；
- GM-only 字段不能进入组件输入；
- 同一事件重渲染不重复创建或应用交易；
- UI 故障时无损回退文本输出。


## 11. 本轮接口修订与范围登记

### 玩家投影契约

UI 仅消费 Runtime 生成的 `player_reply_payload`，与文本回退共用同一份授权投影。组件输入不得包含内部 `roll_event_id`、Session/Event ID、Resource Ledger Entry ID、交易幂等键、发布批次 ID、GM-only 规则引用或未授权内容。上述字段只留在 GM 内部事件与审计记录。

UI 更新标识仅允许接收者隔离的 `view_id` 与单调递增整数 `revision`。它们不得由内部编号直接编码或可逆推导。相同 revision 不同内容视为冲突；较旧 revision 必须拒收。

### 结算状态与显示状态分离

`RESOLVED` 只表示规则结果已确定，不代表玩家奖励选择完成、资源交易已应用或持久化已验证。UI 必须允许显示“结果已确定，等待选择”及“结果已确定，保存状态待核”等组合；不得仅凭一个 RESOLVED 状态推断所有工作完成。

### 明确暂缓项

本轮仅验证基础 6d4、原始骰面/最终骰面、逐骰修改、自然三重升华等待奖励选择及普通 Burnout/QA 的只读合成视图。Conflict Resolution 虽已列入规则路由，但当前单骰池 Schema 不足以表达多参与者与同步多轮数据，必须使用文本回退，待专用多轮投影另行设计。依赖 Playwall 解锁或专属条文的能力、特殊骰型、额外骰、费用与结算覆盖均标记 `UNSUPPORTED_PENDING_RULE_REVIEW`，不进入可渲染的已支持状态。后续须逐项核验规则并另增夹具。
