# 备团—带团联动与运行效率规范

> 性质：GM-only 操作规范。本文补足《12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md》的备团质量要求，定义备团成果如何组织、交接并在带团时被高效调用；不替代《02_WORKFLOW_AND_PREFLIGHT.md》的 Preflight，也不创造 TRPG 规则。
>
> 核心目标：备团充分，但不把所有资料塞进每轮上下文；带团灵活，但不脱离已确认事实。可靠性是永久底线，运行效率通过减少重复读取、重复叙述和无价值维护实现。

## 1. 总体结构：备团产物服务于运行

每个模组的备团至少形成三类内容，并明确标注性质：

### A. 设定基石（事实约束）

记录带团时必须遵守的事实。每条重要内容标注来源性质：

- **SOURCE**：模组/规则原文明确内容，尽可能保留章节、页码或段落定位。
- **TABLE CANON**：本桌已经实际发生并确认的事实。
- **GM ADAPTATION**：为本桌人数、角色或体验所作的明确改编。
- **GM INFERENCE**：基于来源和已建立事实作出的推断，不能伪装成原文。
- **UNKNOWN**：尚未核实的内容，保持开放，不得补写成事实。

设定基石包括但不限于：事件真实经过与时间线、地点结构、异常机制及触发条件、NPC 身份/经历/动机/知识边界、关键物品与事实关系、结局成立条件。

**固定事实与动态状态必须分开。** 固定事实不因玩家路线而随意改变；动态状态（位置、伤势、持有物、当前计划、已知信息等）由带团过程持续更新。不要把某一时点的动态状态冻结成永久设定。

### B. 可调用素材（呈现资源）

提前准备带团时可直接调用、组合或按需改写的内容，例如场景描写、NPC 行为/对话要点、可观察细节、线索呈现方式、环境互动、遭遇元素和过场摘要。

素材不是必须播放的台词稿。保留用途、适用条件和必要事实约束即可；避免为每种可能对话预写长篇文本。素材若包含事实信息，必须能追溯到对应设定基石或明确标为 GM Adaptation。

### C. 预设方向（可行性与成本控制）

预先检查可能路线和关键决策点，用于验证模组可运行、降低临场推演成本并保障基础体验。包括：

- 主要目标、必要条件、可选目标及其奖励条件；
- 关键调查方向、节点功能、可能连接方式与收束条件；
- 关键 NPC/势力在不同触发条件下可能采取的行动；
- 主要路线偏离、关键人物不可接触、检定失败、时间流逝等情况下的合理响应；
- 可能的软锁、信息单点依赖、无回报长支线和无法收束事项。

预设方向是 GM 的导航与压力测试，不是剧情轨道。玩家提出合理的非预设行动时，仍按设定基石、规则和世界因果响应；不得为了执行预案而把玩家拉回指定路线。

## 2. 备团工作顺序

按风险和依赖关系组织工作，不要求每个模组都产出同等规模的材料：

1. **确认来源**：核实模组名称、作者/版本、原文完整性、勘误与规则权威；区分原文事实、外部参考和桌面适配。
2. **提取基石**：建立事件真相/时间线、空间结构、关键机制、NPC 知识与动机、目标和结局条件。优先整理会影响裁定或后续因果的事实。
3. **建立调查与行动结构**：按《12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md》设计重要调查链，明确节点功能、回报、替代来源、失败/中断后果和结束条件。不是每个地点或每条支线都必须有线索，但高投入调查链不能连续空转。
4. **准备可调用素材**：为高概率、重要或高风险场景准备足够的呈现素材；低概率枝节只准备事实依据与简短响应原则，不写庞大剧本。
5. **预设方向与可行性检查**：从主要目标反向检查必要信息是否可获得、路线是否可替代、关键 NPC/地点失效时是否仍可推进，以及玩家偏离预设路线后世界如何响应。
6. **NPC/环境一致性审计**：检查动机、知识、行为、衣着、生理状态、时间、位置、资源和异常因果。矛盾必须归类为有意线索、待调查未知、GM 已知真相或准备错误。
7. **运行化打包**：制作短小的运行索引与必要的调用入口，见第 3 节。
8. **可选 Prep QA**：根据模组复杂度、备团风险和实际需要，决定是否按第 12 号规范执行高强度挑错。若执行，必须在该模组第一次 Session 的 Preflight 之前完成并记录；若跳过，明确标记“本轮未执行 Prep QA”，不影响后续 Preflight。Preflight 一旦在该模组启动，Prep QA 窗口即关闭，之后不再补做或重开该模组的 Prep QA。

备团深度按影响分配：
- **必须准备**：规则关键、主目标、关键事实、重要 NPC、核心调查链、重大风险、结局/收束条件、单人桌适配、装备与奖励交接。
- **条件准备**：玩家可能到达且会影响关键因果的地点、支线、特殊互动和中高风险分支。
- **轻量准备**：低概率枝节、纯装饰内容和不影响后续的普通角色。保留事实约束和即兴边界即可。

不要为了“覆盖所有可能性”穷举每一种玩家行动。备团应准备世界如何运作，而不是预写玩家会怎么做。

## 3. 运行化打包：让带团能快速找到正确资料

每个模组的 GM Prep 应有一个简洁的**运行索引（Runtime Quick Reference）**，作为现场入口，而不是再复制一份完整备团。建议控制在一屏到数屏可快速扫描的规模，至少包含：

- 当前场景/任务阶段及其关键事实入口；
- 主要目标、可选目标、奖励触发条件和结局/收束条件；
- 关键 NPC、地点、事件、异常、线索的规范 ID 与资料入口；
- 重要调查链的节点索引及其回报/收束提示；
- 关键触发条件、时间条件、危险提示和不可忽略的事实约束；
- 需要现场核对的规则条款/原文定位；
- 未解决的 UNKNOWN、审核遗留风险和禁止擅自补定的内容。

运行索引只放导航和短提示；详细事实只保存在唯一权威位置，通过 ID、标题或链接引用。不得在 README、Prep、线索账本、NPC 卡中复制多份互相可能漂移的完整事实。

推荐资料分层：
- **入口层**：README + Runtime Quick Reference。用于快速恢复整体局面。
- **工作层**：NPC 卡、地点卡、调查链、异常卡、目标/结局说明、线索来源账本。只在当前场景或行动相关时调用。
- **证据层**：模组原文、规则原文、勘误与外部研究。遇到不确定、争议或红色高影响行动时回查。

索引必须支持从运行中的实体反查权威资料；同一实体只保留一个规范 ID。若一个文件已经是某项事实的权威来源，其他文件只引用，不另写一套副本。

## 4. Prep QA 与 Preflight：备团阶段和运行启动阶段

两者职责不同，处于同一项目生命周期的不同阶段：

- **Prep QA 是备团阶段的可选质量审核**：在 GM Prep 形成后、该模组第一次 Session 的 Preflight 之前执行。它检查备团成果本身，帮助提前发现逻辑漏洞和结构缺陷；不是每个模组都必须执行。
- **Preflight 是每次新对话/新 Session 的必做启动流程**：新对话承担本次游戏的运行上下文恢复，必须重新加载本场需要的规则、模组资料、人物卡、战役交接、最新 Runtime State 和相关记录，并核对本次启动条件。
- **严格时序**：如需执行 Prep QA，必须先于该模组第一次 Preflight；Prep QA 可以跳过，Preflight 不依赖 Prep QA 的完成或通过。
- **关闭规则**：该模组第一次 Preflight 一旦执行，Prep QA 阶段即结束。此后不得再对该模组补做、重开或追补 Prep QA；运行中发现的问题进入运行纠错、Runtime State/Session Log 或模组复盘，不倒流成事后 QA。

### A. Prep QA｜备团质量审核（可选）

**对象：备团成果本身。** 在模组备团草稿形成后、第一次 Session Preflight 之前，按《12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md》按需启动。它回答：“这份模组准备是否足以支持可靠、灵活的主持？”

是否执行由备团风险与实际需要决定。高复杂度、高风险、重要调查链较长、存在大量 GM 扩写或前次复盘暴露同类问题时，Prep QA 的收益更高；简单、低风险或准备资源受限时可以跳过。跳过时只记录未执行及原因，不将其设为 Preflight 阻塞项。

审核范围维持既定内容：
- 关键事实是否有来源与性质标记；
- 重要调查链是否有实际回报、替代路径和结束条件；
- NPC/环境/异常因果是否自洽；
- 主要目标与结局是否可达、可理解、可收束；
- 是否存在单一线索/单一检定/单一 NPC 导致的软锁；
- 单人桌与当前角色能力是否适配；
- 运行索引是否能让 GM 在现场快速定位资料；
- GM-only 与玩家侧内容是否隔离。

Prep QA 的输出是独立审核记录：必须修正的问题、建议修正的问题、已确认合理的设计、资料缺口、后续观察风险，以及本轮审核状态。若执行，必须在第一次 Preflight 前结束；第一次 Preflight 执行后，本模组 Prep QA 阶段关闭，不再补做或重开。

### B. Preflight｜每次新对话/新 Session 的启动与资源恢复

**对象：当前这一次实际开团/Session 的启动条件与运行上下文。** 每次新对话/新 Session 准备继续或开始游戏时，按《02_WORKFLOW_AND_PREFLIGHT.md》《09_MODULE_FOLDER_STANDARD.md》及系统专属要求执行。它回答：“本次对话是否已恢复正确的规则、模组、角色、战役和运行状态？此刻是否具备继续游戏的条件？”

Preflight 的首要任务是加载本次运行所需资源，而不是审核备团设计。至少恢复并核对：
- 当前规则版本、规则索引与本次行动所需的必要原文；
- 当前模组原文、GM Prep、Runtime Quick Reference，以及本次可能调用的关键 NPC/线索/机制/结局资料；
- 正式人物卡、当前场次副本、战役交接、最新 Module Runtime State、最近 Session Log/Player Notes；
- 本场实际装备、持有人、资源、系统资源/伤害与压力状态、充能等状态；
- 当前场景、时间、位置、在场者、玩家已知信息、未解决事项和上次复盘行动项；
- 主要/可选目标、公开风险、奖励条件和必要规则差异；
- GM-only 与玩家侧材料隔离；
- 用户明确同意开始后才开团。

Preflight 必须为每个新对话/新 Session 建立本次运行快照与就绪记录。可引用之前的 QA 结论或 Preflight 记录作为资料，但不能用旧记录代替本次上下文恢复与状态核对；不得因上次 Session 已通过而跳过新对话的资源加载。效率优化体现在只读取本次需要的权威入口和相关文件，不重读无关历史或整仓库。

### C. 时序、依赖与结果边界

- Prep QA **可选**；跳过 Prep QA 不影响 Preflight 启动、通过或开团。
- 如执行 Prep QA，必须在该模组第一次 Preflight 之前完成；不得在 Preflight 后补做。
- Preflight **每个新对话/新 Session 必做**，不依赖 Prep QA，也不负责替代备团质量审核。
- 第一次 Preflight 执行后，该模组的 Prep QA 窗口永久关闭。之后发现的备团缺陷，按运行时纠错或模组复盘处理，不再启动该模组的 Prep QA。
- Prep QA 的通过只表示备团审核完成，不代表某次 Session 的角色、装备、资源、资料和启动条件已经就绪。
- Prep QA 是否执行、审核结果如何，都不改变 Preflight 的资源加载与就绪检查职责。

## 5. 带团时的资料调用策略

带团以最新 Runtime State 和当前运行快照为动态状态权威，以设定基石为固定事实依据，以素材和预设方向为可选资源。

按当前行动调用资料，不要把整个 GM Prep 每轮重新装入上下文：

- **绿色普通行动**：使用当前场景与运行快照，直接按事实回应；不打开整套备团，不重复 Preflight。
- **黄色重要行动**：只查受影响的 NPC/地点/线索/事件卡和对应调查链；完成行动—依据—结果—状态更新闭环。
- **红色高影响行动**：回查相关规则原文、模组关键事实和状态来源；必要时暂停裁定，不能为了速度猜测。
- **非预设行动**：先查询相关设定基石和当前状态，再决定是否需要补充素材或推演新后果；若新增内容会影响后续，标记为 GM Adaptation 并进入 Runtime State/Session Log。
- **玩家再次调查已知来源**：按《08_CLUE_AND_SOURCE_LEDGER.md》检查来源知识边界与本次问题，不把已知信息误作“来源已耗尽”；调查增量检查不作为每个节点的强制流程。

同一活动对话/Session 中，完成一次必要的上下文恢复并形成运行快照后持续维护；除非出现新对话、上下文缺失、资料冲突、关键变化或规则不确定，不重复全量读取。Session 续团读取最新 Runtime State 和最近日志；历史日志按需追溯，不扫描全部历史。

## 6. 运行效率保护

效率优化只削减重复和低价值成本，不削减必要的事实核验与玩家选择。

应当减少：
- 每轮重读完整模组、人物卡、全部规范和历史日志；
- 在多个文件重复抄写同一事实；
- 每个调查节点强制运行完整增量检查；
- 对普通行动执行黄色/红色审计；
- 重复展示已知信息、重复描写机械操作；
- 为低概率枝节准备大量没有调用价值的台词与分支。

必须保留：
- 首次新团/新 Session 的必要恢复与 Preflight；
- 规则关键和高影响行动的原文核验；
- 重要调查链的可行性、回报与收束设计；
- NPC 知识边界、动机与行为一致性；
- 关键资源、装备持有人、时间、位置和 CANON 的准确更新；
- 玩家作出选择所需的风险、代价与信息；
- GM-only 与玩家侧隔离。

效率是否提升，以“减少无价值等待与重复工作，同时保持或提高规则准确性、事实连续性、叙事质量和玩家行动空间”为标准；回复更短、文件更少或流程更快本身不构成成功。

## 7. 带团反馈如何回流备团

发现问题时，先分类根因，再决定是否修改备团：

- **备团遗漏**：原文中已有、且可预见但未整理的事实/机制/线索/状态 → 补充 Prep 和索引。
- **备团结构缺陷**：路线软锁、长调查链无回报、目标不可达或缺乏收束 → 修订调查结构与可行性检查。
- **素材调用缺陷**：资料存在但现场找不到、太长或没有触发索引 → 优化 Quick Reference 和入口，不重复复制内容。
- **带团执行缺陷**：资料充分但现场未读取、误用或未更新状态 → 优化运行路由与检查，不盲目扩写备团。
- **模型能力/推理缺陷**：在资料充分、流程正确的情况下仍反复推理失误 → 记录证据，评估模型/任务复杂度，不用无限增加规则掩盖能力边界。
- **玩家路线超出预案但世界逻辑可响应**：这属于正常游戏，不自动视为备团失败；只有暴露可预见的事实缺口或因果漏洞时才修订。

每次模组复盘最多提炼 1–3 个可执行改进目标。新规则必须对应真实问题，说明预期收益和可能增加的运行成本，并在后续场次验证；不要为一次偶发情况堆叠永久流程。

## 8. 最小完成定义

一份可用于开团的备团，不以篇幅或素材数量判断，而以以下条件判断（这是备团产物质量定义，不等于 Prep QA 或 Preflight 的流程记录）：

1. 重要事实可追溯，固定事实与动态状态分离；
2. 主要目标与关键结局可行，重要调查链有回报与收束条件；
3. 重要 NPC/环境/异常因果自洽；
4. 素材能支持高价值场景，但不写死玩家路线；
5. 运行索引能让现场快速找到权威资料；
6. 备团资料已具备运行所需的入口与可追溯性；
7. 最终 Preflight 按其独立流程完成，且等待用户明确开团指令。

未满足关键条件时，标记缺口与风险，不宣称备团完成。


## 9. 首次接触卡与冷启动验证（新增运行交接要求）

运行索引不能只告诉 GM “去看某个文件”；对于本 Session 预计首次接触的命名 NPC，必须有可直接调用的首次接触卡，或在进入场景前从权威原文即时生成。卡片包含身份/代词、年龄/职业、初始位置与同场人物、抵达时的动作、外貌与服饰、显著物件、表层信息、隐藏信息门槛和禁止混淆项。信息不足时明确留空，不凭常见设定补全。

正式开场前做一次轻量冷启动验证：
1. 从当前开场画面开始，用玩家实际可能选择的第一条调查路线，检查首个 NPC 出场；
2. 将开场叙述逐项对照模组原文与首次接触卡；
3. 检查有无未经来源支持的职业、地点、伤势、设备、客户、证人、机构响应或线索；
4. 检查是否过早泄露隐藏信息；
5. 若发现偏差，先修正材料与运行状态，再开放开团。

这项验证属于 Runtime Readiness / 错误预防，不重开已关闭的 Prep QA，也不替代规则原文核验。文档已经存在、QA 曾经 PASS/CLOSED、或曾做过一次 Preflight，都不能替代本次冷启动验证。


## 10. 叙事素材与连续性种子的备团交付

备团阶段的职责是提供可调用的准备资源与初始状态，不是替现场写好全部演出。具体准备深度依照场景重要性、模组复杂度和风险决定。

### 10.1 重要场景素材卡

对于核心地点、首次异常、重大调查发现、关键选择和重要 NPC 场景，按需准备：

- 场景 ID、功能和来源；
- 空间锚点：入口、出口、位置关系、遮挡、距离和重要物件；
- 感官锚点：少量有辨识度的光线、声音、触感、气味或温度；
- 动态锚点：场景开始时正在发生的动作、变化或环境状态；
- 互动入口：玩家可以观察、询问、触碰、实验、移动或改变什么；
- 信息边界：当前可见事实、隐藏事实、UNKNOWN 和合理获取条件；
- 节奏建议：哪些发现应展开，哪些机械流程可以摘要；
- 可调用参考：原文位置、NPC 卡、线索卡、相关规则和后续状态。

### 10.2 NPC 可演卡

重要 NPC 记录目标、顾虑、当前策略、知识来源、权限/资源、与在场人物的关系、正在做的事，以及哪些行动/信息会使其改变策略。准备“可演方向”而非穷举对话分支。示范台词仅用于建立声音，不得替代现场对玩家真实话语的回应。

### 10.3 事实与事件种子

备团时整理：

- 固定事实与 GM 改编；
- 时间线和事件触发条件；
- NPC 在不同条件下能够采取的行动；
- 关键物品及初始持有人；
- 玩家可见信息与 NPC 知识边界；
- 已确定的事件结果与仍然开放的变量。

不能确定的事实明确标记 UNKNOWN，不以常见叙事惯例补全。

### 10.4 Preflight 初始状态与续接标记

Preflight 应在首次正式开场前建立本 Session 的初始 Runtime State。至少标记 NEW START、起始场景 ID、场景状态 NOT ENTERED、当前时间/地点、初始在场者、角色资源与装备持有人、玩家起始已知信息、最近事件 ID 和待处理事项。

场景入口第一次呈现后，将状态更新为 ENTERED / ACTIVE，并记录已呈现的入口描述或叙事节点。之后的对话恢复必须采用 CONTINUE，不得再次从起始场景生成开场。

### 10.5 备团交付的取舍

- 只为高价值场景准备完整素材卡；普通地点使用简短事实与互动索引。
- 重要 NPC 准备可演方向，不预写长对白。
- 为调查链准备事实、来源、获取方式与验证关系，不预写玩家必然得出的推理。
- 运行状态只维护当前值与变化依据，完整历史留在 Session Log / Event Log。
- 素材必须能在现场快速定位；若现场无法找到或无法判断是否适用，应改进索引，而不是继续堆叠描述。

## 2026-11-24｜Handoff 与运行检查点一致性补充

Handoff 是恢复入口，不是独立权威状态，不得凌驾于 Campaign Binding、Runtime State、Session Log、角色卡或模组原文。
- 必须声明 system_id、ruleset_version、campaign_id、module_id、活动分支、Runtime 修订/检查点、Resume Mode。
- 必须列出最后已呈现事件、最后已回应事件、待回应玩家行动、未合并 event_id、保存发布状态、当前事故状态及玩家授权范围。
- 对每项关键状态引用权威文件/字段，不复制另一套可独立编辑的“当前值”。
- 若 Handoff 与 Runtime/Log 冲突，停止相关推进，按事件历史和字段所有者核验；不得按提示词文本的日期或最近编辑时间自动选值。
- 活动存档缺少上述字段时标记 LEGACY_UNMIGRATED，走完整 Preflight；不允许快路径默认补齐。
- 已结案模组的 Handoff 必须明确标记 RETIRED / CLOSED，不再作为 CONTINUE 指令。
