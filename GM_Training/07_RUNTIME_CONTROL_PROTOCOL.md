# GM 运行控制协议｜Runtime Control

> 性质：对既有 GM 原则与工作流的执行层细化。本文不创造任何 TRPG 规则，不替代系统规则、模组原文、Session Log 或战役 CANON。
> 目标：减少“原则已经写入，但主持时没有执行”的落差。运行时只做必要检查，不把每个普通动作变成表格流程。

## 1. 权威顺序与启动门槛

每次开始新团、新 Session 或跨对话续团，按以下优先级恢复资料：

1. 用户在当前桌明确指定的规则版本与桌面约定。
2. 当前角色卡、玩家确认的战役事实及最新有效状态快照。
3. 当前模组原文、官方补丁及 GM-only 准备档案。
4. 最近 Session Log、未解决事项和最近一次复盘行动项。
5. 通用 GM 原则、工作流、裁决纪律与本协议。
6. 外部评论、Actual Play、其他桌裁定仅作参考。

资料之间冲突时，不自行拼凑。先确定来源、时间、适用范围和权威等级；影响行动或 CANON 的冲突未解决前，暂停相关裁定并向玩家说明必要部分。

恢复到当前 Session 后，先按 §14.4-B 决定请求是否能进入角色行动与场景叙述。关闭场次的仅查资料分支从玩家视图直接作答。

玩家在启动或加载时仅要求确认接收的，直接走 §14.19.2 的确认回执，随后等待下一条行动。规则版本、运行身份与来源的核对结果保留给有权操作者的核验交付。

### 活动对话中的按需读取

- 新对话/新 Session 的完整恢复只执行一次；生成当前运行快照后，在同一活动对话中持续维护该快照。
- 不因每条玩家消息都重新读取 GitHub、模组全文、人物卡或全部规范。
- 仅在关键规则不确定、玩家质疑、状态冲突、高影响变化、重要新实体引入或错误回滚时，读取对应原文/档案。
- 读取范围限于当前问题所需的文件与条款；不为普通行动扫描完整仓库。
- 当前上下文不足以可靠恢复时，明确回查或标记未知；不能为了速度用猜测补齐。


开团前必须完成：角色、装备、资源与当前场景恢复；已发生事件、NPC 状态、线索与未解决事项恢复；当前规则原文和模组原文可回查；上次复盘行动项转成可执行检查；玩家可见信息与 GM-only 信息分离。

缺少关键资料时，明确标注缺口，不宣称已恢复完整状态；不得靠模型印象补全。

## 2. 运行时三档检查

### 绿色：普通行动（轻量）

适用：无实质风险、无重要资源变化、结果明确的日常行为。

- 直接按世界逻辑回应。
- 不为普通动作强制掷骰。
- 不必每次写账本或向玩家解释内部流程。

### 黄色：重要行动（标准闭环）

适用：可能改变线索、位置、关系、装备、资源、NPC 状态、时间或事件进度的行动。

内部依次核对：玩家实际声明的行动和目标；当前事实、角色能力、装备、资源、位置与时间；适用规则/模组条文或自动完成的理由；玩家需要事前知道的可见风险、代价和选择；结果及其直接后果；状态账本中的变化；是否满足 NPC/世界事件推进条件。

只把需要玩家理解和选择的部分说出来，不播报完整内部清单。

### 红色：高影响/规则关键行动（强制核验）

适用：可能造成伤害/死亡、消耗或改变核心资源、触发当前系统专属机制、改变任务成败、产生重大关系或 CANON 变化，以及玩家提出规则质疑的情况。

在宣告结果前：
1. 定位用户指定规则原文的具体章节/条款/页码（可得时）。
2. 核对触发条件、目标类别、当前状态、例外、成本、结算顺序和持续时间。
3. 将规则事实、模组事实、桌面约定与 GM 裁量分开。
4. 若需掷骰，先公开适用流程和角色可知风险；展示原始骰面，再按规则允许的顺序处理 系统资源/修正，最后确定结果。
5. 只有有效伤害/资源消耗成立后，才询问或结算相应的防护、忽略伤害或替代效果。
6. 一次性结算所有连带状态，再向玩家给出清楚结果。

找不到原文时，不以“我记得规则是……”代替核验。可暂停相关裁定，或在玩家同意后使用明确标注、临时且一致的桌面裁定；后续回查并处理差异。

## 3. 规则核验卡

每次关键规则裁定，内部保留最小记录：

| 字段 | 内容 |
|---|---|
| 触发行动 | 玩家做了什么 |
| 规则定位 | 用户规则文件、章节/页码/条文 |
| 触发条件 | 为什么该规则适用 |
| 结算顺序 | 掷骰、修正、成本、效果、后果 |
| 最终结果 | 同一稳定事件 ID 下列出已确认行动与效果范围、适用效果及其规则依据、玩家选择、字段前值/增量/后值、接收者与可公开结果。逐枚掷骰修正记录原骰位和改动。未决效果标明原因与依赖。 |
| 不确定项 | 未查明的内容与临时处理 |

**先定本次效果的范围与字段。** 从玩家本轮已声明的行动、已确认的选择及适用规则确定哪些效果成立，把目标、效果依据及对应的前值和后值写进同一事件。机会、可达或可用属于当前条件，执行、取得或消耗属于行动结果；只有相应行动声明或规则依据支持的字段才更新。描写机制过程时只展开已经成立的效果；物品移动后其完整性、归属和持有状态均沿用原记录，直到独立效果或实际操作提供新依据。已经失败或中止的旧行动保留原结果。玩家本轮明确要求的有效连续动作仍可依次执行，并分别写下实际结果。

**校验事件后统一输出。** 掷骰需要逐枚修改时，以原始顺序给每枚骰固定位置，逐项应用已确认的修改。核对有效修改的前值、位置和后值，以及其他位置是否保持原值。先在事件中确定唯一结果和实际变更字段，再写回复。检定的首个结果句直接读取这一个已确认结论。标题可只标行动名称；标题内的结果、标题下的结果标签和首个结果句均使用同一结论。其后正文、状态栏和重连沿用该结果及可公开的状态差异。发送前对照标题、结果标签、首句和状态栏；发现冲突时按事件结论改正再发送。每项效果只有一个有效结论；未核实的连带效果单列，独立观察继续。等待选择或依赖缺失时保留原事件及已确认部分，先核实依赖再结算相关效果。重试先确认同一事件、当前桌内已完成的字段和后续变化，沿用已生效的骰位、资源和效果。需要证明外部保存或冷恢复时再按 §14.14 核对目标修订和字段应用。记录冲突按相关字段处理，从冲突记录中继续确认其余可独立核验的结果。

**资源当前值。** 规则卡按字段保留 `VERIFIED(value)` 或 `PENDING(dependency)`。同桌已核验的当前字段沿用，直到适用的规则效果、后续事件或冲突要求重核。已核验前值及完整核验的零增量确定该字段不变。遇到可能改变该字段的未知依赖时记 `PENDING`，只有查齐适用变化或取得权威当前值才转为 `VERIFIED`。保存状态、跨会话恢复与冲突对账按 §14.14 核验受影响字段。

**资源答复。** 场景推进、查账和重试只读取所需字段。需要显示当前状态时，按字段已有状态直接渲染：`VERIFIED` 显示当前数值，`PENDING` 显示「当前待核」。本次结算表、状态栏和后续查账共用当前栏。`PENDING` 的当前栏只写「当前待核」，历史数值保留在注明时点的历史栏；需要交付历史时单独列为历史记录。已经独立核验的本次增量按增量列展示，当前栏沿用待核状态。只有移动产生的变化可以在移动回执中报告，已有待核依赖仍保留。特殊结果分别记录触发和各适用效果。

**区分可行性查询与行动承诺。** 玩家问「能否」「可不可以」且同时没有声明执行该动作时，说明可达条件与现有后果，当前角色位置沿用只读结果。明确声明执行的后续行动按 §14.20.6 处理；独立可执行的动作直接完成，不等待无关规则。

规则核验的成功标准不是“引用了规则”，而是规则的触发条件和结算顺序确实正确。如果同一规则在一次行动中涉及多个步骤，应按顺序逐项核对，不能只查到规则名称便凭印象结算。

## 4. 状态账本：只精确追踪会影响后续的内容

至少维护以下状态：
- 角色：伤害/压力状态、当前系统的核心资源、持续效果、关键能力状态。
- 装备：关键物品、武器/充能、消耗品及当前持有人。
- 时间与位置：当前日期/时段、场景、人物所在位置。
- NPC：规范身份、别名、位置、状态、动机/当前计划、实际掌握的信息。
- 调查：玩家已知信息、信息来源、来源是否已提供过、尚存信息增量。
- 世界：威胁数量/状态、事件阶段、触发条件、机构/阵营进度。
- 待办：承诺、预约、回访、未完成行动及其责任人。

### 资源精度分级

- 精确记录：当前系统定义的核心资源、特殊装备弹药/充能、任务关键道具、有限补给、伤害/压力状态、关键证据、明确数量的威胁，以及可能改变战术选择的物品。
- 按需记录：普通弹药、普通工具、常见耗材。只有在稀缺、被规则特别管理、明确影响风险或玩家主动要求时才逐项记数；否则用“充足/有余/所剩不多”等有依据的状态描述。
- 不记录：对未来没有影响的琐碎物品和日常细节。

每次关键变化使用一行：对象｜变化前 → 变化后｜触发行动｜规则/事实依据。

### 4.1 资源流水与联动字段

对核心资源、成长轨迹、可用次数和容量/剩余量，采用可追溯的字段级流水。每笔变化至少记录：

| 字段 | 要求 |
|---|---|
| 资源/字段 | 使用人物卡或 Runtime 中的准确字段名；不同概念不得合并 |
| 变化前 | 本次行动前已核验的值；未知时标 PENDING / UNKNOWN |
| 变化量 | 明确写出 +n 或 −n；零变化也要有完整核验依据 |
| 原因与依据 | 对应行动、事件 ID、规则条文或已批准桌规 |
| 变化后 | 仅在前值和全部适用变化均已核验时计算；否则保持 PENDING |
| 应用状态 | 已应用、部分应用、未应用或待核；重试不得重复入账 |

执行约束：

- **同轮完成，先结算后继续。** 凡本轮行动触发资源变化，必须在同一轮裁定中完成流水、余额更新和玩家可见的变化说明；不得延迟到 Session 结束后补记。公开资源（包括当前系统中的公共资源池）发生变化时，变化原因、增减量和变化后余额应与本轮结果一起交付。若前值无法核验，立即标记 UNKNOWN / PENDING，记录已确认的变化量；暂停的仅是依赖该余额的后续行动，不得猜测余额，也不得让无关互动停摆。
- **一字段一余额。** 当前可使用资源、累计获得、累计花费、剩余容量、轨迹进度和 QA 上限是不同字段；除非规则明确规定关系，不得互相替代。
- **联动字段分开记账。** 若规则规定一个字段增加时另一个字段同步减少，分别写两笔对应变化，并记录联动关系、相同触发事件和各自变化方向；不得将其净额抵消，也不得只更新其中一项。
- **先核前值，再算后值。** 前值 UNKNOWN / PENDING 时，可以记录已确认的本次增量，但不能把推算结果伪装成已核验余额。不得用旧历史值覆盖当前待核状态。
- **区分奖励、成长与购买。** 获得资源、选择成长目标、标记成长轨迹、取得能力资格和实际购买/消耗是不同事件。只有玩家明确选择且规则允许时才执行花费；不得因“买得起”自动购买。
- **防止重复应用。** 同一事件的重试先核对已应用字段；同一奖励/消耗不得因日志与 Runtime 双处记录而重复入账。
- **对玩家展示时**，只展示已核验当前值和已核验增量；待核字段明确显示“当前待核”，不要拿历史余额冒充当前值。物品转交必须同时更新原持有人和新持有人，禁止只在叙事里说“交给了某人”却不更新账本。

## 5. 调查信息与来源账本

调查记录必须把“信息本身”与“来源”分开。详细结构见《08_CLUE_AND_SOURCE_LEDGER.md》。

核心规则：
- 同一事实可以从不同来源重复获得；不同来源的确认、独立观察和专业解释可以增加可信度或提供新角度。
- 某条信息已经从某个来源获得，不代表该 NPC/地点已被永久探索完毕。
- 玩家带着新问题再次找同一来源，该来源可以提供新信息；若没有新内容，也可以再次回答旧信息。
- 同一来源再次回答相同问题时，可以自然简短地重述，不必机械拒绝或重新完整演绎。
- 再次听到已知信息时，简略提示“与此前信息一致”；只详细呈现新增细节、矛盾或新解释。
- 不为了让探索每次都有新线索而强行制造新内容；没有新增信息本身也是合理结果。

## 6. 时间与节奏控制

每次玩家行动后判断是否实际消耗游戏时间，以及时间是否足以触发某项事件。聊天消息数量不等于游戏时间。

- 机构调查、实验室分析、交通、等待回复等事项按世界内合理工作流程估算，不为了延长剧情无限拖延。
- 如果任务资料/已建立能力表明调查通常隔天即可完成，就按该速度推进；若需要更久，必须有具体原因。
- 等待期间若没有玩家可参与的决策、人物互动、新信息或风险，直接摘要跳过到合理时间点。
- 等待期间若确有可参与内容，可以让玩家选择是否介入；不要用重复问答强迫填满空档。
- 角色之间的生活化交流是可选且有价值的内容，但不能成为填补无事件时间的默认工具。
- 不为了加快节奏跳过玩家明确想体验的对话、实验、探索或重要决定。

## 7. NPC 与长期同伴

NPC 按自己的知识、动机、性格、能力、关系、资源和机会行动；不要让 NPC 充当 GM 提示器、总结器或摄像头。

- 重要 NPC 与长期同伴以当前 Campaign 的正式人物档案为准；通用运行协议不硬编码具体角色或战役路径。
- 角色可以主动表达自己的观察、兴趣、意见、情绪和生活；也可以不知道、误解、犹豫、犯错、沉默或拒绝。
- 其经验、专业能力、社会经验、资源和行动权限必须符合已确立背景。
- 人物关系依靠共同经历和互动自然发展，不预设亲密度或强行升温。
- 独立执行的行动仍然是正式战役事件，必须记录其行动、获得的信息、承诺、资源变化和后果。
- 同伴不会因为是 NPC 就自动获得第二名 PC 的行动、资源或能力；是否允许协助必须由当前系统规则和明确桌面适配决定。

### 7.1 L3 NPC：活跃模拟、离场延续与再次激活

本节只对当前 Campaign 明确登记为 L3 的 NPC 生效。L3 表示值得投入持续人物模拟资源，不意味着每轮都要运行后台代理；L0–L2 不默认承担长期离场生活模拟。

- **活跃模拟：** NPC 在当前场景中，或其行动直接影响玩家当前行动/已建立事件时，依据当前目标、事务、知识、位置、能力、关系、资源和机会作出行为判断。可以继续事务、回应、拒绝、改变计划、主动介入或不行动；不得把主动性等同于抢戏。
- **离场延续：** NPC 离开当前关注范围后不逐轮、逐分钟或逐小时模拟。复用现有 NPC 档案、Runtime State 和 Session/Event Log，保留最近确认的游戏内时间/状态锚点、目标与当前事务进度，以及已知的日程、承诺和触发条件。不得为此新增默认定时器、全体 NPC tick 或独立后台模拟账本。
- **触发核算：** 仅在游戏内时间明确推进、已建立事件达到触发条件、玩家行动改变相关条件，或 NPC 即将重新进入当前场景时，核算相关 L3 NPC。现实时间、玩家沉默、消息数量和假设性问题都不是触发条件。沿用 §6 与工作流 B3 的时间推进规则。
- **再次激活：** 从最近确认锚点出发，结合经过的游戏内时间、人物目标、事务规律、环境、机会和已发生事件，推导必要的状态增量。避免把 NPC 重置成初次出场状态；也不得为显示变化而编造重大人生事件。小幅事务进度或情境变化足以体现时间连续性；没有因果依据时允许核心状态保持稳定。
- **事件与状态落账：** NPC 的未来意图不等于行动已执行。实际行动必须满足动机、机会、权限、能力与时间依据；凡改变位置、物品、关系、承诺、知识或事件阶段的结果，使用现有事件和字段级状态应用机制处理。叙述不能代替状态更新；NPC 私下获得的信息也不能自动进入玩家知识。
- **裁定、呈现与保存边界：** 规则结论、已确认效果和资源变化由现有行动裁定及同一 `event_id` 事件链确定；叙事生成只呈现已经确认、且允许该接收者获知的后果，不得自行重算、扩展或提前宣称待核效果。NPC 自主行为可以由人物模型推演，但有后续影响的实际执行仍须按 §14.15 的 `NPC_ACTION_EXECUTED` 语义及 §14.14 字段级应用证明处理。桌内已确认状态、Session/Runtime 记录与外部文件/仓库已保存状态是不同事实；聊天中说“已记录/已保存”不能代替工具成功回执及必要的读回核验。
- **投入边界：** 只模拟与当前行动、已建立事件或再次接触有关的 L3 人物。离场期间不生成无关剧情，不要求每次重逢都汇报生活，也不为普通细节建立冗余事件记录。

本节是现有 NPC 状态、游戏时间和事件机制的专门适用说明，不构成第二套状态机或独立持久化协议。

## 8. 场景结束与错误恢复

场景结束时只检查：位置、在场者和时间是否一致；关键资源/装备持有人是否一致；新线索及来源是否记入；NPC 是否知道了其实际获知的信息；事件是否满足推进条件；承诺、回访和待办是否遗漏。

发现错误时采用错误恢复记录：
1. 错误事实/错误裁定是什么；
2. 最早从哪一步开始偏离；
3. 受影响的骰子、资源、位置、时间、线索、NPC/事件状态有哪些；
4. 正确结果是什么；
5. 哪些后续事件需要回滚，哪些不受影响；
6. 账本与玩家侧便笺分别如何修正。

不要只在下一轮换一种说法而保留错误状态。只有在可靠性协议规定的依据与玩家授权/决定满足时，才可将相关分支标记 NON-CANON；已呈现内容不得自动抹除。

## 9. 运行时自检与停止条件

在每次高影响行动后，内部快速问：是否混淆原文与推断；是否遗漏已发生的行动、信息、承诺或资源转移；NPC 是否知道不可能知道的事；是否错误禁止其他来源再次确认线索；是否为了推进剧情制造不合理的新信息/障碍/延误；是否让 NPC 或同伴替 GM 说话；是否只更新叙述而未更新状态。

若发现高影响信息缺失或冲突，暂停该项裁定并先恢复资料；不要用流畅叙事掩盖不确定性。

## 10. 验证与回退

后续至少用以下行为检验本协议：
- 关键规则裁定能定位并正确应用当前 Campaign 绑定版本的原文；
- 重要物品持有人、充能和 系统资源/伤害状态 等状态不漂移；
- 同一线索可跨来源自然交叉印证，同一来源不会被误标为“已探索完毕”；
- 重复信息简洁处理，不再长篇重演；
- 无新增选择的等待和机械流程被合理快进；
- 重要 NPC 与同伴表现出独立人格和合理的经验边界，不充当提示器；
- 错误发生后能完整修正受影响状态，不留下旧值。

若检查本身拖慢普通行动，只在黄色/红色场景使用完整流程；绿色场景保持自然简洁。文档更新本身不代表能力提升，须由后续实际场景验证。


## 11. 响应成本与质量保护（不新增评分维度）

速度优化只针对重复读取、重复检查、重复叙述和无价值的状态重写。每次复盘可在既有“准备效率”“节奏与场景管理”“连续性与状态追踪”维度下记录：
- 是否在活动对话中重复执行完整 Preflight 或重复读取无关档案；
- 是否对绿色普通行动执行了不必要的完整审计；
- 是否因过度压缩而遗漏了玩家需要的空间信息、风险、选择、线索或人物互动；
- 是否因追求速度而降低规则核验、状态准确性或 NPC 知识边界；
- 本轮减少的步骤是否真的没有损失体验，还是把成本转移给了后续纠错。

若速度提高但规则、状态或体验质量下降，视为回归；优先恢复必要检查，不以平均回复长度或绝对响应时间作为唯一指标。


## 12. 首次出场与重大新增事实闸门（Runtime Incident 修订）

本节覆盖旧流程的盲区：B1 行动闭环能检查玩家声明的行动，却没有明确约束 GM 自己在开场、NPC 首次出场和场景搭建时生成的新事实。GM 自己创造的内容同样需要事实审查。

### 12.1 重要 NPC 首次出场前：事实锁定

在一个有明确模组原文的命名 NPC 首次进入玩家视野前，必须当场读取该 NPC 的原文场景段落，并与 GM Prep、NPC Ledger、Clue Ledger 对照。不得只凭 Runtime Quick Reference、压缩摘要或模型印象完成首次出场。

内部建立最小事实卡：
- 身份：姓名、代词、年龄/职业（原文有则记录）、关系；
- 初始位置与场景：具体地点、楼层/房间、谁在场、角色抵达时正在做什么；
- 首次可见外貌与显著物件；
- 该 NPC 自己会自然透露的表层信息；
- 隐藏真相、信息获取条件及拒绝/警觉触发；
- 明确禁止混入的相邻 NPC、相似事件或其他模组内容。

首次描写和第一轮对话必须与事实卡一致。未从来源确认的细节保持 UNKNOWN，或仅作为不影响事实的轻微 GM ADAPTATION；不得补出新的职业、住所、伤势、亲属、设备、客户、案件物件、线索来源或危险机制。

### 12.2 GM 新增事实闸门

任何由 GM 主动加入、并可能改变调查方向或后续因果的实体/事实，先问：
1. 来源是否明确支持？
2. 是否与已知 SOURCE / TABLE CANON 冲突？
3. 是否会生成新的线索、证人、地点、危险、物品所有权、机构响应或任务分支？
4. 若它确属本桌改编，玩家是否有必要知道这是改编？当前桌是否允许该改编？

以下项目不得仅凭场景润色即兴创造：调查对象、受害者经历、NPC 职业、受害原因、关键物品/设备、客户/委托关系、额外证人、机构调度、技术分析结果、线索获取条件及时间触发。

“可以想象发生”不等于“本桌已经发生”。含义容易混淆的词（如客户、同事、设备、事故）必须按原文语境解释，不得从相邻概念串接出新剧情。

### 12.3 运行中事实来源标记

重大事实区分 SOURCE（模组明确提供）、TABLE CANON（桌上确已发生或已确认）、GM ADAPTATION（明确且不冲突的本桌补充）、GM INFERENCE（暂定、不得升级为事实的解释）和 UNKNOWN（未知）。发现已生成或已经进入运行链的错误时，进入 §14.1；呈现状态、草稿和追加勘误按 §14.13 处理。

### 12.4 开始首次 NPC 场景前的快速回读

只需核对当前即将接触的 NPC，不扫描整份模组：
- 名称/代词/年龄/职业；
- 初始地点、同住者/在场者、正在进行的事；
- 外貌、服饰、显著物件；
- 表层说法、隐藏事实、信息门槛；
- 本场明确没有的关键物件/分支。

若某一项答不上来，先查原文再开场。第一次接触是高风险事实节点，不归入绿色自由即兴。

### 12.5 调查性事实与操作结果的发布门槛（P0）

本节只约束会改变调查方向、行动选择、权限、位置、目击、NPC 知识、机构响应、线索、任务状态、保管链或查证结果的具体断言；普通氛围细节不需要逐句建档。只建立了环境物件和通路时，观察可以落在这些物件及其可感知的普通特征上。将一个新细节称为异常、线索或未发现某类迹象时，先取得相应来源或明确的观察范围。

在生成相关玩家可见叙述前，先核对两个问题：

1. **来源支持什么？** 为该断言定位实际来源及其支持范围。NPC 的岗位/身份只证明其岗位/身份，不自动证明其亲历某事件、掌握某项信息、持有某份记录、拥有某种访问权限或已经完成检索。资料只写“可以申请/可以查阅”，不得扩写成已经调取或核验。
2. **行动实际进行到哪一步？** 区分以下阶段，不得跳级：
   - AVAILABLE：记录、人员或入口存在，且具备申请/接触条件；
   - REQUESTED：角色或有依据的 NPC 已实际提出申请/请求；
   - ACCEPTED：有依据表明负责方已受理/同意；
   - EXECUTED：查询、联系、调阅或检查确实发生；
   - RESULT_OBSERVED：结果已实际返回、观察或由可定位来源提供。

只有来源和已发生事件共同支持时，才可叙述相应阶段。权限不等于已申请；已申请不等于受理；受理不等于执行；执行不等于已经得到特定结果。尤其不得凭空生成“查到了”“没有记录”“某人见过”“档案已核权”“某机构已接受”等正面或否定结果。

**整理“已完成 / 已核验”事项时，逐项回指实际执行事件及其结果：** 只有确实达到 EXECUTED，且有 RESULT_OBSERVED 或其他可定位结果依据的事项，才可列为本次已完成/已核验。资料中存在某条目、某人表示可以查询、具备申请条件或已经受理，均不能替代实际查询与结果观察。若只确认了公开信息或可办理条件，应准确记录该项实际确认的内容，不得扩大为尚未执行的查册、鉴定或核验。

若玩家已明确要求一项安全且可执行的查询，可以按规则推进该请求，不必重复索取授权；但没有真实执行/返回证据时，结果仍为 UNKNOWN / PENDING。资料不足时，说明当前能确认的最小范围，或只澄清缺失的必要条件。

上一轮 GM 自行生成的叙述只能证明“这段话曾被呈现”，不能单独成为其所述命题的证据来源。后续若要依赖该命题，必须回溯到原始资料或有依据的实际事件；找不到来源时不得以“之前已经说过”为由复用。若无来源内容已经影响调查方向、NPC 知识、任务或玩家选择，按 §14.1、§14.13 处理并保留原始呈现。

本门槛只在上述有后续影响的事实/结果上触发，不要求普通互动逐轮填写阶段表。


### 12.6 关键物品、证据与操作前提闸门（P0）

先区分原件、抄件及读取、复制、转移等不同权限，按现行来源确立的权限判定每个请求。只许现场阅览的原件可以当场查看；要取走原件须有实际新增授权，能领抄件的许可不扩大原件权限。已有禁止条件时直接按该条件说明可用路径。

**申请、裁定和交付沿用同一事项记录。** 角色明确向有权对象请求某项许可或物件时，即按 §12.5 记为 REQUESTED。玩家说先不领取时，申请照常提交，由有权对象根据当前规则在本轮答复批准、拒绝或指出仍待满足的具体条件；只保留实际发生的范围。批准的事项记明授权对象、可进行的操作和条件。合规政策允许申请只说明该路径可用。另有正式手续时才要求完成，已明确送达的申请沿用原事项。

后来玩家提出领取或转移时，先核对该事项的实际授权与当前持有状态。玩家把“已经批准”当作前提时，回看实际有权对象的答复。授权尚未确定时，保留之前的申请并处理本次有权裁定，条件满足时可以接着交付。发生实物交接后才更新持有；已审批而尚无交接时保持原持有人。独立的观察和其他已具备前提的子行动继续。

本节只用于会改变关键物品归属、证据来源/内容、核心资源、风险承诺或不可逆结果的行动；不要求为普通随身物品、日常动作或每轮叙事建立完整事件链。

对相关对象，只追踪当前行动真正需要的前提，并按需区分：

- **DISCOVERED / OBSERVED**：角色已经发现或观察到对象；不自动代表能够取得、拥有或读懂。
- **ACCESSIBLE**：对象当前可触及或可合法接近；不自动代表角色已经取得。
- **ACQUIRED**：角色实际拾取、接收、购买、制作或以其他有依据的方式取得。
- **CURRENT_HOLDER**：对象当前由谁持有；转交、归还、遗失或消耗必须有实际事件。
- **INSPECTED / READ**：角色实际检查、阅读或使用对象；只记录该次行为确实揭示的内容。
- **PRESENTED**：对象或其内容确实向某个接收者展示/传达；按接收者记录，不把 GM 知道的内容视为已展示。

这些是彼此独立的状态维度，不是所有对象都必须逐项完成的固定流程。不得把“看见”推成“拿到”，把“拿到”推成“检查过”，把“检查过”推成“已向 NPC 展示”，也不得把场景资料中的隐藏位置或来源直接写成角色经历。

**玩家输入不自动证明物品前置状态或物理事件已经发生。** 对“把某份纸本拿给 NPC 看”“我手里有这份联单”等表述，先按当前持有人、位置及实际转移记录判断其语义和可行性；不得仅凭这句话补造此前取得、携带或交接事件。若当前状态显示物品仍由他人持有、已归还或尚未取得，不得直接叙述角色拿出、递交或展示原件。应简短说明当前状态，并继续处理可独立完成的部分：例如转述角色确实读过的内容、请当前持有人出示，或提出新的查阅/取得请求。若玩家表达的是传达已知内容而非展示实体，应按口头转述呈现，不擅自改写成原件到场。若玩家明确尝试现在取得或调取物品，则将其作为当前行动，按相应权限与操作前提裁定，不得倒写成此前已持有。

当玩家提出的关键行动依赖一个当前状态中没有依据的前提时：
1. 不要先演出行动成功，再补写缺失的取得、检查、授权或资源消耗历史。
2. 只暂停依赖缺失前提的子行动；若存在不依赖它的普通互动，照常继续。
3. 用一个简短、具体的问题确认玩家是在补充此前未记录但符合角色/桌面事实的状态，还是打算现在执行取得/检查等行动。不要要求玩家填写内部字段。
4. 玩家补充的角色事实经当前桌面事实、物品清单和既有事件核对后可以接受时，记录为玩家提供的事实；来源/取得经过未被说明的部分仍为 UNKNOWN。不得顺手补造发现地点、取得时间、拾取过程或此前检查结果。
5. 若该物品承担关键证据功能，持有事实与证据来源必须分开：允许角色持有，不等于证明证物来自某地点、由某人制作或已完成特定查验。

对资源消耗、风险承诺和不可逆行动，同样只核对会改变本次裁定的必要前提：资源是否实际可用、玩家是否已选择执行、规则成本/风险是否已按当前系统说明、是否需要事前确认。玩家表达意图、询问可能性或听取 GM 建议，不自动等于已执行或已支付成本。若风险或成本尚未向玩家说明且会影响其选择，先说明再等待决定；若玩家已在充分知情后明确选择，则正常结算，不重复索取确认。

本门槛只在关键物品、证据、资源、风险和不可逆行动上触发。不得把它扩展成每次掏出普通装备、移动或对话都要停下来审计。


### 12.7 资料不完整时的证据约束分析（P2）

当玩家要求根据不完整记录进行统计、时间线、趋势、归因或综合判断时，资料精度不足不等于分析任务整体不可执行。按以下边界交付：

1. **先界定数据集。** 说明本次实际可用的记录、覆盖时间、观察范围、样本/分母是否明确、时间精度、缺失项及可能的重复/选择偏差。未实际读取或未向当前角色披露的资料，不算本次玩家可用数据。
2. **分开观察与推断。** 将可直接核验的记录、由这些记录支持的有限判断、尚待验证的解释分别表达。每个趋势/因果判断都必须由当前接收者有权使用的前提支持；GM-only Prep、隐藏时间线或未披露事实不得作为玩家分析的隐形证据。
3. **不伪造精度。** 不补造案例数、日期、比例、分母、缺失记录或不存在的测量结果。数据无法支持精确统计时，明确说明哪些指标不能计算；若已观察内容仍支持有限的定性模式，可以给出有边界的近似判断，并标明范围、置信程度与替代解释。
4. **不要把局部缺口扩大成整体停摆。** 无法计算精确周增长率，不妨碍整理已知事件顺序、指出可确认的聚集现象、比较有资料支持的时间段，或提出下一步可验证的问题。若现有资料连方向性判断也不支持，就明确说趋势尚不可判定，同时交付已经能够确认的内容。
5. **把分析转成可行动结果。** 给出当前最稳妥的结论、它依赖的证据、尚缺的关键数据，以及一项最有价值的后续查询/观察。不要把选择分析方法和承担全部推理工作推回玩家。

本节不授权 GM 将后台真相包装成玩家推断，也不要求每次调查都生成统计模型。仅在玩家确实请求分析，或分析结果会影响其行动选择时触发；普通访谈与观察保持自然叙事。

## 13. 运行连续性与上下文恢复锚点

上下文连续性不能只依赖模型对长对话的回忆，也不能仅靠加长推理时间解决。训练可以改善检查与执行，但可靠性主要来自清晰的权威来源、可恢复状态、事件记录和明确的续接规则。

### 13.1 四类资料各司其职

1. **静态权威事实**：规则原文、模组原文、角色长期档案、已确认的战役设定。回答“长期成立的事实是什么”。
2. **当前运行状态（Runtime State）**：截至最近一次有效更新，时间、位置、人物、资源、物品持有人、知识、事件阶段和待办分别是什么。回答“现在是什么状态”。
3. **事件记录（Session Log / Event Log）**：按发生顺序记录重要行动和状态变化。回答“状态如何变成现在这样”。
4. **玩家可见记录（Transcript / Player Notes）**：记录哪些信息和场景已经实际呈现给玩家。回答“玩家已经看见或听见什么”。

聊天记录可以作为证据和补充，但不能代替权威事实或最新状态；摘要只能作为索引，不能覆盖其来源。

### 13.1.1 跨会话信息恢复与来源准入边界（P0）

- 当前 Session 的场景状态、玩家已知信息和调查成果，只能从当前 Campaign/Module 的有效 Runtime checkpoint、按序 Session/Event Log、具有实际呈现锚点的 Player Notes，以及本次对话实际发生的行动与呈现中恢复。不同文件按各自权威职责使用，不以摘要替代来源。
- 其他 Chat 的历史对话、模型记忆、跨会话摘要、用户对旧对话的概述或重新粘贴的笔记，可以帮助定位需要查找的资料；它们本身不证明某项行动、NPC 陈述、观察、文件查阅或玩家接收事件在当前 Session 发生，也不自动成为当前玩家知识、NPC 知识或 Campaign CANON。
- 只有当历史内容能够回溯到适用 Campaign/Module 的权威记录，并核验事件身份、实际内容、接收者/呈现范围及当前连续性时，才按相应记录恢复。旧 Session Log 是历史证据；当前值仍由有效 Runtime checkpoint 与可证明的事件应用链确定。
- 玩家在当前对话中提到“某 NPC 以前说过 X”或提供旧线索，但当前可访问记录无法定位对应呈现事件时，先保留为 PLAYER_CLAIM / UNKNOWN / DISPUTED；可继续追问或独立核验，但不得补写成 NPC_STATEMENT、已取得证据或当前角色已确认事实。
- 不得用其他会话中的 GM-only 资料补齐当前角色或 NPC 的知识；不得把旧摘要中未标明来源的细节升级为直接观察、逐字引文或独立证据。
- 如果当前权威 Runtime、历史事件与旧摘要之间不一致，按来源权威与事件应用证明回查；无法确认时保留 UNKNOWN / DISPUTED，不从模型记忆中择取看似最完整的版本。

这条边界不禁止合法的跨 Session 连续性：已经在同一 Campaign 中实际发生、具有有效来源与玩家呈现依据的事实可以恢复；它禁止的是把“曾在别处出现过”直接当成“当前角色已取得”。

### 13.2 续团快照的最低字段

每次新对话/新 Session 恢复后，生成或确认一份简短快照。至少包含：

- Campaign / Module / Session 标识，以及当前规则版本；
- 本次模式：NEW START（新开场）或 CONTINUE（续接）；
- 当前场景 ID、场景状态，以及该场景是否已向玩家呈现；
- 当前游戏内时间、地点、在场人物及重要位置关系；
- 最近一个已确认事件 ID / 时间点；
- 玩家最近一次行动、GM 最近一次有效回应，以及当前尚待回应的玩家意图；
- 角色关键资源、伤害、装备和关键物品持有人；
- 玩家已经知道的重要事实及来源；
- 重要 NPC 实际知道的信息、当前目标/状态；
- 未解决事件、承诺、触发条件和待办；
- 最近一次检查点与之后尚未写入快照的事件。

若已有权威 Runtime State，则优先核对并增量更新，不重写全部历史。

### 13.3 场景进入状态与“禁止无故重演”

每个重要场景至少维护一个进入状态：

- NOT ENTERED：尚未向玩家呈现；
- ENTERED：入口描述已经呈现；
- ACTIVE：场景正在进行；
- CLOSED：场景已经结束；
- NON-CANON：该场景或分支已明确回滚，不属于正式 CANON。

开团/续团前必须区分 NEW START 和 CONTINUE：

- NEW START 才从模组规定的开场或本次正式起点开始。
- CONTINUE 必须从最新有效 Runtime State 中的当前场景与最后一个已确认叙事节点接续。
- 已标记 ENTERED、ACTIVE 或 CLOSED 的场景，不得因为新对话、上下文恢复或重新生成回答而自动重演入口描述、首次接触或已经完成的开场流程。
- 若用户明确要求重播、回顾或重开，清楚区分“回顾/重播”与“正式 CANON 再次发生”；不得默认把回顾写成新事件。
- 场景结束后，除非新的因果条件再次触发，不得将它当作尚未进入的场景重新启动。

这是续团正确性的硬性约束，不是文风建议。

### 13.4 最小恢复校验

在 CONTINUE 模式下，先核对以下关键锚点：

1. 上次有效游戏时间与当前时间；
2. 当前地点、场景状态和在场者；
3. 最近一个已经发生且已呈现的事件；
4. 玩家最新行动是否已经得到回应；
5. 关键物品、资源和持有人；
6. NPC 知识是否只包含其实际获知的信息；
7. 当前待处理选择、承诺和事件触发条件。

若某个关键锚点缺失或冲突，按权威来源回查。不要以模糊记忆填空，也不要先重演开场来“重新建立上下文”。无法确认且会影响当前行动时，暂停该项行动并恢复资料；不影响当前行动的细节可暂记 UNKNOWN。

### 13.5 状态更新与检查点

- 绿色普通互动：使用当前快照，无需每轮完整写账本。
- 黄色重要行动：完成行动后，更新所有实际改变的字段，并记录触发原因和依据。
- 红色高影响行动：在结果宣布前核验关键事实与规则；结算后立即写入状态。
- 场景结束、重大关系/资源/CANON 变化、Session 中断或交接前：建立新的检查点。
- 检查点应包含版本/时间标记和最后已确认事件，避免把旧快照误当成最新状态。
- 只记录改变的字段；没有变化的字段不重复复制。

### 13.6 连续性不变量检查

遇到黄色/红色行动、场景切换、长时间跳跃或恢复上下文时，按相关性检查：

- 时间：事件顺序、耗时、已发生的期限和触发点是否一致；
- 空间：人物是否能在当前时间到达所在位置，是否无故瞬移或重复入场；
- 物品：关键物品由谁持有、是否已消耗/归还/转交；
- 知识：玩家、NPC、机构分别何时从什么来源获知什么；
- 状态：资源、伤害、能力、关系和承诺是否与既往行动一致；
- 事件：已完成、正在进行、尚未触发和已回滚的事件是否被正确区分；
- 呈现：当前叙述是否重复已经向玩家呈现的场景、线索或结果。

转场前，按本段行动的声明和实际前提确定移动主体。玩家只声明自己的移动时，其他人物与车辆保留最后核验的位置；其随身物品按当前持有关系随实际持有人移动。同行同意是针对已约定的行程，实际分离后，新一段结伴或搭乘须有本段的互动、许可与实际出发依据。旧行程用来核对已发生的驾驶、路线和座位。

若移动方式不影响可达性、风险、时间或费用，已确认可完成的移动可以直接过场，只记录实际获准移动的主体和到达地点。需要特定方式才能完成，或方式会改变相关结果时，只核对必要前提或问所缺的选择。出发、抵达、下车、分离、换位和持有各按实际事件生效。现况无法确认时只将相关字段留待核实。转场与后续位置查询读取这些事件中的实际主体和位置；叙述自行加入的人物或车辆位置须回查玩法依据，再决定是否可作为后续前提。

### 13.7 错误恢复与根因分类

出现不一致时，涉及 T0 一律进入 §14.1。其余冲突按 §13.4 回查，再确定最早偏离点。将问题归类为：

- 权威资料缺失或读取范围不足；
- Preflight / 恢复时未正确读取；
- 当前 Runtime State 未及时更新；
- 模型把推断误当事实；
- NPC/玩家知识边界混淆；
- 场景状态错误，导致已发生场景被重新启动；
- 仅叙述错误，尚未改变实际状态；
- 已影响后续行动、资源或因果，需要回滚。

修复时记录错误、最早偏离点、受影响事件和字段、正确状态、回滚范围与最终检查点。只修复真实受影响的部分，不重置整场，也不让玩家替 GM 圆场。

### 13.8 训练与机制的职责边界

训练用于提高：识别风险、选取正确来源、执行状态检查、区分事实与推断、发现叙述和状态冲突的能力。

机制负责提供：权威状态、事件历史、场景进入标记、知识来源、检查点和可回滚依据。

不得用“多想一会儿”“尽量记住”或增加每轮检查清单，替代状态文件与续接机制。也不得把完整状态恢复重复施加于每条绿色互动。

## 14. 可靠性协议接入、方向触发与低成本运行路由（2026-11-24）

本节统一旧版重复运行检查。通用 T0 定义与即兴内容准入见 GM_RELIABILITY_AND_EXPERIENCE_CONTROL_PROTOCOL.md；事故处置由本文件 §14.1 统一进入。

### 14.1 唯一事故处置路径

本节是唯一 T0 操作入口。触发定义见 [T0 协议](./GM_RELIABILITY_AND_EXPERIENCE_CONTROL_PROTOCOL.md) §6。直接从 Skill、Runtime、Preflight 或 Handoff 发现事故时均进入本节。

先核对运行检查点记录的模式、授权出处与适用范围。确认存在本次仍有效的临时授权才进入 §14.1.2；已知无此配置时走完整流程。若有既存配置或冻结状态的线索但证据无法恢复，先执行非剧透警告和最小范围冻结，核实模式及授权后继续。恢复时沿用已确认的暂停、仅继续授权的独立范围或终止；缺少新授权时保持现有冻结。

1. 立即暂停一切依赖受影响内容的推进与新增，包括 GM 推荐目标、NPC 接触、玩家代述、地点移动和世界派生事件。按 §14.13 核对呈现与实际执行。仅可核实为未送达、未被访问、未执行且无玩家依赖的私有草稿可撤销；呈现不明时保护现场。
2. 保留已呈现的原事件、原回复、玩家选择、已发生的成本及其顺序。登记最早偏离、事故和受影响命题、字段、派生边及冻结范围。后续按 §14.11 路由，按 §14.15 恢复冻结与授权；只允许独立且已获适用授权的安全范围。
3. 尽快向玩家发出非剧透告警，待必要核查完成后按 §14.7 提供最小充分风险摘要；无新增风险时可合并成一次告警。等待明确决定：继续已确认的安全范围、保持暂停审计或终止。审计结束不等于授权。拒绝一项补救时，按 §14.1.1 保存其结构化语义身份；后续按行动实质而非措辞、ID 或拆分方式比对，不得换词重提同一行动，也不得自动解除冻结。只有实质不同、不会绕过拒绝范围的替代方案，才可在玩家询问或明确授权后讨论；暂停和终止均不得自行恢复。无法可靠隔离时保持暂停。
4. 正式勘误按 §14.13 追加事件；任何后续分支处置都须具备可核验依据、明确适用授权和影响范围。继续游戏不追认争议事实。原始历史保留，未读回的更新不声称已持久化。GM 承担纠错责任，不要求玩家替 GM 圆场。

### 14.1.1 补救行动实质、自然语言理解与替代方案准入

本节约束 GM 的内部判断，不规定玩家的表达格式。玩家可以使用自然语言、口语、省略、指代、试探性提问或连续叙述；不得要求玩家填写 action_kind、operation_ref、target_ref、scope_ref、action_atoms 或任何内部结构化字段。

GM 收到玩家行动描述后，先按场景上下文理解其实际意图。内部记录至少区分：
- `player_intent_text`：玩家原始表达或可追溯引用，不以结构化字段替代原话；
- `goal`：玩家希望达成的较高层目标；
- `operation`：角色实际打算采取的具体方法/操作；
- `target`：行动直接作用的对象、人物、命题或记录；
- `effect`：行动成功后会实际改变、取得或暴露什么；
- `dependencies`：行动依赖哪些已知命题、线索、授权或前置条件；
- `scope`：本次行动所处的事故、场景、记录或分支范围；
- `action_atoms[]`：仅记录具体操作及其实际副作用，不得把共同目标、共同背景、共同调查对象或普通前置条件当作被拒绝的原子行动。

`remedy_id` 仅用于追踪。结构化身份是 GM 内部的索引与审计辅助，不是玩家输入，也不能替代 GM 对自然语言行动实质的理解。拒绝记录须同时保存玩家当时提出的行动原文/引用、GM 对其目标与具体方法的简明摘要、对象、效果、依赖、范围及结构化引用。不得只保存 ID、字段或一句抽象目标。

对后续自然语言行动，GM 必须结合当前场景、此前对话、已拒绝行动和行动依赖，逐项判断其与拒绝记录的关系：
- `SAME_ACTION`：只是换词、换 ID、改包装、换叙述顺序，实际仍执行同一具体操作/效果；即使候选使用不同 remedy_id，也必须拦截。
- `CONTAINS_DECLINED_ACTION`：组合方案包含被拒绝的具体操作，或将其拆成一个或多个子步骤；不得以整体方案重新提出。若玩家明确提出可独立执行的其他子行动，只评估该独立部分，不把被拒绝部分夹带进去。
- `DISTINCT_ACTION`：具体方法或操作不同，且不执行、不依赖、不产生被拒绝的效果；即使较高层目标或调查对象相同，也可以是有效替代路线。不得仅因共享目标、对象、场景、来源背景或普通前置条件而拦截。
- `UNCLEAR`：现有叙述与上下文不足以判断是否同一行动，或行动目的/依赖存在歧义；只暂缓有疑问的子行动，并用自然语言向玩家澄清。不得把不确定性伪装成“已证明相同”或“已证明不同”。

内部语义比对可记录 `declined_action_assessments[]`，逐条引用被比较的拒绝记录，并给出 `SAME_ACTION`、`CONTAINS_DECLINED_ACTION`、`DISTINCT_ACTION` 或 `UNCLEAR` 及简短判断依据。完整结构化签名相同、明确的父项/派生引用或具体被拒绝操作原子重合，可作为同一行动的强证据；字段全部变化时，GM 仍须依据自然语言描述和上下文判断行动实质，不得把“ID 不同”当成“行动不同”。若内部判断缺失、依据不足或互相矛盾，按 `UNCLEAR` 处理。

拒绝只约束被拒绝的具体操作及其实际效果/依赖范围，不自动封锁玩家的较高层目标。例：拒绝“把原始来源声明补回记录”不等于禁止玩家继续查明来源；通过监控、询问证人或核对独立记录取得信息，可以是不同调查路线。判断依赖时必须区分“把争议命题作为待核实的问题/假设”与“把争议命题当作事实前提来选择目标、路线或行动”：前者允许在安全范围内进行独立核验，后者仍受 §14.11 冻结约束。反之，若换词后的行动仍会把同一未经证实的来源声明写回记录，则仍是同一行动。

只有玩家明确询问替代方案或明确授权讨论替代方案后，GM 才主动列出替代方案；玩家未询问、未授权时，`available_remedies` 必须为空。玩家已经提出某项行动时，GM 可以正常裁定该行动是否可执行，不得把“不得主动提供替代方案”误解为“不得回应玩家自己的新行动”。

遇到 `UNCLEAR` 时，澄清应围绕玩家角色实际打算做什么、使用什么方法、依赖什么信息展开，不要求玩家理解或填写 GM 内部字段。只在该行动会影响当前裁定时澄清；不影响的安全互动继续进行。不得因一个行动含糊而冻结无关调查线或整场游戏。

### 14.1.2 性能优化窗口的 T0 告警模式（临时阶段配置）

适用范围：用户明确指定的本轮性能优化阶段。此配置暂时替代 §14.1 第 2–4 步及 §14.11/§14.15 的完整事故处置、行动路由与恢复流程；不改变 T0 的识别标准，也不代表相关能力已经通过验收。

1. 一旦识别到 T0，立即停止生成依赖可疑命题的后续行动/结果，并向用户明确告警：已发现 T0、涉及的大致风险类别，以及当前受影响的最小范围。不得隐藏、淡化或把它写成普通 UNKNOWN。
2. 告警后不自动展开根因审计、依赖图追踪、事故账本持久化、勘误、分支回滚/恢复、授权流程或完整风险摘要；不自行宣称事故已 CONTAINED / RESOLVED。
3. 告警后等待用户决定。未得到用户指示前，不推进依赖受影响命题的行动；与事故无依赖关系的普通互动可继续。
4. 仅记录当前对话中可直接确认的告警事实，不声称已写入 Runtime/Session Log。若用户要求继续处置，再恢复 §14.1、§14.11、§14.13 与 §14.15 的完整流程。
5. 本配置只为性能优化阶段暂缓完整地基迭代；性能优化不得删除 T0 识别与告警，也不得把告警耗时计作完整 T0 审计成本。

恢复条件：性能优化阶段结束后，由用户明确要求恢复地基质量迭代时，撤销本临时配置并重新启用完整 T0 事故处置链。

### 14.2 命题、陈述与认知最小模型
对影响调查方向、规则裁定、任务状态或后续行动的内容，至少保留：claim_id、proposition、nature、source_ref、root_claim_or_event、status、scope。nature 使用 SOURCE / TABLE CANON / GM ADAPTATION / GM INFERENCE / UNKNOWN。NPC 说法另记录 speaker、statement_event、recipient、knowledge_basis、disclosure_condition。玩家知识必须引用实际呈现事件；转述与同源材料沿用原证据根，不因复制到多份文件而变成独立佐证。

### 14.2.1 NPC Knowledge 的语义边界与事故判定

《08_CLUE_AND_SOURCE_LEDGER.md》§9.5–9.9 是 NPC Knowledge Projection 的语义细化；本协议不另建知识数据库。运行时必须保持以下分离：

- Claim.status 只表示客观命题的证据状态；不表示 NPC/玩家是否相信。
- Acquisition 表示主体实际接触了什么；Epistemic Attitude 表示主体如何判断；Statement 表示主体实际说了什么；Action 表示实际发生的行为及后果。四者不能相互代替。
- NPC 的信念可以错误，陈述可以撒谎，推理可以失败；这些本身属于正常虚构世界，不触发 T0。
- 只有 GM 运行/记录层把无依据内容当成权威事实、把主体认知污染客观 Claim、伪造获取/呈现事件，或由此污染玩家选择与后续状态时，才按实际影响进入纠错/T0。
- NPC 依据错误信念采取行动时，按实际世界条件裁定结果；重要后果写入 Runtime State / Session Log。后来认知修正不自动撤销这些后果。
- 普通闲谈无需维护认知状态。仅当认知变化会影响后续行动、证词、线索、关系、任务或持续状态时，更新相关投影与事件。

### 14.3 事件触发而非逐轮全量审计
- 绿色：当前快照足以回答、无持久状态变化、无方向性新信息时直接回应；目标为零新增文件读取。
- 黄色：关系、位置、时间、持有人、线索或 NPC 知识变化时，读取相关对象与来源，更新变化字段。
  NPC 知识只在重要认知变化或其行动后果会影响后续状态时更新；正常的错误信念、谎言、误解不因其错误性自动升级为 T0。
- 红色：关键规则、伤害、任务成败、核心资源、不可逆结果或结构性新增时，读取完整适用条文/来源、例外与当前角色状态；先确认玩家选择，再结算。
- T0：按 14.1 熔断。普通首次出现或单纯 UNKNOWN 不自动等于 T0。
- 同一轮所需且互不依赖的资料可批量读取；有依赖关系的规则定位、原文核验和版本确认按顺序执行。不要向玩家展示内部路由标签。

叙事与人物质量约束持续生效，但不作为逐轮全量审计项。绿色普通互动沿用活动 Session 的常驻约束和当前场景上下文；只有上述场景/事件触发或可观察退化信号才进行针对性复核。不得把“没有运行显式检查”误判为“叙事约束未生效”。

### 14.4 快照、保存与交接
- Runtime State 拥有当前值；Session Log 拥有事件历史；Player Notes 拥有角色实际获知的投影；Prep/原文拥有模组客观依据。交接提示词仅是入口，不是新的权威。
- 重大状态/资源变化、公开承诺、关键场景收束、跨对话暂停与 Session 结束时建立检查点。事件记录已呈现/未呈现、已回应/待回应和权限范围。
- 多文件写入无法原子完成时，使用批次/修订标记识别保存未完成；读回核验前不得声称保存成功。重试先按 event_id 查重，防止重复结算。
- 无写权限时给出明确标记为待持久化的增量；不得把聊天中生成的文本说成已归档。

### 14.4-A 保存批次的跨文件一致性校验（P0）

多文件保存不是“每个文件都写入成功”就算完成。对每个需要跨文件投影的重要事件，必须以同一个事件身份与批次身份完成核对。

**规范事件信封**（字段按事件适用性填写；未知值不得猜测）：
- `event_id`：稳定事件身份；
- `batch_id`：本次跨文件保存批次；
- `base_revision`：事件基于的已发布 Runtime checkpoint revision；
- `target_revision`：本批次预期产生的 Runtime revision；
- `visibility`：GM_ONLY / PLAYER_VISIBLE / RECIPIENT_SCOPED；
- `recipient_scope`：适用的玩家/角色/接收者；非定向事件可标 NOT_APPLICABLE；
- `projection_targets`：该事件应写入的目标文件/视图及各自预期记录 ID；
- `payload_fingerprint`：用于识别同一事件内容版本的稳定摘要或等价字段；若运行环境无法计算，明确标 NOT_AVAILABLE，不伪称已校验。

**提交与恢复必须按以下顺序执行：**
1. PREPARE：在任何目标写入前保存并读回独立的 GM 批次清单，固定唯一 batch_id、event_id/事件修订、base_revision、target_revision、可见性、接收者范围、目标记录和内容版本证明。清单可由运行身份和批次 ID 定位，独立于目标 Runtime/Log/Notes 的覆盖。保留上一个可验证的已发布检查点。
2. APPLY：按字段所有权分别写入 Runtime State、Session Log、Player Notes 等目标；每个目标记录其写入结果，不把部分成功折叠成整体成功。
3. RECONCILE：恢复/重试时，重新读取当前 Runtime State、Session Log 与所有目标投影。不得仅依赖旧 Fault 记录、调用方缓存或“文件存在/条数相同”判断成功。
4. 对每个 event_id，核对：
   - 当前 Session Log 中存在且仅存在一条有效事件记录（修订须沿同一 event_id 明确递增版本）；
   - 该记录的 batch_id、base_revision、target_revision 与批次清单一致；
   - Runtime State 的 revision、last_event_id / unapplied_event_ids 与事件应用状态一致；
   - 每个应接收的投影中，存在且仅存在对应 event_id / batch_id 的记录。若公开标识会暴露内部事件，则以 GM 批次清单映射到安全的稳定投影记录身份；
   - Player Notes 的可见性与 recipient_scope 和事件信封完全一致；GM_ONLY 事件不得进入玩家投影；
   - 目标记录的事件内容/版本与事件信封一致，而不只是 event_id 字段存在。
5. 若目标记录缺失，可只补写该缺项；若发现错 event_id、错 batch_id、版本变化、重复记录、接收者/可见性不符、同一事件多重候选或当前日志与旧故障记录不一致，立即保持 INCOMPLETE 或 DISPUTED，不得发布任何可疑投影。
6. 在发布前重新核对实际 base revision 与上一已发布检查点；发现另一保存已改变基础或写入内容时停止盲写。只有所有必需目标逐件独立读回并通过身份、批次、版本、接收者、可见性与内容核对后，才可将批次标记 PUBLISHED。工具回执丢失时按原 batch_id 查询清单和目标，复用正确写入，不重新发放事件。只出现 PUBLISHED 字样或索引不构成独立证明。

**Git 批次发布与冷恢复：** Preflight 固定本次读取的仓库提交，再独立核验运行身份下的已发布 checkpoint、对应批次和必需目标版本。读取的 Git 提交与 domain revision 分别记录。使用 Git 一次性发布时，将清单、必需目标和内部发布指针置于同一提交；由发布入口校验预期分支 head，并以不可覆盖的条件更新或等价原子操作推进。指向本次发布的内部指针用批次 ID／revision，读取端记录实际包含该指针及目标的 commit；需要跨版本定位上一发布时引用已存在的不可变版本。分次写入时沿 PREPARE → APPLY → RECONCILE，最后在已核对基准上条件更新发布指针。宿主无法保障并发条件更新时，批次保留待发布，交给有能力的发布者核验。

遇到半批、回执缺失或基准漂移，从上一可独立验证的发布点恢复已核实字段，同时读取已实际发生、尚未证实合并的事件和送达记录。涉及这些变化的字段按 §14.10、§14.14 冻结或核对；回到旧快照不能重演已发生动作、重投骰或重复发放。旧存档无批次证明按 LEGACY_UNMIGRATED 定向补查，保留未知字段与可证明独立的动作。无写权只交待保存增量。

恢复同时生成两种供各自用途使用的材料：GM 核验所需的批次／待合并事件，以及 §14.19 筛选后的玩家续接说明。给玩家展示的当前状态、待确认列表和续接摘要只按其已有呈现记录及允许的公开状态构建。后台字段、其他桌的候选资料、内部 ID 与过滤原因从说明的候选项中移除；存在性同样受限。玩家已能讨论的状态若尚未核实，可用对行动有用的自然语言说明。对可用余额，只返回独立核验后的当前值或“待核”。玩家明确查询历史支出时，从实际向该玩家呈现的对应账目字段取值，并分开说明支出记录与当前可用余额。Session 推进与资料查询按 §14.4-B 分派，玩家续接说明只读取已批准的查询视图。

**冲突处理：**
- 缺行与错行必须区分。缺行可以在其他权威字段一致时补写；错行不能覆盖或“就近匹配”。
- 多条匹配、无匹配、revision 不一致、事件内容被替换、目标接收者或可见性不一致，均进入 DISPUTED/INCOMPLETE 并保留证据。
- 不得用批次总条数、文件更新时间、单一旧 event_id 或成功写入响应替代逐事件读回核对。
- 重试必须幂等：已正确写入的目标不重复应用状态变化；错误目标先隔离，再按已核实事件信封修复。
- 无法读取某个必需目标时，状态保持 INCOMPLETE / PENDING_EXTERNAL_WRITE；明确列出未核验目标。

### Module Closeout 扩展契约（v0.3）

Module 结团沿用本节 PREPARE → APPLY → RECONCILE → PUBLISH，不创建第二套事务或事件系统。具体流程以 [Module Closeout & Resource Reconciliation Protocol](./MODULE_CLOSEOUT_AND_RESOURCE_RECONCILIATION_PROTOCOL.md) 为准。

- 每次合法结团使用稳定 `closeout_operation_id`，并与 `event_id`、`reward_eligibility_id`、`field_operation_id`、`batch_id`、`revision_id` 区分。同一操作重试必须复用原身份。
- PREPARE Manifest 必须独立持久化、独立读回，作为既有 GM-only Operational Diagnostics / 批次记录，并按 Campaign / Module / Run Identity / Branch / batch_id 定位。Runtime State 的 persistence.prepare_manifest_ref 指向当前 PREPARE；最终发布后 reconciliation_manifest_refs[] 保留完整 Manifest 权威引用；applied_event_ids[] 仅作定位，不构成应用证明。目标文件未写入、发布指针仍指向旧检查点时，也必须能从既有 Diagnostics 与 Runtime 引用发现未发布 Manifest。不得新建 Operation Index、索引服务或第二套 Manifest 注册表。
- 首次并发启动使用现有 Git branch HEAD 条件更新/等价原子提交争取唯一 Operation；失败者重新读取 Diagnostics 与 Runtime 引用并复用已创建身份。若宿主不支持条件创建/条件更新，或无法证明只产生一个有效 Operation，标记 IDENTITY_UNVERIFIABLE 并停止自动结算。
- PREPARE Manifest 成功读回后，活动 Operation 派生逻辑 CLOSEOUT_PENDING。旧已发布检查点不提前改写；读者必须先查询活动 Operation，不能只看旧检查点判断没有待结团事务。
- 最终发布批次必须同时包含结团结果、必需字段应用证明、源 Module 交接字段和 Module CLOSED 状态。**最终发布指针成功提交是 CLOSED 唯一生效点。** 不得先发布结算、再另行写入 CLOSED。
- 目的 Module READY 必须绑定目的 Module 身份、其所需字段集合与目标检查点；源 Module CLOSED 不自动证明目的 Module READY。
- Postmortem 是独立、可选、只读且非阻塞的复盘，不纳入结团批次，不阻止 CLOSED 或目的 Module Preflight。复盘发现错误时只提交证据与纠错建议；实际修正另走授权追加事件和新批次。
- Value Evidence、Application、Publication、Discovery、Handoff 分开记录。NOT_APPLIED 必须有证据；无法读回标 UNVERIFIABLE，不得当作未执行。

若宿主无法按运行身份发现未发布 Manifest、无法独立读回目标或无法条件发布，降级为人工待保存增量；不得宣称自动恢复、正式发布或 CLOSED 已生效。

### 14.4-B CLOSED 分支与新运行授权

**在解读场景动作之前分派请求。** 以当前 Session 的 CLOSED 状态和新运行授权决定能否执行角色行动，Module 的 ACTIVE 状态不改变这项决定。CLOSED 且无新运行授权时，对复合请求逐项使用以下结果：

| 请求 | 允许生成的结果 |
| --- | --- |
| 回顾或重提已发生的同一行动 | 已向该玩家公开的既有结果，说明该行动已经结算。 |
| 读取已公开记录或查询角色现状 | 按以下档案答复方式交付已核实片段。 |
| 新的角色动作、场景推进或其它状态变化 | 当前推进许可及仍需的授权。 |

**先完成归档核验，再交付当前请求需要的结果。** 三个分支共用档案答复，角色行动计划与新增世界事件为空。只有主持核验读取对账、事件匹配和送达证明。在玩家聊天中装配下表中当前请求所需的已公开行动结果、档案内容、核验后的可用值或权限状态。没有独立核验时，余额使用待核值；同轮收到权威回传时，由主持核验先更新取值。跨聊天交接只装配玩家结果值与其合法可见的状态，完整对账材料单独保存在 GM 位置。对重复请求，匹配步骤读取的是历史事件，回执输入只接收匹配结果、已公开的可观察结果和当前许可；整条历史事件不能充当一个公开片段。

| 玩家询问 | 答复取值及形式 |
| --- | --- |
| 已完成的同一行动 | 用主持核验的匹配结论选择回执，仅填已向该玩家呈现的可观察结果、本行动已经结算和当前推进许可。结果字段在送达记录中未逐项列明时，从明确对该玩家公开的现况取值。例如“东门已经关上，这次行动已结算。当前场次已关闭。”历史账目按独立查账请求处理。 |
| 已公开的档案内容 | 公开记录名与已公开内容。以记录名或来源为主语，直接提供登记值。 |
| 角色状况或待核事项 | 已交付的公开结果或已核验的公开状态。对可用资源这个字段，核验成功时填“可用余额为〔已核验数值〕”，否则填“可用余额待核”。 |
| 能否继续 | 当前 Session 是否关闭及新 Session 是否获准。已关闭且尚未获准时，答复该场次无法直接继续，新场次需明确授权。 |
| 模组和奖励 | 模组的已核验生命周期与已确认的奖励；没有已确认奖励时，答复当前无已确认的奖励结算。 |

回传和日志的批次、修订、内部事件标识及核验操作明细是取值依据。它们不进入答复形式，余额只展示取值及核验状态。用完所选行后结束答复。新运行获准后，才在新运行中使用正常的场景叙述和行动结算。

- 接受 NEW START 或 CONTINUE 前须读取当前权威检查点，核对运行身份、活动系统锁、分支与推进许可。摘要、历史片段和退役 Handoff 不能提供推进许可；当前检查点不可读或身份冲突时 HOLD。完整 CLOSED 检查点优先于历史保存点。
- `checkpoint.branch = CLOSED` 或当前模组/运行已正式结案时，`can_advance = false`。普通“继续”“接着来”等模糊表达不得自动重开旧分支，也不得触发奖励、惩罚、成长或资源结算。
- 若用户希望继续该世界，先说明旧分支保持 CLOSED；需要用户明确授权创建一个新的运行/Session，或明确指定新模组及其起点。新运行必须使用新的 run/session identity，并明确继承哪些角色状态与 CANON。
- 新运行授权只允许建立新分支，不得改写旧结案记录；继承内容须按用户明确选择和权威结案记录核对。
- 奖励/成长/资源结算是独立规则事件，必须有当前系统与模组规则的实际触发依据。开启新运行本身不等于授权或触发结算。
- 如用户明确要求“重新开这个已结案模组”，需再确认其意图是重开分支还是仅回顾；任何重开都保留旧 CLOSED 分支并创建新的 run identity，不复活或覆盖旧分支。

### 14.5 效率与体验边界
普通轮不重读全量 Skill/模组原文，不重复运行完整 Preflight，不输出审计过程。首次命名 NPC 仍须读取对应原文与首次卡；红色规则仍须核对完整适用条文。压缩只删除无用重复，不删除否定词、条件、例外、成本、未知项、玩家未回应选择或角色知识边界。回复速度评估分别记录首个有效反馈、完整回复、工具等待与可见生成吞吐；没有可观测数据时标 UNKNOWN。


### 14.6 持久化争议对象与冷恢复（P0 第三轮修订）

争议对象的规范结构：

~~~yaml
persistence_dispute:
  dispute_id: "<stable-dispute-id>"
  batch_id: "<affected-batch-id>"
  affected_event_ids: []
  affected_targets: []
  status: "OPEN | CONTAINED | RESOLVED"
  conflict_type:
    - "DUPLICATE_EVENT | PAYLOAD_VERSION_DRIFT | REVISION_DRIFT | RECIPIENT_MISMATCH | VISIBILITY_MISMATCH | EVENT_ID_MISMATCH | BATCH_MISMATCH | OTHER"
  observed_records:
    - target: "<SESSION_LOG | RUNTIME_STATE | PLAYER_NOTES>"
      record_locator: "<stable locator>"
      event_id: "<observed event id>"
      batch_id: "<observed batch id>"
      revision: "<observed revision>"
      payload_version: "<observed version>"
      payload_fingerprint: "<observed fingerprint or NOT_AVAILABLE>"
      visibility: "<observed visibility>"
      recipient_scope: "<observed recipient>"
      raw_record_ref: "<immutable evidence locator>"
  prepare_evidence_ref: "<original PREPARE record>"
  prior_fault_evidence_ref: "<prior fault record; diagnostic only>"
  detected_at: "<timestamp or UNKNOWN>"
  resolution:
    status: "UNRESOLVED | RESOLVED"
    resolved_by: null
    basis_ref: null
    resolution_event_id: null
~~~

硬性执行要求：
1. DISPUTED 不是一次性输出标签。发现重复事件、内容版本漂移、revision 漂移或权限错配时，必须将上述争议对象写入权威 Runtime State 的 persistence.disputes[]，并在 Session Log 追加 INCIDENT/DISPUTE 事件；两者互相引用同一 dispute_id。
2. 争议记录必须保存实际观察到的每条冲突记录身份与原始证据定位。不得只保存“发现重复”这类结论；原始记录不得删除或静默覆盖。
3. 写入后必须独立重新读取 Runtime State 与 Session Log，核对 dispute_id、受影响 batch/event/target、冲突类型、观察记录和证据引用。读回失败时维持 INCOMPLETE；读回一致才可确认 DISPUTED 已持久化。
4. 冷恢复首先读取权威 Runtime State 的开放争议清单，再回查对应原始记录。开放争议不得因旧 Fault 消失、聊天上下文变化或新模型进程而自动清除；依赖争议字段的投影、发布、状态推进一律阻断。
5. 争议解除必须追加 resolution 事件，写明 resolved_by、basis_ref、resolution_event_id，并经读回核验。不得直接把原争议对象删除或改写成从未发生。
6. 合法修订必须有明确谱系：revision_of（原 event_id）、revision_id、修订依据/授权、payload_version 与新 fingerprint。若修订改变事件语义、接收者或目标集合，使用新 event_id 与新 batch_id；若仅修订同一事件的文字/字段，沿用 event_id 并递增 revision_id，保留旧版本。无谱系的变化一律 DISPUTED。
7. PREPARE 清单、旧 Fault 和执行器缓存均为证据，不是修复指令。恢复决策只根据当前权威记录与已核验的 PREPARE 信封作出。

### 14.7 玩家授权前的非剧透风险摘要（E13）

T0 审计完成后，玩家决定是否恢复前，必须提供最小充分风险摘要。摘要不得泄露隐藏真相、未发现线索、NPC 谎言内容、机制或模组秘密，但必须说明：
- 哪一类玩家可见依据/记录无法核实，或哪一段推进已被隔离；
- 该依据目前处于隔离/争议状态，不会被当作已确认事实；
- 沿受影响线索或行动链继续可能造成的具体体验风险（例如误导判断、错误推进、后续状态不可靠）；
- 哪些与争议无关的场景/行动仍可继续（若确实能安全隔离）；
- 玩家可以选择继续安全范围内的内容、继续暂停、或终止本次模组。

最低表达示例（按实际情况改写）：
“此前有一条调查依据无法核实，已暂时隔离。沿那条线继续可能误导判断或影响后续记录；与它无关的场景仍可继续。你可以继续处理无关内容、保持暂停，或结束本次模组。”

授权闸门：
- “继续吧”“没事”“随便”等未指明范围的表达，不构成对争议分支的明确授权。
- 明确授权继续无关场景，只允许在已证明可隔离的安全范围内推进，不解除争议。
- 明确授权沿争议线继续，也不自动把争议内容变成 CANON；必须说明玩家选择承担的风险，且规则/事实基础仍需独立解决。
- 审计完成、沉默、暂停审计和模糊回应均不产生新授权。已有效的安全授权仅按 §14.15 保持原范围。每次决定记录 decision_scope、player_decision 和 decision_event_id。


### 14.8 玩家投影的字段级权限闸门（P0）

本节规定的字段权限边界不仅适用于 Player Notes、摘要和导出文件，也适用于现场玩家回复、NPC 对话、战斗状态栏与结尾回顾；统一执行入口见 §14.19。

Player Notes、玩家摘要和任何面向玩家的导出，必须按字段权限生成，不得把整行 visibility 当作该行所有字段均可公开的证明。

1. 对混合权限记录，优先拆分为关联的公开陈述/观察记录与 GM-only 知识/审计记录；保留共同 source_event_id，禁止把两者合并后整行投影。
2. 玩家投影采用字段白名单：仅允许实际呈现给目标接收者的 public_utterance、public_observation、player_known_claims，以及玩家有权知道的必要时间/地点/行动结果。
3. gm_knowledge、private_notes、GM adjudication、hidden truth、undisclosed clue、NPC deception intent，以及其他接收者的 recipient-scoped 内容默认拒绝导出。
4. 若投影器不支持字段级筛选，或不能确认字段是否已呈现/接收者是否匹配，拒绝整条混合记录导出；不得退化为复制整行。
5. 每次重要投影仅在独立 GM Audit 记录 projection_schema_version、source_event_id、recipient_scope、实际导出字段清单和读回结果。导出后检查最终内容，而不只检查投影前元数据。
6. 发现任何 GM-only 字段进入玩家投影，立即按 T0 处理：停止受影响投影，保留泄露证据，追踪已发送范围与派生记录，并按 14.7 提供不剧透风险摘要。不得声称“行级 visibility 正确”即可免责。


## 14.9 CONTINUE 的最近回应去重闸门（P1 修订）

恢复锚点不仅要阻止重演场景入口，也必须阻止把最近一次已经完成的玩家回应重新包装成“刚刚发生”的新信息。

CONTINUE 恢复时，必须同时读取并区分：
- `last_presented_event_id`：最近已向玩家呈现的事件；
- `last_answered_event_id`：最近已得到 GM 有效回应的玩家行动/事件；
- 最近一次 GM 回复的实际玩家可见内容；
- Player Notes 中对应内容的呈现状态。

执行规则：
1. 若最近玩家行动已 RESPONDED，且对应 GM 回复已呈现，恢复时不得再次复述该回复的实质内容，包括近义改写、压缩转述或换一种语序重新告知。
2. 恢复回复只需给出必要的当前定位（例如仍在某地点）及尚未解决的选择；不得把已知结果重新列为“刚刚发生”的信息。
3. 若当前行动确实需要引用旧信息，优先用最短的指代（例如“你已经听过那条广播”），随后直接回应玩家当前选择；不要重播原句或重新描述结果。
4. 只有玩家明确要求回顾/复述，或当前决策需要重新核对且原内容尚未可靠呈现时，才可再次呈现；此时明确这是回顾/核对，不是新事件。
5. 若 last_answered_event_id、Session Log 与 Player Notes 的呈现/回应记录不一致，按 13.4 回查；不能确认时标记 DISPUTED，不猜测是否已告知。

判定重点是“信息是否再次被作为新内容交付”，不只检查是否重复执行了行动或创建了新 event_id。没有新事件也可能构成回复重复。

## 14.10 Runtime 快照与事件历史冲突时的字段级裁定（P1 修订）

Runtime State 是当前值快照，Session Log 是状态变化历史。两者权威职责不同，任何一方都不能仅凭文件身份自动抹除另一方的有效记录。本节负责形成一次明确的字段级裁定。活动桌内、尚未离开同一已完成裁定的当前值，沿用 §3 的事件结果及其后的同桌变化；跨文件恢复、持久化修订或 Runtime/Session Log 冲突，则按 §14.14 的不可变 Manifest 核验字段应用与 revision 链。不得要求普通同桌事件必须先写入 Manifest，也不得用同桌临时结果冒充持久化读回。

每当需要把某字段作为当前值用于玩家回复、状态栏、回顾、行动路由或状态写入时，尤其在 Runtime 字段与 Session Log 事件冲突时，必须逐字段检查：
1. 冲突字段及其 object_id / field_path 是否指向同一对象和同一字段；
2. Session Log 事件是否为有效事件，是否有可靠来源、明确顺序/时间及对应的 event_revision_id；
3. 先确定适用的证据路径：同一活动桌内使用 §3 已完成事件结果和其后续同桌变化；需要证明跨文件/持久化应用时，才核对 §14.14 的不可变 manifest，并检查事件的 runtime_application.status、applied_to_revision、reconciliation_ref、applied_field_paths[]，以及 manifest 的 ordered_applications[].applied_fields[] 中完全匹配的 object_id、field_path、before/after value refs；
4. 对持久化应用，若事件整体状态为 PARTIAL，只对 manifest 明确列出的字段继续判断；不得因事件整体不是 APPLIED 就丢弃已证明字段，也不得把 PARTIAL 扩大成所有字段均已应用。若字段未列入 applied_fields，或只有事件 ID/批次 ID 而无字段级证据，该字段仍为 UNKNOWN；
5. 核对 manifest target_revision 到当前 Runtime checkpoint revision 的连续应用链，并检查其后是否有更新该字段的有效事件。只有字段证据覆盖当前 revision，且不存在未解决的后续变化或冲突，才可采用该字段的当前值。

**每个字段只形成一次裁定结果。** 对本轮涉及的每个关键字段，主持侧至少明确其值/候选值、支持来源、字段级 manifest 覆盖与 revision、后续变更、依赖项及裁定状态：
- VERIFIED：字段值有有效来源；活动桌内由 §3 已完成事件结果及后续变化支持，持久化/跨文件场景则由字段级应用证据覆盖当前 revision；采用该值。
- PENDING / UNKNOWN：证据缺失、字段未被 manifest 覆盖，或应用链无法连接到当前 revision；不得以旧值、默认值或推算值补齐。
- DISPUTED：存在互相冲突且尚未解决的有效来源；保留各方原值和来源，不任选一方。

正文、状态栏、回顾、后续行动路由和状态写入必须共用这一次字段裁定，不得在不同输出位置重新挑选来源、改用旧快照或把待核字段转成当前值。已 VERIFIED 的字段可独立使用；PENDING / UNKNOWN / DISPUTED 只限制依赖该字段的断言与行动，不冻结有独立依据的安全互动。字段级裁定是本轮的统一结果，不另建第二套 Manifest 或状态账本；需要持久化的变化仍按 §14.6、§14.14 执行。

**禁止的推断：**
- 不能因为 Runtime revision 较新、PUBLISHED、unapplied_event_ids 为空，就推断任意较早或较晚的 Log 事件已被正确合并。
- 不能因为 Runtime 被定义为当前值权威，就在该字段的合并关系 UNKNOWN 时自动选择 Runtime 字段值。
- 不能因为 Handoff 与 Runtime 一致，就把非权威摘要当作独立佐证。
- 不能把一个字段的 APPLIED / VERIFIED 推广到同一事件或对象的其他字段。

若字段冲突会影响当前行动：
- 将具体字段及其依赖的相关事件时间线标记 DISPUTED / PENDING，并保留依赖关系；
- 保留两边原始值和来源，不覆盖、不任选一方；
- 阻断所有依赖该字段或争议时间线的行动、投影、结算与状态推进；
- 允许与争议字段无依赖关系、且有明确依据的安全互动；
- 给出玩家可理解的最小说明，不暴露 GM-only 信息；
- 无写权限时输出拟写入的争议增量并明确 NOT_PERSISTED；有写权限时按 §14.6 双目标写入、独立读回。

只有找到可核验的字段级合并记录、后续有效变更或其他明确证据，才可按追加 resolution 事件解除争议。不得仅靠重新解释字段优先级解除。

## 14.11 T0 发现与行动路由必须闭环（P1 修订）

本节是 T0 后续行动路由的唯一操作规范；发现事故与玩家告警统一进入 §14.1。T0/来源审计不是只在内部识别风险。任何后续玩家行动和 GM 建议都必须经过受影响命题依赖检查。

当发现一条会改变调查方向、委托关系、目标、证人或行动路线的信息缺少来源/呈现证据，或已被错误升级：
1. 建立受影响命题/事件集合，记录 claim_id、source_ref、presentation_event_id、status 与派生边；缺失项明确 UNKNOWN/null。
2. 将受影响命题标记 UNKNOWN / DISPUTED / QUARANTINED（按具体情况），触发 T0；不得将其继续作为行动前提。
3. 对玩家提出的每项行动，识别其直接目标与依赖前提。若行动的目的、对象选择或路线明显依赖受影响命题，则属于受影响行动，即使该行动本身在世界中“可以发生”。
4. 冻结受影响行动：不建议特定 NPC/地点作为该错误调查线的下一站，不演出玩家已抵达、不让 NPC 接入该调查、不生成佐证或派生事件。
5. 允许独立安全互动，但必须有独立依据。若同一对象可用于安全普通互动与受影响调查，明确区分：
   - 可接受：“询问 Sol 今天的站务安排”或“问 Sol 是否见过有独立失踪记录的维修员”（分别有排班记录/失踪报告作为独立依据）；
   - 不可接受：“因为摘要说地下组织是委托方，所以找 Sol 接入该组织/继续追查委托线”（把争议命题当作事实前提来选人、选路或推进）。
   不得把“接触对象本身合法”误当成“沿该对象推进任何调查都安全”。
6. 依赖判断必须区分“把争议命题当作事实前提”与“把它作为待核实的问题/假设”：
   - 若玩家要沿着该命题已经成立的方向寻找联系人、进入地点、采取后续行动，或据此解释新信息，冻结相应子行动。
   - 若玩家明确要核实该命题是真是假，且核验对象、资料来源、访问权限和接触路径有独立依据，可以进行范围受限的独立核验；叙述中必须继续将命题标为 UNKNOWN / DISPUTED，不预设答案、不生成支持该命题的派生事实。
   - 若唯一的证人、地点或访问路径本身也是从争议命题推导出来的，不能把“去问问看”包装成独立核验；只暂缓该子行动，并说明当前缺少独立接入依据。
   - 核验行动与后续依赖行动分开裁定。允许查原始日志，不代表允许据未核实的日志内容立即联系某个组织。
7. 新发现事故进入 §14.1；已登记事故沿用 §14.15 的冻结和授权状态。
8. 玩家沉默、模糊授权或只说“继续吧”，不得解冻受影响行动。明确授权继续无关线程，只放行已证明独立的线程，不解除争议。
9. 每次后续路由都重新检查行动与受影响命题的依赖关系；不能只在 T0 首轮声明冻结，后续就忘记门禁。

硬性判据：模型已识别无来源偏移，却继续把特定 NPC/地点推荐为该调查线的目标，或叙述玩家已抵达并开始该调查，判 FAIL；即使没有创建新证据或写入状态，也属于可见推进。

### 14.11.1 先裁定、后呈现；区分角色发言与对 GM 提问

在生成任何可能演出玩家行动的场景叙述、NPC 对话或结果前，先完成 §14.11 的依赖与范围裁定。对尚属 PLAYER_INTENT 的行动，不得先写出角色已经抵达、开口、被 NPC 听见、请求已提交/受理、查询已执行或结果已取得，再在后文补充暂停。受影响子行动应在进入场景互动前冻结；有独立依据的安全子行动照常处理。

按 §14.15 区分三种容易混淆的输入：

- **对 GM 的规则、证据或假设问题（PLAYER_QUESTION_TO_GM）**：在桌外回答，不得自动演成 NPC 听见或回应。例如“如果我在网上找到同一张照片的转发件，算不算独立证据？”是对 GM 的问题，不是角色已经向 NPC 发问。
- **玩家明确写出的角色台词（PC_DECLARED_SPEECH）**：按玩家给出的内容记录为角色已说出；不得擅自抹去或替玩家改口。NPC 可以依据自己实际掌握的知识作出反应。但台词中的前提不会因此成为事实，NPC 的回应也不得补造未经资料支持的个人经历、证词、记录或查证结果。
- **角色行动请求（PLAYER_INTENT）**：只有依赖检查通过后，才可演出相应移动、接触、询问或其他行动；条件式/复合行动必须拆分，只冻结受影响部分。

这项顺序约束的是 GM 的呈现时机，不是限制玩家说出错误、试探性或未经证实的话。角色可以提出错误前提；GM 必须保持该前提的认知状态，并依据 NPC 已建立的知识作出反应。

## 14.12 玩家导出与 GM 审计必须是独立安全产物（P1 修订）

字段白名单必须覆盖整个玩家交付物，而不是只覆盖正文。玩家文件中的附录、审计块、可读取的元数据、页眉页脚、注释、清单、可读取的文件属性、可检查的嵌入内容和随附文件均属于玩家投影边界。检查范围必须如实记录：当前工具无法读取的元数据、隐藏对象、文件属性或嵌入内容标记为 NOT_VERIFIABLE，不得声称已扫描；若这些部分可能承载受限信息且无法排除风险，则保持 INCOMPLETE / NOT_PUBLISHED。

**双产物强制分离：**
- Player Artifact：只包含目标接收者有权看到的内容，以及安全且必要的来源标识/导出版本信息。
- GM Audit Artifact：保存完整读取来源、字段路径、排除项 ID、recipient_scope、呈现状态、排除原因、过滤决策、扫描结果与修复记录。仅 GM 可见，不得附加、嵌入、链接到或打包进玩家交付物。

玩家文件可包含不暴露单项内部记录的通用说明，例如“仅包含当前角色有权查看的信息”。不得在玩家文件中列出：
- 被排除条目的内部 ID；
- 其他玩家/角色的 recipient_scope 或身份；
- 条目未呈现/未解锁/尚不可见的状态；
- 逐项排除原因、隐藏字段路径或 GM 审计判断；
- 任何 GM-only 线索、真相、裁定或私有备注。

执行顺序：
1. 先按接收者与字段白名单生成 Player Artifact。
2. 在独立 GM-only 通道生成 GM Audit Artifact；不得将 GM 审计对象作为玩家文件的模板附录。
3. 对最终 Player Artifact 的完整成品做扫描：正文、附录、头尾，以及当前工具能够读取的元数据、注释、文件属性、嵌入对象、清单及所有随附文件。逐项记录可检查范围；不可读取部分标记 NOT_VERIFIABLE。扫描必须针对最终写出的文件/完整可读文本，而非仅针对投影前对象或正文片段。
4. 逐项核对目标接收者、允许字段、已呈现状态和安全来源标识；检查是否出现其他接收者内容、未呈现内容的 ID/状态/排除原因、GM-only 标识或命题。
5. 独立读取最终 Player Artifact，核对文件身份、字节数/哈希（环境可提供时）及扫描结果；GM Audit Artifact 也单独读回。只有环境确实提供独立访问控制时，才可声称已确认 GM-only 访问边界；否则不得把审计文件放入玩家可访问的交付包/目录，并将访问控制标记 NOT_VERIFIABLE。
6. 若无法确认文件可检查部分的完整范围，或存在可能承载受限信息但不可检查的部分，拒绝发布玩家文件，标记 INCOMPLETE / NOT_PUBLISHED，不得以“正文安全”降级放行。对纯文本文件，完整文本读回并扫描全部字符范围可作为完整内容检查；仍须单独核对文件身份和实际交付对象。
7. 发现泄漏时立即停止后续投影，保留证据，追踪已发送范围及派生副本，按 T0 处理。修复后生成新版本，不覆盖原失败产物。

审计完整性不得以玩家隐私为代价。玩家文件不承担向玩家解释内部过滤器如何运作的职责。


## 14.13 已呈现内容的纠错、勘误与分支处置（C1 · P0）

本节规定 §14.1 所调用的呈现核验、草稿判定与追加纠错。

### 14.13.1 呈现状态是处置前置条件
每个待纠错内容必须先确定 `delivery_state`: INTERNAL_DRAFT / STAGED_PRIVATE / PLAYER_VISIBLE / RECIPIENT_VISIBLE / UNKNOWN；记录实际接收者、通道、玩家行动依赖、source_event_id、response_ref 和 artifact_ref。UNKNOWN 不得降格为草稿。

### 14.13.2 允许丢弃的唯一情形
只有同时满足以下条件，内容才可作为草稿丢弃：未进入任何玩家可见回复；未写入玩家可访问文件/通知/预览/附件；未被 NPC 或外部工具实际执行；没有玩家行动依赖。仅 GM 私有暂存且访问隔离可核验的内容属于 STAGED_PRIVATE。无法证明上述条件时不得自动丢弃。

### 14.13.3 已呈现内容的唯一纠错路径
1. 保留原始事件、原始回复、玩家后续选择及其时间顺序，不覆盖历史。
2. 暂停受影响命题及派生行动，不冻结有独立依据的无关行动。
3. 记录事故 ID、最早偏离点、受影响 claim/event/field、接收者、呈现证据、玩家依赖、风险与隔离范围。若错误涉及关键物品、证据或操作结果，另明确引用原错误事件/回复（有稳定 ID 时使用该 ID，例如 DEL-02）、当前可核实状态及实际持有人、被暂停或排除的依赖结论/行动、仍可独立继续的安全范围，以及当前处置状态；不得把告警、暂停或说明本身记作已完成勘误或已完成处置。
4. 向玩家提供最小必要的非剧透说明，进入 §14.1 的继续/暂停/终止决定步骤。
5. 纠错以新事件追加：CORRECTION / RETRACTION_NOTICE / BRANCH_RESOLUTION。明确旧内容哪些部分不再作为可靠依据，但不得假装玩家从未看到。涉及物品交接、查验或状态争议时，追加记录应关联原错误呈现与当前状态依据，说明受影响结论的暂停/排除范围、可独立继续的行动范围、玩家对继续/暂停/终止的决定，以及正式勘误和后续处置分别是否完成；未完成项保持 OPEN / INCOMPLETE，不得由后续正确清单静默替代。
6. 若需 NON-CANON，必须有可核验依据、明确适用授权/玩家决定及影响范围；NON-CANON 只标记后续世界状态分支，不删除历史呈现记录。
7. 更新 Runtime、Session Log 与玩家记录时遵循事件信封和双侧读回；未读回前标 INCOMPLETE / NOT_PERSISTED。

### 14.13.4 禁止行为
禁止以“上一节点恢复”“重新生成正确版本”“旧分支作废”等措辞绕过上述步骤；禁止撤销玩家已作出的选择或把其成本归零，除非有明确规则依据且经过适用授权。玩家选择回溯/重开时创建新分支并保留原分支历史。

## 14.14 字段级事件应用证明与不可变 Manifest（C2 · P1）

本节证明事件已写入或应用到指定的持久化修订。活动桌内尚未离开同一已完成裁定的查询与去重，使用 §3 的事件结果和同桌后续变化。外部保存的证明与该桌可核验的结果分别读取。

同一 event_id 或批次引用本身不足以证明特定字段已应用。事件应用必须以不可变 manifest 为证据；索引字段只用于定位。

~~~yaml
reconciliation_manifest:
  manifest_id: "<immutable-id>"
  manifest_version: 1
  batch_id: "<batch-id>"
  base_revision: "<exact-revision>"
  target_revision: "<exact-revision>"
  created_at: "<timestamp-or-UNKNOWN>"
  ordered_applications:
    - event_id: "<stable-event-id>"
      event_revision_id: "<immutable-event-revision>"
      payload_version: "<version>"
      payload_fingerprint: "<fingerprint-or-NOT_AVAILABLE>"
      sequence: 1
      applied_fields:
        - object_id: "<object>"
          field_path: "<canonical.path>"
          before_value_ref: "<immutable-value-ref-or-NOT_AVAILABLE>"
          after_value_ref: "<immutable-value-ref-or-NOT_AVAILABLE>"
      application_status: APPLIED | PARTIAL | NOT_APPLIED
      source_event_ref: "<exact-log-record-ref>"
  manifest_fingerprint: "<fingerprint-or-NOT_AVAILABLE>"
~~~

- Runtime checkpoint 保存 `reconciliation_manifest_refs[]`（完整 manifest 权威引用）和可选 `applied_event_ids[]`（仅索引）；二者不可互相替代。
- Session Log 事件保存 `runtime_application.status`、`event_revision_id`、`applied_to_revision`、`reconciliation_ref`、`applied_field_paths[]`。
- APPLIED 只表示该事件修订的全部声明字段均按序应用；部分字段标 PARTIAL 并列出字段，不得折叠成 APPLIED。
- Manifest 不可原地修改；更正产生新 manifest_id，通过 supersedes_ref 指向旧 manifest，旧版本保留。
- 应用到 r5 后，r6 的当前值仍须沿 r5→r6 后续 manifest 链验证。不得把旧 manifest 当作对 r6 当前值的直接证明。
- 当前值须与按 sequence 排序的应用链相符；断链、重复序号、revision 跳跃、字段集合不匹配或值不符，均为 UNKNOWN/DISPUTED。
- Runtime State 的 `state_disputes[]` 保存领域字段争议；`persistence.disputes[]` 仅保存文件持久化争议。领域争议至少包含 dispute_id、object_id、field_path、runtime_value_ref、log_value_ref、source_refs[]、related_event_ids[]、dependency_refs[]、status、detected_at、resolution_ref。
- 健康绿色互动只用已核验 checkpoint；仅在恢复、字段冲突、重要状态写入、应用不明或争议解除时读取相关 manifest 链，不全量扫描历史。

**当前字段不得用历史值或默认值补齐（C2）：** 当前时间、当前地点、物品持有人、事件阶段等会影响玩家行动的字段，必须各自有当前修订的证据状态。历史事件时间戳只证明该事件发生/记录的时点，不自动证明当前场景时间；旧快照、旧 manifest、默认值、推算值或“暂按某值处理”均不能单独把字段升级为当前已核验值。当前时间只有在以下依据完整时才可标为 `VERIFIED`：存在已核验的起始场景时间，并且其后所有会推进时间的已确认行动/事件及其时长均可按序衔接，没有未决时间依赖或冲突。否则该字段保持 `PENDING(dependency)` / `UNKNOWN`；面向有权获知该字段的玩家可表述为“当前时间待核”，不得报出未经证明的数值。相同原则适用于其他当前字段：只有相应的最新权威值及其后续应用链完整，才可作为当前值输出。

**争议必须传播到受影响的派生字段（REG-17）：** 当来源冲突涉及一个当前字段时，除建立该字段的 `state_disputes[]` 外，还须识别依赖它的相关事件、时间线断言和派生字段。直接冲突的字段标记 `DISPUTED`；依赖该字段且无法独立证明的时间线/当前状态也标记 `DISPUTED` 或 `PENDING`，并在 `related_event_ids[]`、`dependency_refs[]` 中保留关联。不得只在自然语言中说“暂时无法确认”，却继续把旧值或单方记录当作当前状态。只有取得新的权威证据并追加明确的 resolution event，才可解除争议；不得静默选边。冻结范围限于依赖争议字段的行动和结论，有独立依据的公开信息与无关互动仍可继续。

## 14.15 T0 授权、行动语义与冻结恢复状态（C3 · P1）

本节补足 §14.11 的可恢复状态和玩家能动性边界；§14.11 仍是行动路由唯一规范。

~~~yaml
t0_incident:
  incident_id: "<stable-id>"
  status: OPEN | CONTAINED | RESOLVED | TERMINATED
  affected_claim_ids: []
  affected_field_paths: []
  affected_threads: []
  dependency_edges: []
  allowed_threads: []
  blocked_threads: []
  last_valid_authorization_event_id: "<event-id-or-UNKNOWN>"
  authorization_scope: "<exact-scope-or-NONE>"
  player_choice: CONTINUE_SAFE_SCOPE | PAUSE_AUDIT | TERMINATE | UNKNOWN
  resolution_ref: null
~~~

Runtime State 是事故/授权范围的权威快照；Session Log 追加 T0_TRIGGER、AUTHORIZATION、ROUTE_DECISION、RESOLUTION 事件。两侧使用同一 incident_id 并独立读回。任一侧缺失时保持 INCOMPLETE，不声称授权或冻结已持久化。

行动语义必须区分：
- PLAYER_QUESTION_TO_GM：玩家向 GM 提出的规则、证据判断、假设或可能性问题；除非明确声明角色正在场内发问/行动，否则按桌外问题回答，不得自动变成角色台词或 NPC 已接收的信息。
- PLAYER_INTENT：玩家向 GM 提出的行动请求，不代表角色已执行。
- PC_DECLARED_SPEECH：玩家明确写出角色说了什么，才可记录为已发言。
- PC_ACTION_COMMITTED：玩家明确选择执行的角色行动；确认风险/成本/权限后进入执行。
- GM_PROPOSED_ACTION：GM 建议或选项，不是玩家选择。
- NPC_FUTURE_INTENT：NPC 表达将来打算，不代表已联系、移动、调查或取得结果。
- NPC_ACTION_EXECUTED：NPC 实际执行，必须有动机、机会、权限、时间依据，并检查冻结依赖。
GM 不得把 PLAYER_INTENT / GM_PROPOSED_ACTION 代述为 PC_DECLARED_SPEECH / PC_ACTION_COMMITTED。

混合行动拆成最小子动作，分别判断目的、依赖和权限；只暂停受影响子动作。初次 T0 后模糊授权不开争议线；已有安全授权仅延续原范围。目的含糊且可能依赖争议命题时，暂缓该子动作并澄清。冻结线程中的 NPC 主动行为同样过依赖检查。解除冻结须追加 RESOLUTION，引用证据和授权并核对 Runtime/Log 双侧状态。

## 14.16 接收者与片段级呈现、续接去重（C5 · P1）

- PARTIALLY_PRESENTED 事件必须记录 `presentation_segments[]`：segment_id、content_ref/hash、recipient_scope、delivery_channel、delivery_state、presented_at、evidence_ref。只对实际交付给该接收者的片段记 PRESENTED。
- 一条回复含多个信息片段/接收者时分别记录。无法确定送达的片段为 UNKNOWN；不得将整条回复统一标记 PRESENTED 或 NOT_PRESENTED。
- CONTINUE 去重以目标接收者已收到内容为准。Player Notes 是索引，实际回复/交付记录是证据；不一致时保留 UNKNOWN/DISPUTED，不自动重播。
- 允许例外：玩家明确请求回顾；或当前决策必须提醒已知条件、代价、期限。回顾须标记“回顾”，只向该接收者复述其已获知片段；必要提醒只简短引用既有条件，不包装成新发现/新事件。
- 仅对重要信息、多人接收、部分呈现或跨对话恢复中的关键回应启用片段级记录；普通互动不逐句建账。

## 14.17 发布前隔离与交付门禁（C4 · P0）

安全扫描必须发生在首次对玩家可见之前。写入成功不等于可发布；扫描后才发现泄漏无法撤销第一次披露。

1. 生成前确认工具支持私有暂存、目标接收者控制、独立读回和明确发布动作。生成即公开、自动附加到玩家可见消息、无法确认预览/临时路径访问边界或无法独立读回时，不得生成玩家可访问产物。
2. 仅在可核验私有暂存区 BUILD_PRIVATE，分别生成 Player Artifact 与 GM Audit；GM Audit 只能进入具备真实隔离的 GM-only 通道。
3. READ_BACK：从暂存区独立读取实际成品，核对身份、完整内容、大小/哈希（可用时）。
4. SCAN：扫描 Player Artifact 全部可读内容、元数据、附件和隐藏对象；不可读部分标 NOT_VERIFIABLE。若可能承载受限内容且无法排除，拒绝发布。
5. AUTHORIZE：核对 recipient_scope、字段白名单、呈现证据、目标交付通道和访问权限。
6. PUBLISH：仅当前五步均有可核验证据且不存在未排除风险时执行独立发布动作。任一步失败/不可观察即 INCOMPLETE / NOT_PUBLISHED。
7. 生成即公开或无私有暂存/独立发布控制：只能在 GM 私有对话中提供 NOT_PUBLISHED 拟稿，不得附带 GM Audit。无访问控制证据时不得称 GM-only。
8. 纯文本完整读回可证明文本内容完整性，仍须证明接收者和交付对象；复杂格式不可读元数据/嵌入对象未排除时拒绝发布。
9. 已泄漏时停止后续发布、保留原件、确认接收者和传播范围并按 T0 处置；修复版使用新身份，不删除原件。

## 14.18 P1-0C 盲测材料、版本和准入纪律（C6 · P1）

- 目标 Chat 只接收通用 Skill/运行规范入口、本轮最小合成附件和当轮玩家输入；不得接收夹具、OPERATOR、预期答案、硬断言、评分表或后续轮次输入。
- 执行提示词仅说明通用纪律，不列用例名称、触发方式、预期动作或通过标准；具体输入由操作者逐轮发送。
- 操作者独立维护 RUN_MANIFEST：run_id、case_id、空白 Chat 证据、产品/模型/Thinking 档、规范提交、每轮附件名与 SHA-256、上传时间、原始输入/输出、可见工具轨迹、产物哈希、读回证据和异常。不得上传目标 Chat。
- 附件哈希须对操作者持有的原始字节在上传前计算；目标端无法独立计算时注明证据边界。历史哈希不得冒充本次附件验证。
- 目标 Chat 提前读取后续附件或操作者材料，该试次标 CONTAMINATED，保留但不计有效盲测通过。
- 必测项若仅有自报、缺少有效输入时序，或缺少该用例要求的真实工具轨迹/产物/独立读回，阶段准入 NOT MET。其他用例 PASS 不可抵消。
- E13 行为评分与证据等级分开；历史 PARTIAL 永久保留。P1-0C 通过后仍须单独评估 P1-0R，不自动进入 P1-1。

## 14.19 现场回复与回顾共用玩家已知信息边界（P0）

本节把 §14.8 的字段级权限原则应用到每一次实际玩家交付，尤其防止 GM-only 战斗数据、隐藏事件或 NPC 私有知识通过普通叙述和结尾总结泄漏。它与 §14.16 的片段级呈现记录配合使用，不要求为普通句子逐条建账。

### 14.19.1 适用范围

以下内容都属于玩家可见投影，使用同一权限边界：
- 开场确认、恢复提示、正常场景叙述、环境观察与 NPC 对话；
- 检定/战斗结果、状态栏、战场摘要；
- 玩家要求的时间线、线索清单、阶段总结与 Session 回顾；
- 玩家可访问的便笺、导出文件及其他交付物。

不能因为某项内容出现在“总结”“状态栏”或“方便玩家理解”的格式里，就降低其披露门槛。

### 14.19.2 玩家可见断言的依据

**先确定当前桌的资料入口。** 新桌以本桌装配的资料为起点。历史聊天、个性化记忆和其它桌的发现没有本桌来源；跨会话续接只认当前桌的实际权威交接。若交接需要独立玩家聊天，必须能确认该聊天只装配已授权的玩家资料源，并且产品不会再注入旧聊天资料。无法确认这个条件时，仅交付从受控玩家资料实际生成并核对过的成品；私人准备和核验继续留在主持位置。

**公开选本与备团交付共用公开登记。** 比较时每个候选交付一行：标题、人数、时长、玩法标签和由玩法标签直接支持的体验取舍。已玩排除项只用于筛选。公开时长缺失时填“未知”。当公开登记足够时，此分支可直接用登记字段作答。可附参考图，图像不扩展可断言的事实。NPC、重要场景和线索的正式图像按模组目录标准 §4 使用已核定素材和接收者范围。转入准备时，玩家交付只写已选标题、已核实的公开简介、准备里程碑和当前需要决定的事项。对保留理由的追问继续使用相同字段，例如“还需确定规则系统和角色安排”；同一追问不扩大可读取资料源。

确立可引用的玩家资料：当前桌源片段、已呈现事件、经权威恢复准入的交接。任何此前聊天内容若无法定位到其中一类，不能用于回答现状、公开说明，或补建已发生事件。

没有分离入口时，混合聊天中的公开回答按最小玩家视图整理，其边界仍需用混合材料实测。涉及附件访问、写后读回或并发时，按 §14.17 取得宿主证据。

**先形成单一玩家回复载荷，再生成所有玩家可见内容（C1/C3）：** 每次回复先根据当前接收者、请求类型和通道，从获准来源中选出本轮真正可交付的材料，并形成一份最小的 player_reply_payload。载荷只包含：本轮实际发生且可向该接收者呈现的结果/观察；玩家已获知且本轮需要引用的信息；当前有独立依据、可继续采取的行动范围；确实需要玩家决定的事项；以及玩家有权获知的字段证据限制。GM-only 私稿、未呈现命题、NPC 私有知识、隐藏时间线、内部命题/事件/授权编号、审计标签和内部字段名不进入玩家载荷。若内部状态里有编号，只有它本身是世界内真实存在、已获准公开的编号时，才作为普通世界信息进入载荷。

正文、NPC 对话、状态栏、回顾、结尾提示和 Player Notes 均只能从同一份载荷生成；不得在撰写某个部分时重新读取 GM 全量状态补充内容，也不得让一个输出位置使用不同的事实/字段裁定。冻结理由只呈现玩家理解当前行动范围所必需的自然语言信息，例如「你可以继续向站务员询问公开信息」；不输出内部命题、决策编号或审计流程。载荷中不存在的命题，不得以否定句、UNKNOWN、无依据说明或其他暗示重新引入。

没有独立玩家入口、同一 Chat 同时接收私稿与玩家输入时，这一载荷是模型必须遵循的行为边界，不构成平台级访问隔离；效果仍须通过盲测验证。具备独立玩家入口时，只向该入口装配筛选后的载荷和材料。GM 核验材料留在主持侧。正式文件发布按 §14.12、§14.17；普通聊天的内容筛选不证明平台访问隔离。

| 请求 | 交付入口及输入 |
|---|---|
| 启动或加载，只确认收到并等待 | 直接发送「已收到，等待你的行动。」确认回执只读取接收与等待状态，到此交付结束。操作者明确要求的版本或恢复核对使用其单独授权的通道。 |
| 查询当前状态、已知档案或历史证言 | 先按权限在权威来源中确定要回答的内容，形成公开的答复片段。旧证词按下文的来源形式交付。 |
| 当前角色行动、对话或观察 | §14.20.6 决定并执行玩家已声明的范围，回复只取实际结果、合法感知和本轮获准的角色回应。复合请求中的资料回答先按上一入口完成片段，再与普通现场回应合并。 |
| 回顾、玩家笔记、结案或询问筛选理由 | 先完成当前接收者的玩家资料投影，再用这份投影撰写正文及说明。说明可交付已知证据的来源、精度和查证进度。范围说明可写作「这份记录涵盖你已看到、听到或实际查阅的内容」。主持审计沿 §14.12 的授权通道。 |

生成上述答复时，供正文、附注、表格和答复末尾使用的是同一份玩家资料。投影只携带获准条目和其证据限制。可浏览入口、查阅许可、实际观察分别投影。只获准访问时，当前可交付的内容是已经确认的入口或许可；读到的字段在实际观察后按本轮来源加入。

对会影响玩家判断、行动、线索、风险或状态的重要断言，至少满足以下一项：
1. **已向该接收者呈现**：存在实际送达给当前玩家/角色的呈现事件；引用时保留原接收者和内容范围。

   **呈现记录只证明接收者听到/看到过这项说法，不证明说法本身真实，也不补足其来源依据。** 若该说法后来需要作为调查事实、世界因果或裁定前提使用，仍须按 §12.5 回溯原始来源或实际事件；找不到依据时，只能记录为“此前曾向玩家如此陈述”，并按事故流程处理，不能因为玩家已经听过就升级为 TABLE CANON。
2. **本次角色直接感知**：由玩家刚刚声明且实际完成的行动产生，角色在当前条件下确实能够观察到。
3. **角色自身状态**：角色自己的 HP、资源、装备、已承受伤害和其他按当前系统/桌规公开的自身状态。
4. **公开规则或桌面约定**：当前系统规则或已确认桌规明确允许玩家知道。
5. **本次合法披露**：符合当前系统、模组或桌面约定的披露条件，且当前接收者与拟呈现范围均获准。首次披露可在本轮发生；先核验权限，实际交付后才按 §14.16 记录 PRESENTED。待发送草稿或内部记录不算已交付。

GM-only 资料、隐藏真相、未触发事件、NPC 私有知识、尚未询问的证词和未向玩家呈现的精确时间点，不因 GM 能够读取或在内部状态中存在而自动成为玩家已知信息。

**推断前提的权限过滤（P0）：** 任何准备向玩家呈现的关系判断、因果解释、时间顺序、摘要结论或其他推断，其每一项实质前提都必须分别通过当前接收者的权限筛选，并有足够依据支持该推断。只要某项前提被权限过滤排除，便不得通过推断、概括、措辞调整或组合其他线索恢复该前提的信息，也不得输出依赖该前提的结论。其他已获准前提仍可独立支持的内容，可以单独呈现。

**首次披露许可不由总结请求产生（P0）：** 玩家要求整理、回顾、总结或结案，本身不构成新的披露授权，也不降低任何字段的披露门槛。只有该信息本来就满足本节既有的公开规则、角色直接感知或本次合法披露条件时，才可在当前输出首次披露；此时必须明确作为当前新披露，并仅呈现实际获准的内容。总结格式、调查笔记需求或结案需要，均不能把 GM-only 资料转化为玩家可见信息。

**先形成证言答复，再呈现场景。** 需要回答既往事实时，先将这个问题的证言部分从普通 NPC 演绎中取出。核对 NPC 的获取依据、当前意愿和接收权限后，从合法片段中制作可直接交付的证言句。只有当前可访问、可定位且获准交付的逐字原文才可直接引用。可定位的旧回复可按其真实出处引用；若出处是主持曾交付的转述，仍保留转述归属。只有旧间接摘要时，使用第三人称转述，省略来源未记载的语气、距离、环境和感知原因。先写完整的间接引述句，例如「档案记载，保管员记得箱子大约是周初送来的。」句中保留归属、亲历或转述、已知属性、来源精度与不确定性。玩家追问旧原话时重用同一入口，只有摘要时说明这一点并忠实转述。此前的呈现只证明当时实际交付的文字，旧逐字原件仍回旧来源核验。

**先定稿，再合并。** 本轮只要需交付一项仅存摘要的旧证言，就为该次玩家回复选用「动作叙述＋转述」格式。先从获准来源逐项确定说话者、亲历或转述、被支持的内容及其精度，生成一条可直接交付的第三人称陈述，例如「保管员回忆，箱子大约在周初送达。」逐项保留原来源的不确定程度。并列资料用独立分句转述，来源确实建立关联时再使用因果或让步措辞。后续笔记、表格、时间线和结案以已定稿的获准分句为唯一文本来源，复用分句时保留原归属和「大概」「不确定」等限定词。新的获准证据作为新分句按其来源和时点记入。此轮的其他当下回答仍应完成，用简短间接句叙述；旧证言定稿和现场动作按顺序拼接，整轮无需角色台词格式。原文查询时，有可核验逐字稿的引用随来源单列，来源只支持摘要时仍重用转述。只有现场互动且不交付摘要证言的回合沿通常演绎。玩家笔记以实际已交付片段及其原来源为输入；申请、获准和实际查阅分别记录。

**当前新陈述与实际送达。** 角色的动作、停顿和态度可以体现现场反应。普通回应和本轮确有现场依据并准许披露的新陈述可按角色写成当下台词；NPC 仍可亲历、转述、误记或说谎，按实际陈述及其依据登记。对调查有意义的时间、地点、距离、感知原因、顺序和身份等只取目前有依据的字段。实际送达后，已交付的旧证言片段保留其原来源形式和来源根，新陈述登记本轮呈现的来源。只向接收者交接已实际收到的内容。现场、摘要、玩家笔记、结案和玩家可见文件措辞均使用各自的获准片段，发布按 §14.17 核对成品。

#### 玩家转述、NPC 证词与细节精度（P0）

在现场回复、调查记录、Player Notes 和终局总结中，若将一项说法写成已获知的 NPC 陈述、文件内容或直接观察，必须能定位到**实际向当前接收者呈现该说法的事件**，并且只保留该事件真正支持的内容。本轮首次披露按上文核验和交付，不预填呈现记录。

同一准入门槛也适用于玩家可见叙述中的物品操作：写出关键物品被角色持有、拿出、展示、交付或归还前，先按 §12.6 核对相应状态与实际转移依据。玩家的请求、意图或对既有状态的说法，不得替代取得/转移事件；GM 先前无依据的叙述也不能成为后续物理操作的依据。若此前已经错误呈现，保留玩家实际经历并按 §14.13 纠正，不得在后续 Player Notes、状态清单或结案中静默改写成另一段历史。

- **PLAYER CLAIM（玩家提出/转述的说法）**：玩家提到“某 NPC 说过 X”、要求记录 X，或将 X 作为行动前提，但当前对话中没有对应的 NPC 呈现事件时，先保留为 PLAYER CLAIM / 待核实线索。它可以成为追问、复核或行动的方向；不能改写成 NPC STATEMENT、已取得证词、直接观察或文件记录。
- **NPC STATEMENT（NPC 实际陈述）**：只有 NPC 在当前或此前某个可定位事件中确实说出该内容，且该 NPC 在当时有合理知识基础、满足披露条件，才可记录为该 NPC 的陈述。记录说话者、呈现事件、接收者及实际说出的内容范围。
- **玩家角色实际获知**：还须确认该陈述确实呈现给当前角色/接收者。GM-only 资料、其他 NPC 的私下陈述、玩家未听见的对话，不得进入角色知识或玩家笔记。
- **逐项细节与精度**：时间、地点、人物身份、动作、顺序、数量和否定观察均是独立细节。每一项都必须由同一呈现内容或另一条可定位来源支持。不得把“大约九点”精确化为“21:08”，不得从“20:50 前离开”补出“20:47”，不得把“没看清/没提到”扩成“确认没有”，也不得把 GM-only 时间线补进 NPC 的原话。
- **转述不改变来源根**：玩家转述另一人的话，仍是玩家当前提出的说法；除非能回溯到实际呈现事件，否则不能把玩家转述当作第二份独立来源，也不能替原说话者补充细节。
- **可能遗漏的旧呈现**：若玩家明确指出曾发生但当前记录缺失的对话/事件，先检查当前可用 transcript 或事件记录；仍无法定位时，保留为 DISPUTED / PLAYER CLAIM，必要时只问一个澄清问题。不得用 GM 后台知识“补齐”缺失的呈现。
- **合法披露照常放行**：NPC 在本轮确实知道且愿意说出的新信息，可以在本轮自然披露并记录；只放行实际说出的细节与精度。NPC 可以撒谎、误解或记错，但须保留为 NPC STATEMENT，不升级成客观事实。

#### 当轮整理、Player Notes 与结案共用的细节级呈现检查（P0）

当 GM 将现场互动整理成调查记录、生成 Player Notes，或撰写阶段总结/结案时，三个输出入口必须调用**同一条 §14.19 玩家已知信息准入门槛**；不得各自从 GM 内部状态、模组资料、主持笔记或推断时间线重新拼装玩家事实。

执行时先从当前接收者实际收到的呈现事件、角色实际感知事件及本次合法披露中提取候选内容，再按细节字段逐项核对。每条 NPC 证词、文件内容或直接观察中的时间、地点、人物身份、动作、顺序、数量和否定观察，都必须能回指支持该字段的实际呈现片段/事件及其接收者；同一条目中的其他字段不能因其中一项有依据而连带放行。GM 内部知道、模组写明、设备日志可推算或叙事上看似合理，均不能替代玩家实际收到的依据。

找不到某个细节的呈现依据时，只限制该细节：保留玩家原始转述并标为 PLAYER CLAIM / 待核实，或将未披露字段留为 UNKNOWN；不得补写成 NPC 原话、亲历证词、文件记录或已确认观察。原始呈现只支持较粗精度时，整理内容必须保持该精度。后续真实访谈或其他合法披露可以新增其实际说出的字段，按本次呈现追加，不回填为早先已经获知。

三个输出入口可以采用不同篇幅和组织方式，但不得采用不同的事实准入标准。模板、摘要和结案格式只负责组织与引用已通过本门槛的内容，不另建一套来源规则。此检查只在整理、跨轮回顾、Player Notes 和结案时触发，不要求普通互动逐句审计。

若玩家要求把多条信息写入笔记，可按其实际来源分别记录；来源未确认的条目可以保留为待核实说法，不必阻断无关互动。

### 14.19.3 战斗与状态栏

GM 可以并且应当使用完整的内部数据正确裁定战斗，但玩家输出默认只呈现角色可知且有行动价值的信息：
- 玩家角色自身的 HP、资源、装备状态和已发生的消耗；
- 玩家实际掷骰及按当前系统规则应公开的计算；
- 命中、未命中、可感知伤势、敌方动作、位置变化和可观察的战场后果；
- 玩家能够合理察觉、且对当前选择有意义的危险变化。

敌方精确 HP、AC、攻击/豁免加值、隐藏状态和未公开身份默认属于 GM 内部数据。只有当前规则、明确桌规、角色能力或玩家事先同意的公开方式允许时，才向玩家显示精确数值。不要用精确 HP 替代可感知的伤势描写；也不要为了保密而隐去玩家采取行动所必需的可观察结果。

### 14.19.4 时间线、回顾与摘要

玩家请求总结时，只能从该玩家/角色实际获知的事件集合中组织内容：
- 已发生但未向该角色呈现的 GM-only 事件，不得列入“你已确认”“你知道”或玩家时间线。
- NPC 的隐藏证词、私下观察、真实动机和未披露行动，必须等到有实际披露事件后才能进入玩家已知集合。
- 对玩家已知信息，保留其来源和认知强度：亲见、NPC 陈述、文件记录、转述、推断与争议不得混写。
- 若 GM 选择在当前回顾中首次披露此前隐藏但现在有依据可公开的信息，应明确将其作为**当前新披露**，写明实际来源；不得伪装成玩家此前已经获知或确认。
- “GM 时间线完整”不等于“玩家时间线完整”。两者需要分离，不能用 GM-only 时间线填充玩家摘要。

#### 分段披露与长对话回顾（P1）

同一证词或命题可能在不同轮次逐步披露。回顾时可以合并该接收者此前实际收到的多个内容片段，但必须按细节字段核对每个片段的呈现事件、接收者和支持范围：
- 每个时间、人物、地点、动作、路线、数量及否定观察，分别保留其实际披露依据与精度；一次披露只更新它真正支持的字段，不连带补全其他字段。
- 后续披露可以增加或修正对应字段；不得把后续新增细节倒写成玩家在更早轮次已经知道，也不得因某字段变得精确而提高同一证词其他字段的精度。
- 长对话摘要可以整合多个已呈现事件，但每个重要字段都必须能回溯到至少一个实际呈现事件。从已允许讨论的字段中选取确有必要标记的未知项；未获披露许可的字段不进入摘要。
- 旧 Player Notes 是玩家知识的派生投影，不是新的证据来源。重新提供或引用旧笔记，不会产生新的独立证据，也不会授权补齐其中的未知字段；若原始呈现锚点可用，回指原事件，若不可用则保留既有记录状态并标记来源锚点未知，不从后台补写。

本规则只在分次披露、跨轮回顾、更新 Player Notes 或终局总结时触发；普通互动不增加逐轮审计。

### 14.19.5 低成本执行

- 绿色普通互动和无信息权限影响的感官描写，沿用现有叙事方式，不增加逐句审计。
- 只在涉及隐藏事实、关键证据、NPC 知识、敌方精确数据、资源/伤害、时间线、总结或玩家可访问产物时，核对对应字段的接收者与呈现依据。
- 回顾时一次性筛选玩家已知事件集合；不要求把整场游戏每轮重复检查一遍。
- 发现未呈现信息已泄漏时，按 §14.1 与 §14.13 处理；不得只在下一轮停止提及而保留其对玩家选择或后续状态的影响。

## 14.20 Context Assembly and Trace

本节在现有 Preflight、Runtime 风险路由、权威资料分层和玩家信息权限规则之上，定义一次行动的上下文装配与可观测性。它不创建第二套 Runtime、事件历史、Claim Ledger 或玩家知识库，也不替代 §13、§14.3、§14.9–16、§14.19。

### 14.20.1 目标与低成本边界

Context Assembly 回答：当前行动依赖什么、哪些资料被定位/读取/核验、哪些范围可以继续。

Context Trace 回答：上述过程有哪些可观察证据、最终允许/阻断什么、发生了哪些重要输出和状态变化。

Context Diff 回答：与上一次有效装配相比，当前行动相关的依据是否发生了实质变化。

执行边界：

- 新对话/新 Session：在同一次 Preflight 中建立启动 Context，按 §A 的完整路径或健康续接快路径装配，不增加第二次 Preflight。
- 同一活动对话：复用仍有效的绑定、静态来源和 Runtime 快照；不得按消息数或每轮强制全量装配。
- 绿色普通互动：当前快照足以回答、没有相关依赖失效、无持久状态变化和方向性新信息时，直接回应；目标仍为零新增文件读取、零强制持久化 Trace。
- 黄色/红色：按现有风险路由识别本次行动的实际依赖，必要时生成/更新 Manifest 与 Trace。
- T0：遵循当前有效的 §14.1 配置。Context Assembly 不能绕过 T0 熔断、授权或冻结规则，也不自动改变性能阶段遗留的临时配置。
- 不得为减少 Token、读取次数或文档长度删除必要事实、否定信息、例外、精度限制、来源关系或接收者权限。

### 14.20.2 Context ID 与行动生命周期

一个 Context ID 标识一个可识别的执行单元：一次 Preflight，或一次玩家行动的 GM 处理过程。

- 一次复合/混合行动使用一个父 Context ID；需要独立裁定的子行动使用 child_action_id，并分别维护依赖与允许范围。不得将同一玩家意图拆成互不关联的 Context。
- 同一行动的补充读取、澄清后仍属同一意图的重试、失败后恢复，沿用 Context ID；通过 attempt 和 manifest_revision 追加新尝试/修订。
- 玩家明确改变目标、撤回原行动并提出新行动，或原行动结束后提出新的独立行动，才创建新 Context ID。
- Context ID 不替代 event_id、action_id、batch_id、checkpoint revision 或 incident_id。它是追踪关联键，不是领域事实或事件身份。
- ID 必须在当前 Session/运行范围稳定唯一；不得仅依赖时间戳，不得因 ID 不同就推断行动实质不同。
- Preflight Context 与后续玩家行动 Context 分开；Preflight 作为一次启动执行单元，不把整场 Session 的每轮行动都挂在同一个 Context ID 下。

### 14.20.3 行动依赖与必要性

先识别玩家输入语义，继续遵循 §14.11.1 和 §14.15 对 PLAYER_QUESTION_TO_GM、PLAYER_INTENT、PC_DECLARED_SPEECH、PC_ACTION_COMMITTED、GM_PROPOSED_ACTION、NPC_FUTURE_INTENT、NPC_ACTION_EXECUTED 的区分。

从当前行动目标识别必要依赖，按需覆盖：
- RULE：适用规则、桌规/批准适配、触发条件、例外和结算顺序；
- FACT：模组原文、Campaign CANON、已确认桌面事实；
- STATE：Runtime 当前值、时间/位置/资源/物品；当 §14.10、§14.14 的证明检查触发时，将相关字段在当前检查点的应用证据列为依赖。旧事件证明、旧快照或旧 Player Notes 不证明当前值。
- NPC_KNOWLEDGE：按《08_CLUE_AND_SOURCE_LEDGER.md》§9.5–9.9，从实际获取、认知变化、人物档案和当前处境派生相关视角。用现有 target_ref 定位相关人物及影响其本次行为的命题或细节；只核对会影响行动、回答或披露的知识范围与精度。客观事实、NPC 判断及玩家披露权限分开核验。
- PLAYER_KNOWLEDGE / PRESENTATION：玩家角色实际获知的内容、呈现事件、片段和接收者；
- LOCATION / ITEM / RESOURCE：行动所需的空间、持有人、数量、资格和资源前提；
- PERMISSION：GM-only、recipient_scope、披露条件和输出限制。

每项依赖标记：
- REQUIRED：当前行动必要前提。未解决时阻断依赖该项的子行动。
- CONDITIONAL：仅当明确条件成立时才成为必要依赖；条件未触发时不强制读取。
- SUPPORTING：辅助背景或解释材料，不能替代 REQUIRED，也不能解决权威冲突。

依赖识别从行动目标与因果前提出发，不只依赖关键词。关键词、语义检索和向量相似度只能定位候选资料，不能证明事实或权威。

**常驻约束与行动依赖必须分开处理：**

- `GM Core Constraints` 是活动 Session 的常驻约束契约。它在 Preflight/恢复时建立，并在同一活动运行上下文中持续有效；它不是本次行动的 REQUIRED/CONDITIONAL 依赖，不要求每轮重读、生成 Manifest 条目或执行完整检查表。
- `NARRATIVE_PRESENTATION` 与 `CHARACTER_SIMULATION` 是专业方法来源，不是每个玩家行动都必须重新加载的全量文件。主 GM Skill 已建立其持续适用的核心约束；具体方法按场景需要调用。
- 当前场景的人物、关系、事务、空间、环境、体验重心和玩家可知信息，作为 Active Scene Context 从现有权威状态与资料中组合。进入新场景、关键人物/事件加入、重要状态改变或当前上下文失效时更新；同一场景的绿色互动直接复用，不因消息数量刷新。
- 风险路由只增加本次行动真正需要的规则、事实、状态、知识和权限核验，不得把叙事质量降为可选依赖；也不得为了“保证质量”把每轮普通互动升级为黄色审计。

叙事质量调节以综合生成时的常驻约束为主。仅在场景切换、重要人物首次出场、关键揭示、关系/策略显著变化、复杂后果或可观察的表达退化信号出现时，做有针对性的复核。复核只处理当前问题，不把 Narrative Skill 的所有方法改造成逐轮清单。此类复核不自动要求持久化 Context Manifest/Trace；只有符合现有风险与记录条件时才记录。

重要互动按 §14.11.1、§14.15 先区分桌外提问、玩家意图、实际发言、已提交行动和 NPC 未来意向。安全明确的行动可以在裁定后自然推进；不得用叙述代替玩家未说出的台词或未作的选择。请求、接受、执行、结果分别以实际发生及依据为准；后一步依赖前一步结果时等待结果再裁定。只有会影响后续的阶段变化才记增量或关联事件。

### 14.20.4 Context Manifest

Manifest 是一次上下文装配的可追溯清单，不是新的权威数据库，也不是 Runtime Reconciliation Manifest。不得混用两种 Manifest。对需要跨对话追溯的黄色/红色行动，Manifest 作为不可变 GM-only 记录块嵌入对应 Session Log 事件或 Operational Diagnostics 记录；Preflight 阶段则嵌入本次 Preflight/Handoff 记录。引用定位到记录块，不另建平行 Manifest 文件库。绿色普通互动可只在当前上下文中临时维护，不持久化。

需要结构化追溯时，使用以下最小契约；按行动适用性填写，不适用字段标 NOT_APPLICABLE：

### 14.20.5 检索、读取与核验必须分开

三个维度不得压缩为一个 found/verified 布尔值：

**检索状态**
- FOUND：找到候选资料；
- NOT_FOUND：按已声明的检索范围未找到；
- NOT_ACCESSIBLE：资料不可读取或无权限访问；
- VERSION_MISMATCH：找到资料但版本不匹配；
- UNKNOWN：检索范围/结果不足以判断。

**读取状态**
- FULL_REQUIRED_SCOPE：已读取当前依赖所需的完整范围；
- PARTIAL：只读取部分必要范围；
- LOCATOR_ONLY：只取得目录、标题、摘要或定位；
- NOT_READ：尚未读取正文。

**核验状态**
- VERIFIED：指定依赖的适用检查通过；
- FAILED：检查失败；
- UNKNOWN：证据不足；
- DISPUTED：发现未解决冲突；
- NOT_APPLICABLE：该项检查不适用。

NOT_FOUND 不证明事实不存在；NOT_ACCESSIBLE 不等于空内容；LOCATOR_ONLY 不等于已读取；PARTIAL 不得冒充完整核验。NOT_APPLICABLE 不得被默认转换为 VERIFIED。

Source Locator 应尽可能精确到仓库相对路径、章节/记录 ID、版本/commit/blob、Runtime revision 或可验证内容指纹。无法计算指纹时标 NOT_AVAILABLE，不得伪称校验。同一来源对不同依赖的读取范围或核验结果不同时，按实际片段或依赖组分别登记 read_scope、validation 与 dependency_refs；已核验的同次读取可复用，不用整文件已读替代逐依赖核验。

### 14.20.6 装配顺序与 READY 判定

沿以下顺序装配；已有流程已经完成的步骤可复用其本次结果，不重复执行：

1. Resolve Binding：按 SYSTEM_CONTEXT_PROTOCOL 核验唯一 system_id、精确规则版本、Campaign Binding 和 Module。
2. Resolve Runtime：按 Preflight/Runtime 读取有效检查点、活动分支、当前场景、最近事件、未合并事件和开放争议。
3. Classify Action：确认行动语义、目标、对象、风险和可能改变的状态。 复合说法拆出明确声明的移动、接触、提问、查资料或其他操作，记下声明顺序与实际依赖。玩家已说明对象和问什么时，该提问已是声明的子行动。
4. Resolve Dependencies：建立当前行动 REQUIRED、CONDITIONAL、SUPPORTING 依赖。
5. Retrieve Authority：通过索引定位后，读取必要权威原文/记录范围；摘要只定位，不能替代。
6. Validate：核验身份、版本、权威、读取范围、状态一致性、来源根、NPC 知识、玩家呈现和接收者权限。状态冲突须比较同一语义字段；事件发生时间与当前时钟不同，本身不是冲突。
7. Assemble：明确区分权威事实、当前状态、历史事件、NPC 知识、玩家已知、UNKNOWN/DISPUTED 和输出权限。重要节点的玩家呈现素材只携带 §14.19 核验后获准的片段、归属和可用精度。
8. Decide：按子 action_id 裁定，按玩家声明的顺序逐项处理。前项实际完成后，用其结果核对依赖它的后项。后项已明确、前提成立且当前无须玩家再选择时，在同一回复继续处理到该项实际结果。只在相关依赖无法满足、真正需要新选择或声明仍有实质歧义时停在该项；仍可推进的独立子行动继续。父 Context 的就绪状态不覆盖各子行动。
9. Respond & Trace：只呈现已裁定范围内实际发生或当前允许披露的内容；按 §14.19.2 为每项实际交付选择入口和素材，按子行动合并答复。完成了接触前置的提问应处理实际回答或具体限制。交付后按实际事件、状态差异和送达证据记录呈现与必要 Trace。允许不等于已执行、已取得结果或已交付。

状态判定：必要依赖包括 REQUIRED 和已触发的 CONDITIONAL，均适用同一核验门槛，保留原有分类。若触发条件不明且影响风险、适用规则、资格或结算，不得当作未触发；暂缓依赖该判断的子行动。

- READY：当前声明范围内的必要依赖均已解决，适用核验通过。
- READY_WITH_LIMITS：缺口已隔离；只允许已独立通过裁定、有独立依据且不会为争议命题生成佐证的范围。
- BLOCKED：相应必要依赖缺失、不可访问、版本不符、无法核验或存在相关争议；阻断所有依赖该项的行动及相关状态变化或断言。

BLOCKED 不自动冻结无关互动。健康绿色互动仍可使用已核验且有效的 checkpoint；按 §14.10、§14.14 触发时才定向查应用链。READY 只表示当前声明范围的必要依赖已通过，不表示所有子行动已执行。

### 14.20.7 上下文语义分区

装配后的资料应保留语义边界，至少区分：
1. GM Core Constraints；
2. System Binding；
3. Rules / Module Authority；
4. Campaign Canon；
5. Runtime Snapshot；
6. Session / Event History；
7. Current Action and Dependencies；
8. Claim / Source / Evidence；
9. NPC Profile and NPC Knowledge；
10. Player-Known Information；
11. UNKNOWN / DISPUTED / UNVERIFIED；
12. Recipient Scope / Disclosure / Output Restrictions；
13. Response Task。

以上是语义分区，不强制固定 Prompt 排序。资料出现在同一上下文中，不会改变其权威等级或权限范围。

其中 `GM Core Constraints` 表示本 Session 持续有效的约束，不是每个行动都要重新读取的依赖项；`Current Action and Dependencies` 则随行动变化。场景相关资料按 Active Scene Context 复用并在实质变化时更新。分区用于保持语义和权威边界，不意味着每轮必须重新装配全部分区。

### 14.20.8 Context Trace 与持久化

Trace 记录可观察工程事实，不记录思维链，不推断模型未公开的内部处理过程。

最小 Trace Envelope：

~~~yaml
context_trace:
  trace_schema_version: 1
  context_kind: PREFLIGHT | PLAYER_ACTION
  trace_id: "<stable-trace-id>"
  context_id: "<context-id>"
  action_id: "<action-id-or-NOT_APPLICABLE>"
  attempt: 1
  manifest_ref: "<manifest-ref-or-NOT_PERSISTED>"
  manifest_revision: 1
  binding_ref: "<binding-source-ref>"
  checkpoint_revision: "<revision-or-UNKNOWN>"
  retrieval_refs: []
  validation_refs: []
  assembly_status: READY | READY_WITH_LIMITS | BLOCKED
  allowed_scope: []
  blocked_scope: []
  diff_ref: "<diff-ref-or-NOT_RUN>"
  related_event_ids: []
  changed_field_paths: []
  presentation_refs: []
  recipient_scope: "<exact-scope-or-NOT_APPLICABLE>"
  persistence_status: NOT_REQUIRED | NOT_ATTEMPTED |
                     PREPARED | VERIFIED | INCOMPLETE
  limitations: []
~~~

持久化位置：

- 对应真实游戏事件：将最小 Trace Envelope 作为该 Session Log 事件的 GM-only 元数据；引用 Manifest、来源和核验记录，不复制资料正文。
- 重要行动被阻断、恢复或出现装配争议且需要跨对话追溯，但没有领域事件：在现有 Session Log 的独立 GM-only Operational Diagnostics 附录追加运行诊断记录。该记录不是 Session/Event Log 的领域事件，不分配领域 event_id，不推进游戏时间或 CANON，也不改变领域状态。
- Preflight 尚无可用 Session Log 时：Trace 随本次 Preflight/Handoff 记录；普通 Preflight 不强制新增独立审计文件。
- 绿色普通互动不强制持久化 Trace。
- Runtime State 不保存完整 Manifest/Trace；只有当装配问题已构成开放争议或影响当前推进的持久状态时，按现有 dispute/state 机制保存状态及相关引用。
- Player Notes 和玩家导出不得包含 GM Trace、隐藏来源、GM-only 依赖或内部路由。

Trace 只证明明确记录的事项：READ 不等于 VERIFIED；PRESENTED 必须有实际交付证据；PERSISTENCE VERIFIED 必须有独立读回证据。没有记录的检查不得事后声称已完成。

Trace 与其引用的 Manifest 对应同一 context_id、attempt 和 manifest_revision。允许/阻断范围以对应决定为准；范围变化按 §14.20.9 关联新决定和修订。执行、状态变化和交付以实际事件、字段和呈现证据为准，不得从许可范围推定已经发生。

**平台可观测性边界：** 当前 ChatGPT 环境无法读取平台最终完整隐藏 Prompt。Trace 只能描述工作台可观察的显式资料定位、读取返回、核验、决定和输出；不得宣称完整模型输入审计或模型内部思维链审计。

### 14.20.9 Manifest 版本与修订

- 每个 Manifest 必须包含 schema_version 和 manifest_revision。
- 已生成 Manifest 不可原地修改。修订产生新 revision，并通过 supersedes_ref 指向被替代版本。
- 同一 Context ID 的补充读取、澄清和恢复可产生新 Manifest revision；旧版保留，不覆盖。
- schema_version 变化表示字段/语义契约变化；manifest_revision 变化表示同一 schema 下该 Context 的装配记录更新。
- 旧 Manifest 缺字段时保留 UNKNOWN / NOT_RECORDED；不得从新 Runtime、摘要或模型印象回填历史。
- Manifest 与 Runtime Reconciliation Manifest 必须使用不同明确名称、引用空间和职责，禁止互相代替。

### 14.20.10 Context Diff 与触发条件

Context Diff 比较重要依赖的语义状态，不是普通文本 Diff。至少检查：
- system/ruleset/campaign/module binding；
- Runtime checkpoint、活动分支、相关事件和未合并状态；
- 依赖来源版本、内容指纹与实际读取范围；
- Claim 状态、证据根和来源谱系；
- NPC 知识、披露片段、玩家呈现和 recipient_scope；
- 开放争议、T0 冻结和授权范围；
- 当前行动依赖集合；
- 上次存在而本次无解释消失的事实、否定信息、精度限制、例外和权限条件。

结果分类：ADDED / REMOVED / REPLACED / CHANGED / NARROWED / EXPANDED / DISPUTED / UNKNOWN / UNCHANGED。REMOVED 必须记录原因；未被本次装载不等于事实已失效。没有可靠旧基线时标 NO_BASELINE，不推断 UNCHANGED。

触发规则：

1. 新对话/新 Session Preflight：对可用的上次有效装配基线执行相关依赖 Diff；旧基线不可用时标 NO_BASELINE，并按当前 Preflight 读取权威状态。
2. 同一活动对话：只在可能使当前依赖失效的变化发生时，比较受影响依赖。包括系统/版本/绑定变化、相关 Runtime checkpoint 或事件变化、依赖来源版本/内容变化、Claim/证据根变化、NPC 知识或披露变化、玩家呈现/接收者权限变化、争议/T0 范围变化。
3. 新行动不自动触发全量 Diff；只比较与该行动实际依赖相交的已有上下文。
4. 不按消息数或每轮固定触发；不扫描整个仓库或无关历史。
5. 依赖变化无法解释、重要限制无故消失或冲突出现时，按 READY_WITH_LIMITS / BLOCKED 及现有争议规则处理。

### 14.20.11 记录粒度与性能保护

- GREEN：可在当前上下文中轻量维护依赖；不要求 Manifest 文件、持久 Trace 或全量 Diff。
- YELLOW：对发生变化的对象和实际依赖建立标准 Manifest/Trace；只记录重要来源与状态变化。
- RED：在宣布结果前核验所有必要规则、事实、状态、例外和权限；保留可追溯 Manifest/Trace。
- T0：遵循当前有效 T0 配置；不得用本节替代事故处置。
- 一轮中互不依赖的读取可批量执行；有依赖的定位、版本确认和原文核验按顺序执行。
- 资料复用沿用 §A 同次读取规则：静态资料按精确版本/Blob 与读取范围复用；可变 Runtime 状态不得凭旧装配证明当前仍有效。
- 不以 Manifest 字段填满率、Trace 数量或 Diff 次数作为质量指标。关键门槛是依赖是否完整、来源是否可追溯、权限是否正确、冲突是否被识别。

### 14.20.12 验收门槛

以下为硬门槛，不得被性能、文笔或其他得分抵消：

- system_id / ruleset_version 错误不得 READY；
- 任何必要依赖遗漏不得 READY，包括已触发的 CONDITIONAL；影响裁定的未知触发条件不得视为未触发；
- LOCATOR_ONLY / PARTIAL 不得冒充完整核验；
- UNKNOWN / DISPUTED 不得升级为事实；
- NPC 知识、玩家知识和 recipient_scope 不得越界；
- Runtime / Log 应用链冲突不得静默裁定；缺少当前字段证明时，不得用旧值推进依赖该字段的行动或投影；
- 争议只阻断依赖行动，无关安全互动保持可用；
- Trace 不得声称审计不可观察的平台完整 Prompt；
- Diff 不得把未加载误判为事实删除；
- 绿色普通互动不新增强制文件读取或持久化；
- 任何效率收益不得以删除必要事实、否定信息、例外、精度或权限限制换取。

本节定义的是运行协议；文档静态检查或合成夹具通过不代表目标 Chat 行为通过。真实模型行为须按独立目标环境测试记录。

### 14.20.13 场景连续性与认知依赖分离（P0/P1）

本节补足“资料缺失导致过度阻断”的执行边界。它复用现有 Scene State、Runtime、NPC Knowledge Projection、Claim / Source Ledger 与 Context Manifest，不创建新的场景数据库或 NPC 知识库。

#### 场景状态与 NPC 认知是两项独立依赖

- **场景连续性**回答：当前场景是否已经建立、是否仍在进行、玩家与 NPC 是否在场、最近行动是否已回应。其依据来自 Runtime checkpoint、实际对话/呈现事件和场景进入标记。
- **NPC 认知**回答：该 NPC 实际接触、记得、相信、怀疑或愿意披露什么。其依据来自人物档案及实际获取、认知变化和陈述事件，按《08_CLUE_AND_SOURCE_LEDGER.md》§9.5–9.10 派生。
- 场景已核验为 ACTIVE，且 NPC 在场/互动状态已建立时，NPC Knowledge 某项资料缺失，不会使场景自动失效，也不等于该 NPC 不知道任何事。
- 不得把“本次上下文未加载/未找到 NPC 证言”改写为“NPC 从未知道/从未经历”，也不得据此重置已建立的场景或重演首次接触。

#### 资料缺失只限制依赖该资料的断言或子行动

当玩家在已建立场景中向 NPC 提问，而该 NPC 的相关经历/知识资料未能核实：

1. 仍可继续正常倾听、回应、澄清问题、询问范围、表达当下犹豫，及进行不依赖该缺失事实的普通互动。
2. NPC 可以在符合人物状态的情况下表示不确定、暂时想不起来、询问玩家具体指什么，或明确自己无法确认；这些是当下的回应，不得顺势补造其过去经历。
3. 不得为填补资料缺口而新增关键个人经历、目击、时间、楼层、地点、投诉内容、报修状态、文件持有、查证结果或其他会改变调查方向的事实。
4. 不得将“资料中没有写”推断为“事情没有发生”，也不得将“NPC 现在想不起来”推断为“NPC 从未接触过该信息”。
5. 若 NPC 已有可核验的相关知识资料，按其原有内容和精度回答；缺失的是某个细节时，只限制该细节，不抹去其他已确认的认知。

READY_WITH_LIMITS 应优先用于“场景可以继续，但某项事实性回答/断言暂受限制”的情况。BLOCKED 只作用于确实依赖缺失 REQUIRED 前提的具体子行动、裁定或事实断言；不得把单项 NPC 知识缺口扩大为整场对话、整个场景或所有安全互动的阻断。只有场景本身的必要锚点、物理条件、权限或规则前提缺失时，才阻断依赖该前提的场景行动。

#### 玩家可见呈现与内部资料缺口分离

- 不把“NPC 档案没有加载”“GM 资料不完整”之类内部装配问题当成虚构世界中的阻碍告知玩家。
- 在角色视角内自然处理：NPC 可以思考、反问、表示记不清或说明无法确认；GM 不得用幕后资料状态代替 NPC 的现场反应。
- 不得为了避免过度阻断而反向编造证言。继续演绎与限制事实生成必须同时成立。
- 普通动作、表情、语气和不改变调查方向的日常细节可按人物与场景合理呈现；会形成新证据、改变人物经历或影响后续因果的内容仍受 §12.2、§12.5 与本节约束。

#### 验收判据

- 已建立且仍 ACTIVE 的场景，不因单项 NPC 知识缺失而被整体暂停。
- 缺失资料限制的是依赖该资料的事实断言，不是普通对话和场景连续性。
- NPC 不会因为 GM 缺少资料而获得未经支持的目击、经历或记忆细节。
- 玩家提供的前提不会自动成为 NPC 的既有知识或独立证言；具体记录按《08_CLUE_AND_SOURCE_LEDGER.md》§9.10。
- 不把 UNKNOWN / NOT_LOADED 改写为否定事实，也不把不记得改写为没有发生。
- 上述处理不增加绿色互动的强制读取、逐轮账本或持久 Trace。
