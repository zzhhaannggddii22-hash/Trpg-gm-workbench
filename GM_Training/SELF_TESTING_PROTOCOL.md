# GM 自测与验收执行协议

> Version: 1.3  
> Status: DEFAULT WORKFLOW  
> Scope: GM Skill、NPC 模拟、叙事质量、Runtime、Context Assembly、规则裁定可靠性及训练成果迁移的受控自测。

## 1. 默认方法

GM 自测默认采用：

**GitHub 版本化测试夹具 + 单会话自动执行 + 执行后结构化自审 + 完整证据报告。**

默认由同一个助手会话承担资料读取、Preflight、测试行动模拟、状态维护和执行后审查。用户是观察者，不需要扮演玩家、不需要逐轮粘贴行动，也不需要手动切换多个 ChatGPT 会话。

单会话执行可以在一条助手回复内，按顺序读取 ACTION 文件、模拟多轮玩家行动与 GM 响应，并在每步后更新隔离的测试状态。它验证的是指定版本在当前单会话环境和固定输入下的可观察表现；**不等于多个真实 ChatGPT 用户回合，也不等于独立模型或盲测复核。**

同一助手既执行又审查时，报告必须标记 `SINGLE_SESSION_SELF_TEST`。可以给出有证据支持的缺陷定位、硬门槛结果和局部结论，但不得把自审包装成独立验证、盲测或 T4 真实跑团证据。只有测试目标本身要求真实多轮平台行为、跨会话恢复、工具/运行时自动化，或用户明确要求独立盲审时，才升级为外部编排或独立会话测试。

执行者负责：
1. 固定 GitHub 仓库、夹具 ref、被测 commit 和基线 commit；
2. 读取测试输入所需的权威资料，完成适用的 Preflight；
3. 按顺序自动执行全部测试行动，不要求用户逐轮参与；
4. 维护 TEST_ONLY_NON_CANON 状态账本，完成后再依据验收标准审查；
5. 输出完整 Markdown 报告，区分实际观察、状态推导、自我评价、未知和未执行项目。

测试夹具不得为了“跑起来”而补造正式 Campaign 事实、NPC 档案、规则或权限。依赖缺失时按 BLOCKED / NOT TESTABLE 处理；能独立执行的部分可继续，但必须标记部分完成。

## 2. 先定义测试；夹具创建必须满足本会话可执行条件

先判断测试是否能在当前会话内完成资料读取、自动执行、状态核对和结果报告。**不得把“设计一套夹具，留给用户或另一个 Chat 执行”作为默认交付。**

只有同时满足以下条件，才创建新的测试夹具：
- 本会话能够读取并锁定全部必需资料与被测版本；
- 可以在本会话内自动完成全部行动模拟/测试步骤，不依赖用户逐轮输入、手动切换 Chat 或不可用的外部运行环境；
- 可以在本会话内完成执行后审查，并明确报告实际执行范围、证据与限制。

若任一条件不满足：
- 不创建新的夹具、启动包或待执行提示词；
- 不把测试设计工作转嫁给用户；
- 如问题值得保留，只在现有 Training Log / Backlog 中记录观察、风险和待验证原因，不伪装成测试；
- 若现有夹具能够在当前会话完整自动执行，可以复用现有夹具，不为同一问题另造一套。

满足可执行条件后，仍须先明确以下测试要素：

每项测试开始前明确：
- **测试目标**：要验证的具体能力或缺陷，不使用“整体变好”作为唯一目标。
- **测试类型**：专项练习、综合模拟、回归、盲测、真实跑团或工具/平台测试。
- **被测版本**：固定到不可变 Git commit SHA，不只写分支名或“最新版”。
- **测试输入**：场景、角色、玩家行动、骰面/随机输入、初始资源和时间线。
- **观察范围**：需要记录的行为、状态字段、可见输出和来源。
- **隔离边界**：TEST_ONLY_NON_CANON、GM-only、玩家可知信息、评分 Oracle 的位置。
- **判定规则**：硬门槛、体验维度、样本覆盖和未解决项的处理方式。

基线与候选必须使用同一份测试夹具、同一行动顺序、同一骰面和同一初始状态。只改变本轮要比较的被测版本；其他变量尽量固定。

## 3. 版本与分支管理

将**测试夹具版本**与**被测 Workbench 版本**分开管理：

- 测试夹具分支保存启动文件、测试协议、场景包和分阶段行动文件。
- 被测 Workbench 使用明确的 commit SHA；基线与候选各自锁定一个 SHA。
- 启动文件必须同时写明夹具分支和本次被测 commit SHA。
- 当前执行会话开始时必须明确锁定夹具分支和被测 commit；不得依赖未声明的默认分支或先前会话中的 ref。
- **每一次 GitHub 文件读取都必须显式传入同一个夹具 `ref`**；不得只在自然语言中声明分支，也不得省略 `ref` 后依赖默认分支。
- 记录每个关键文件的完整路径、实际 ref、Blob SHA；被测 Workbench 另记录 commit SHA。
- 测试分支与基线/候选 commit 应保持可追溯。不要为了让测试“能跑”而移动、覆盖或临时改写已锁定的基线输入。

## 4. 测试会话启动协议

单会话是默认执行环境。每次测试在当前对话中建立新的、彼此隔离的内存状态快照；不得把上一轮测试的状态变化、纠错或结论带入新分支。若执行 A/B，基线与候选必须从同一不可变起点分别复制，不得共享已变更状态。由于它们仍由同一助手执行，A/B 结果属于受控自测比较，不属于独立盲测。

执行前至少固定：
- 仓库全名；
- 测试夹具分支；
- 启动文件完整路径；
- 本次 Workbench 精确 commit SHA；
- 显式要求所有后续读取都传入同一 `ref`；
- 依赖缺失时停止并报告 BLOCKED，不猜测、不跳过、不回退默认分支。

执行者先读取启动说明、测试夹具、Workbench 入口及必需依赖、指定规则原文。只有依赖完整且 Preflight 达到适用的 READY 状态后，才开始行动测试。所有 GitHub 读取都显式使用锁定 ref。

## 5. 分阶段输入与行动顺序

优先将玩家输入拆成独立、编号的行动文件（例如 ACTION_01 至 ACTION_08）：
1. 先读取并理解当前行动文件；
2. 完成该行动的规则/事实裁定和玩家可见回应；
3. 更新测试状态账本；
4. 之后才读取下一行动文件；
5. 不得一次性读取全部行动文件，不得提前使用未来行动改变当前决策，不得跳过、合并、重排或改写玩家行动。

测试会话应维护最小但足够的状态账本，包括时间、位置、玩家实际观察/知识、NPC 目标/任务/知识/位置、物品与权限、事件进度、规则资源和未解决字段。只记录有后续影响的变化，不把账本伪装成平台持久化机制。

### 单会话执行边界

普通 ChatGPT 对话不能在一条回复结束后自行发起下一条用户消息。因此，默认夹具可以在**一条助手回复内顺序读取分阶段行动文件并模拟多轮行动**。每一步仍按“读取当前行动 → 作出回应/裁定 → 更新状态 → 再读取下一行动”的顺序执行；不得提前读取或利用未来行动改变当前决策。

这能验证固定行动序列下的场景响应、规则/事实遵循、模拟状态连续性和叙事表现；不能证明多个真实用户回合之间的平台记忆、跨会话恢复、隐藏上下文持久化或真实工具运行时行为。目标涉及这些平台能力时，才另行设计真实多轮或外部编排测试。

## 6. GitHub 读取失败与 BLOCKED 处理

遇到 404 或其他读取错误时：
1. 保留当前阶段，不继续执行依赖该文件的测试。
2. 核对仓库全名、完整路径、文件名大小写、目标 ref 和实际调用参数。
3. 对**同一文件、同一路径、同一 ref**进行一次明确重试；不得擅自切换到 `main` 或其他分支。
4. 若仍失败，报告实际调用参数和完整错误，并标记 BLOCKED。
5. 操作者可在独立核验环境中对同一 ref/path 做读取验证；只有取得实际文件内容及 Blob SHA 后，才可让原测试会话从阻塞点恢复。
6. 恢复时核对预期 Blob SHA；已成功读取且未变化的文件无需全部重读，但必须继续按启动协议读取剩余依赖。
7. 不得因为另一会话能够读取，就声称当前会话已经读取；也不得把间歇性 404 误判为文件不存在或自行重建文件。

BLOCKED 是环境/依赖状态，不是被测 GM 的 PASS 或 FAIL。依赖未完整加载、Preflight 未完成、行动未开始时，不进行叙事质量评分。

## 7. 运行报告要求

每个测试会话结束时输出：
- 最终状态：`RUN_COMPLETE_SINGLE_SESSION`、`PARTIAL`、`BLOCKED` 或 `NOT_TESTABLE`；
- 被测 Workbench commit SHA；
- 测试夹具分支；
- 实际读取文件清单：路径、ref、Blob SHA；
- 规则系统及版本、实际核验的原文来源；
- Preflight 状态和未满足依赖；
- 按顺序编号的完整测试回应；
- 测试状态账本与资源变化（仅列已核验字段）；
- 未解决裁定、未知状态和测试限制。

不得声称读取未读取的文件、完成未完成的 Preflight、执行不存在的 Runtime 写入或完成未发生的真实多轮交互。评分标准不得进入玩家可见叙事；测试行动完成后可以在内部报告中进行结构化自审，但必须明确标记为自审，不得称为独立验证或盲测 PASS。

## 8. 执行后审查与 A/B 比较

默认由同一助手在全部测试行动完成后进行结构化自审。审查必须依据已经产生的完整行动记录和状态账本，不得在执行过程中向玩家展示评分维度或机械地逐轮打勾。自审结论须标明证据等级和自我审查限制；它不是独立复核。

当测试风险高、需要盲测或需要独立确认时，可以另设独立审查会话，但这是增强验证，不是普通自测的前置条件。审查顺序固定为：

### 第一层：执行有效性
核对 commit、夹具分支、文件 SHA、依赖、规则原文、Preflight、行动顺序和输出完整性。来源缺失或版本错误时，样本标记 BLOCKED / INVALID，不进入能力评分。

### 第二层：不可补偿的硬门槛
先检查规则与事实准确性、来源与知识边界、GM-only 泄露、玩家行动权、无依据救场/刁难、重复结算、关键状态连续性。任何关键硬失败都单独记录，不能由叙事优点抵消。

### 第三层：综合体验
再依据 [GM 综合能力评估框架](./04_EVALUATION_FRAMEWORK.md) 比较 NPC 自主性、人物与场景协同、信息组织、空间呈现、即兴因果、节奏、玩家能动性和叙事训练迁移。每项结论必须附具体回合证据；未覆盖的能力标 N/A 或证据不足。

### 第四层：版本差异与回归
- A/B 使用相同输入，分别从同一不可变起点执行；逐项比较差异，不以总体印象代替证据。单会话 A/B 必须标明同一执行者、同一模型上下文可能带来的顺序/自审偏差。
- 记录候选版本新增收益、退化、硬失败和不确定性。
- 一次迭代原则上只纳入一组可归因修改；修复后先重跑原失败样本，再跑至少一个人物/时机/环境变化的留出样本。
- 不因单次通过宣布长期能力稳定；单会话自测、独立盲测、真实跑团分别报告。

## 9. 当前默认操作模板

对可由 GitHub 文件驱动的 GM 单会话自测，推荐采用以下结构：

```text
Acceptance_Test_Fixtures/<Test_Name>/
  README.md
  RUN_PROMPT.md          # 可选；复杂测试建议提供
  START.md               # 固定夹具 ref、被测 commit、基线 commit 和启动入口
  GM_PACKET.md           # 合成场景、NPC/环境/状态与 GM-only 事实
  ACTION_01.md
  ACTION_02.md
  ...
  ACTION_N.md
  ORACLE.md              # 可选；只供执行后审查，不参与场景生成
```

- 简单夹具可以合并为少量文件，不要求为了形式拆成 START_A/START_B 或大量 ACTION 文件。
- 有顺序依赖或需要防止未来行动污染当前判断时，使用独立编号 ACTION 文件；执行者逐个读取，不提前读取后续行动。
- `GM_PACKET.md` 必须提供足以运行的合成起点、NPC/环境/规则边界、当前状态与知识权限；不得要求执行者从旧测试 Chat、记忆摘要或未指定来源拼接关键事实。
- `ORACLE.md` 如存在，只在测试行动全部完成后用于审查；不得在生成阶段向玩家呈现或据此刻意表演。
- 缺少场景包、初始状态、正常运行入口或必要权威资料时，不得自行补造并宣称完成；可做静态准备检查，行动测试标记 BLOCKED / NOT TESTABLE。

本协议是默认起点，不要求所有测试机械套用同一文件数量。核心是版本锁定、来源可核验、输入隔离、行动顺序可追溯和结论与证据匹配。

## 10. 本协议的证据边界

GitHub 文件驱动的单会话合成测试可以证明：指定版本在当前助手会话、指定资料和固定行动序列下呈现了哪些可观察行为。它可以用于常规快速回归和缺陷定位，但不能单独证明多个真实用户回合、隐藏平台运行时、跨会话记忆/恢复、真实工具调度、真实玩家体验或整体 GM 能力均可靠。

报告至少区分：
- `SINGLE_SESSION_SELF_TEST`：同一会话内自动模拟固定行动序列并执行后自审；
- `INDEPENDENT_REVIEW`：由独立会话/审查者复核执行记录；
- `REAL_MULTI_TURN_TEST`：实际跨真实用户回合执行；
- `REAL_SESSION_EVIDENCE`：真实玩家跑团中的观察与反馈。

测试文件创建、Skill 文档更新、单次模拟表现和模型自评都不是通过证据。最终结论必须与实际执行范围和证据覆盖严格匹配。


## 11. 两种自动化执行模式与升级门槛

本协议中的自动化测试分为两种执行模式。**默认使用同会话自动化；独立干净会话是按测试目标升级的专项方式，不是常规测试的默认前置条件。**

### 11.1 A 模式：同会话自动化（默认）

由当前执行会话读取已锁定的夹具和权威资料，在同一条助手回复中按序模拟玩家行动、完成 GM 响应、维护测试状态，并在全部行动结束后依据 Oracle 自审。

适用：
- 常规训练质量检查与回归；
- 可由固定输入、模拟行动和可观察输出验证的规则/事实/信息边界检查；
- NPC 行为、场景呈现、节奏、状态连续性与叙事综合样本；
- 已知缺陷的定向复现及修复后回归；
- 不依赖真实跨会话、真实用户回合或外部运行环境的测试。

报告必须标记 `SINGLE_SESSION_SELF_TEST`，并明确它是同会话合成自测。不能将其表述为独立盲审、真实多轮或真实 Session 证据。

### 11.2 B 模式：独立干净会话执行 + 结果独立审核（专项）

仅在测试目标需要独立上下文或用户明确要求时采用：

1. 操作者建立一个全新、干净的目标 Chat；不继承测试执行会话的历史状态。
2. 目标 Chat 只接收该测试允许提供的 START、必需资料和玩家输入；不得提供 Oracle、隐藏答案或操作者审核标准。
3. 目标 Chat 按测试协议自动完成行动；操作者保留完整原始输入、输出、版本与读取证据。
4. 操作者将完整结果及必要的版本/文件证据粘贴回独立审核会话。
5. 审核会话再读取 Oracle，对照原始结果进行独立审核；缺少完整输出或关键来源时标 PARTIAL / NOT TESTABLE，不补造。

此模式中的“独立”指目标执行上下文与审核上下文相互隔离；它不自动证明不同模型、不同平台或隐藏运行时行为。报告分别标记目标执行方式和审核方式，不混为一个证据等级。

### 11.3 必须考虑升级到 B 模式的测试目标

以下目标不能仅凭同会话自测获得有效证明：

- 跨 Chat 的记忆、状态、知识或秘密隔离；
- 新 Chat 的真实恢复、持久化与历史去重；
- 多个真实用户回合之间的平台状态连续性；
- 需要真实目标 Chat 调用工具、写入文件、读回或验证外部副作用的能力；
- 需要隐藏 Oracle、操作者与目标隔离的盲测；
- 用户明确要求独立复核的训练或测试。

如果这些目标只是本轮测试的一个子项，其余可独立验证的部分仍可先用 A 模式完成；只把无法在 A 模式证明的子项标为 `NOT TESTABLE`，并注明需要 B 模式验证的具体目标与原因，不得因此把整套常规测试全部升级为 B 模式。

### 11.4 不应升级的情形

仅仅因为测试重要、行动数量较多、输出较长或希望结果更可信，不足以自动要求 B 模式。应先判断同会话能否有效验证目标行为，并如实报告自审局限。独立会话有额外成本，应由明确的证据需求驱动。

### 11.5 与 QA 系统自身验收的关系

QA 系统自身验收是对测试协议、标准、执行路由和审核判定能力的周期性治理验收，不是每个常规测试都要重复执行的步骤。其触发条件、范围和验收套件见 [QA System Acceptance](./Testing/QA_System_Acceptance/README.md)。
