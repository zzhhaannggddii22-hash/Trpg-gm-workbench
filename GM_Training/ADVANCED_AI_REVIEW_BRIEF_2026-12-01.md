# 高级 AI 系统复审交接要点（2026-12-01）

> 本文件是一次性复审交接材料，不是新增的长期治理流程。复审时必须以当时 `main` 的实际文件和依赖关系为准；本文件只是用户预期与待检查方向。

## 一、项目定位与优先级

这是用户个人维护、个人游玩的 TRPG GM Workbench，主要由用户和 AI 使用，不是多人协作软件产品。

优先级：
1. 实际跑团体验与 GM 表现；
2. 正常跑团中的响应速度、运行可靠性；
3. 用户能理解、能维护的简单结构；
4. 必要的规则准确性、状态连续性和玩家/GM 信息隔离。

工程流程、架构完整性、测试覆盖率、文档数量本身都不是目标。允许一定低风险不完美；不追求零缺陷，不要把个人项目建设成企业级协作平台。

## 二、明确的工程预期

- 优先简单、直接、低摩擦的做法。只有能明确改善实际体验或降低重要风险时，才引入额外机制。
- 测试只提供有限证据，不能代替真实跑团体验，也不能保证质量。按风险和问题价值使用现有测试。
- 测试中心目前已经较丰富；不要仅因为理论上有益就新增测试族、协议、报告模板、基线、夹具或分类层。
- Evaluation Framework 保留：它用于较严格地约束 GM 能力下限；能力上限与真实表现最终由用户在实际跑团中的体验判断，不要再叠加复杂的认证体系。
- Capability Transfer 可以轻量化，但**跨 TRPG 系统验证必须保留为强制门槛**：通用方法在被视为稳定、推广到其他系统前，至少要在另一个不同 TRPG 规则系统中验证。验证失败或有边界也要如实记录。
- Prep QA 是可选项，不要改造成每次备团的强制流程。通常备团后的 1–2 轮自审已足够。
- 当前顶层架构暂不主动重构。只有发现具体、重要且能说明收益的问题时，才提出结构调整；不要为了整齐而重排目录或抽象层。
- 用户单人维护：默认只在现有 `main` 上工作，不创建 feature/fix/test/experiment/release 等分支，不把 PR 作为常规流程。Issue 如有需要直接使用 GitHub 原生编号。
- 不要把“轻量化”本身继续发展成另一套管理体系。

## 三、单人使用场景下的安全性边界

本项目只有用户本人和 AI 使用，不存在其他玩家、陌生参与者或对抗性使用者。用户也明确表示不会故意攻击或恶意利用系统。因此：
- 不要按多人在线产品、公共服务或高对抗环境建立复杂威胁模型。
- 不需要投入大量精力设计防恶意用户、防玩家作弊、防权限滥用、多人身份隔离或企业级安全治理。
- 不要为了假设中的攻击场景增加复杂流程、验证环节或维护负担。
- 只有发现现实、具体且会影响用户正常使用的风险时，才考虑对应措施。

但以下事项仍然重要，它们属于正常使用体验与数据正确性，而不是防范用户攻击：
- GM-only 内容与玩家当前视角之间的隔离，目的是避免意外剧透；用户不会主动查看 GM-only 资料，但希望减少误展示。
- 不同系统、模组和战役的规则与事实边界，避免意外串用。
- 人物卡、战役状态、资源和结算数据的准确性与连续性。
- 避免意外覆盖、丢失或重复写入用户的项目资料。

复审时应把“对抗性安全”列为低优先级，把“避免正常操作中的意外泄露、混淆和数据错误”作为实际体验与可靠性问题正常处理。

## 四、Runtime 重点审查方向

主要审查 `GM_Training/07_RUNTIME_CONTROL_PROTOCOL.md`。该文件体量较大，先理解实际引用、依赖和运行路径，再判断哪些步骤值得保留、简化或静默化。不要仅凭名称删除机制。

### 值得检查的运行成本
以下是此前初步审查发现的潜在开销，需由高级 AI 对照当前文件核实：
- 正常每轮显式管理 Entry Gate 的 READY / READY_WITH_LIMITS / BLOCKED 标签；
- 常规场景也生成 Context ID、Parent/Child Context；
- 日常流程中反复使用 REQUIRED / CONDITIONAL / SUPPORTING 等装配分类；
- 每轮或每个小动作生成 Trace / Manifest；
- 将完整行动闭环清单逐项显式执行；
- 重复读取已经充分掌握、且没有变化的当前场景资料；
- 向玩家展示内部核验过程，以证明内部流程已经完成。

可以考虑将这些能力改为内部静默判断，或仅在复杂事务、故障追溯、跨会话恢复和高风险场景启用。重点是减少正常跑团中的显式步骤与等待，不是取消必要的判断。

### 必须保护的能力
简化时尤其不能削弱：
- 玩家视角与 GM-only 信息隔离；
- 不同 TRPG 系统、模组和战役 CANON 的边界；
- 关键状态、资源、物品与结算的连续性和防重复处理；
- 高影响规则裁定的准确性；
- 线索来源、事实/推断/未知的区分；
- 出错后的定位、修正与历史可追溯性。

### Runtime 复审希望得到的结果
找出正常跑团路径中真实存在的重复劳动、过度显式化和不必要等待；区分“核心安全机制”与“管理性仪式”。优先给出少量、明确、能解释收益的改动，不要为了全面而全面重写 Runtime，也不要只根据文档长度或形式复杂度下结论。

## 五、主动寻找重大缺陷与高收益改进

本次复审不只是删减流程、降低 Runtime 成本。还要在当前项目目标下，主动检查系统是否存在潜在重大缺陷，以及是否有少量修改就能明显改善 GM 质量或运行性能的机会。

### A. 潜在重大缺陷
重点关注真正可能破坏跑团体验或造成严重事故的失效路径，例如：
- GM-only 信息、模组秘密或隐藏状态泄露给玩家；
- 不同 TRPG 系统、模组或战役的规则与 CANON 串用；
- 规则裁定、骰点处理、资源结算或状态变更存在系统性错误；
- 状态恢复、跨会话交接或结算流程可能丢失、重复或篡改事实；
- Runtime 机制之间存在冲突，导致关键步骤被跳过、重复执行或陷入循环；
- 模组信息、线索或 NPC 行为处理存在结构性问题，可能持续损害公平性、因果一致性或玩家决策空间。

不要求把所有边缘情况都列为缺陷。优先识别影响严重、发生路径可信、当前保护不足的问题。

### B. 高收益质量 / 性能改进
主动寻找修改范围有限、收益可能明显的机会，例如：
- 减少正常游戏轮次的等待、重复读取、重复核验和冗余输出；
- 改善规则与模组资料检索，使关键信息更快、更准确地进入运行上下文；
- 提升场景呈现、NPC 区分度、玩家行动响应、线索公平性和节奏控制；
- 减少备团、状态记录、会话恢复中的重复劳动；
- 简化一处关键流程，消除多份文档重复定义或互相冲突造成的运行不确定性。

这里追求的是实际收益，不是优化数量。不要为微小、难以感知的指标变化增加复杂机制。

### C. 每项重点发现的说明要求
对值得处理的发现，尽量说明：
- **问题 / 机会：** 具体发生在哪里，当前行为是什么；
- **证据与置信度：** 指向当前文件、引用关系、实际案例或可复现路径；区分已确认问题与待验证风险；
- **实际影响：** 对玩家体验、GM 质量、可靠性、响应速度或维护负担的影响；
- **建议改动：** 最小可行修复或优化，以及可能的副作用；
- **验证方式：** 使用最小且相关的检查确认效果，不扩建测试体系；
- **优先级：** 先处理重大风险和高收益改进，其余记录为低优先级或暂不处理。

不要为了显得审查深入而制造问题清单。若没有发现证据充分的重大缺陷或高收益改进，应明确说明，而不是凑数。

## 六、全系统复审方式

1. 从当时 `main` 读取真实状态，检查关键文件之间的引用和冲突；不要把旧报告或本交接文件当作当前事实。
2. 先判断哪些机制对实际跑团确有价值，哪些只是增加维护和执行成本。
3. 结论按“保留 / 简化 / 删除 / 暂缓”区分，并解释对跑团质量、速度、风险和维护成本的影响。
4. 优先复用已有机制；只有具体问题无法由现有机制处理时才考虑新增设施。
5. 对低风险修改做最小相关验证即可。不要每次变更都启动全量测试，也不要为了证明优化而扩建测试系统。
6. 不要把本次复审扩张为大规模重构。除非存在明确的高风险问题，否则保留已经稳定且能工作的部分。

## 七、优先查阅文件

- `GM_Training/07_RUNTIME_CONTROL_PROTOCOL.md`：Runtime 主协议，重点审查正常运行路径的成本与必要机制。
- `GM_Training/Testing/README.md`：测试中心现状与防止继续膨胀的约束。
- `GM_Training/04_EVALUATION_FRAMEWORK.md`：保留的能力下限评估框架。
- `CAPABILITY_TRANSFER.md`：轻量记录方式及强制跨 TRPG 验证要求。
- `GM_Training/ADVANCED_MODEL_PREP_QA_PROTOCOL.md`：确认 Prep QA 的可选定位。
- 其他文件按实际依赖关系查阅，不需要为了“全覆盖”而逐份深挖无关资料。

---

**最终判断标准：** 系统是否让 AI 在真实 TRPG 中主持得更好、更稳、更快，同时仍然简单到用户愿意长期维护。不要让维护系统本身变成主要工作。
