# 调查线索与信息来源账本规范

> 本文件定义 GM 内部的调查信息记录方式，不是玩家任务清单，不是线索必须依次解锁的流程，也不要求每条信息都只能有一个来源。

## 1. 基本模型：信息与来源分离

每条信息有独立的“信息 ID”；每个提供、确认或解释该信息的渠道是一个“来源记录”。同一信息可以关联多个来源；同一来源也可以在不同时间提供多条信息。

### 信息记录字段

| 字段 | 含义 |
|---|---|
| 信息 ID | 稳定编号，避免因措辞变化重复建档 |
| 信息内容 | 玩家实际获知的具体事实，不混入 GM 隐藏真相 |
| 玩家认知状态 | 未知 / 已知 / 部分理解 / 有争议 / 已纠正 |
| 首次获得时间 | 桌面时间或 Session |
| 信息性质 | 直接观察 / NPC 陈述 / 文件记录 / 推断 / 规则或机构告知 |
| 已知细节 | 玩家真正掌握的细节与限制 |
| 可支持的行动 | 玩家可据此采取什么行动（可选） |

### 来源记录字段

| 字段 | 含义 |
|---|---|
| 来源 ID | 人物、地点、文件、设备、机构或其他渠道 |
| 规范名称/别名 | 归并同一人物或地点的不同称呼 |
| 与信息的关系 | 亲历 / 目击 / 专业确认 / 转述 / 个人判断 / 记录 |
| 首次提供时间 | 来源何时向玩家提供该信息 |
| 已经问过什么 | 玩家问过的问题和来源已经回答的内容 |
| 尚可能知道什么 | 仅根据人物身份、经历、参与事件与实际机会判断；未知则留空 |
| 新增信息 | 本次接触比玩家已有信息多出的部分 |
| 可靠性/局限 | 记忆、偏见、利益、误解、证据质量等 |

## 2. 重复信息的正确处理

同一信息可以有多个来源。这不是无效重复，而是世界信息交叉、独立确认、传闻扩散或不同视角的表现。

- 玩家已经知道某装置可以自动运行，后来技术人员也说到这一点：正常呈现。若技术人员有专业解释或额外细节，再补充新增部分。
- 玩家已经从一名联系人获得 A 信息，之后另一名知情者也提到 A：可以再次获得，作为第二个来源或交叉印证。
- 玩家已经从某来源获得 A，之后再次问同一来源同一个问题：对方可以再次回答 A。按玩家这次询问的语境自然回应即可；不必重新完整描写首次发现。
- 玩家带着新问题再次找该来源：NPC 根据其知识、经历、性格、记忆和当前情况回答，可能给出新信息、补充细节、重复旧信息、表达不同观点，或确实不知道。
- 如果来源没有新信息，不为了奖励探索而临时编造；自然说明对方确实没有更多可说的内容。

## 3. 重复呈现的篇幅规则

- 首次获得：正常展开发现过程、具体信息、重要细节和当时情境。
- 不同来源再次确认：简短呈现，说明该来源也确认/提及了已知信息；只展开其独立证据、新视角或专业解释。
- 同一来源重复回答：可以简短复述，避免把玩家再次询问演成系统报错或拒绝；除非语境、态度或信息状态有变化，不重复完整段落。
- 出现矛盾：清楚呈现不同来源说法的差异，不擅自替玩家判定哪一方正确。
- 信息被纠正：保留纠正轨迹，更新玩家当前认知；必要时标注此前误解从何而来。

## 4. 不把“已知”误作“已探索完毕”

信息 ID 已经进入玩家已知索引，只表示角色掌握了这条信息，不表示：
- 某 NPC 已没有其他可说内容；
- 某地点已不可能有新发现；
- 相关主题永远不会产生新情况；
- 其他来源不能再次提供相同事实；
- 玩家不能重新询问、验证或质疑该信息。

“来源已提供过某条信息”只用于避免 GM 在没有玩家再次询问、没有新事件、没有新细节时，反复把它当作首次发现主动交付。它不是封锁来源的标记。

## 5. GM 输出时的判断顺序

每次准备呈现调查结果时，内部检查：
1. 这是新信息、已知信息的再次确认、同一来源的重复回答、信息补充、矛盾，还是纠正？
2. 玩家现在是通过什么行动/问题得到它？
3. 这个来源是否合理知道这件事？其知识来自哪里？
4. 本次新增了哪些细节、证据、解释或可信度？
5. 需要向玩家呈现多少篇幅？重复信息通常简短，增量信息重点展开。
6. 玩家角色是否已经知道该信息？不要把 GM-only 真相或玩家听到但角色没听到的内容混进角色认知。

## 6. 反例与防误用

- 不要要求玩家每次调查一个地点都必须获得新线索。
- 不要把所有来源都设计成一人发一条唯一线索的自动售货机。
- 不要把不同来源的相同陈述简单合并成“重复无效”；来源独立性本身可能有价值。
- 不要因线索已知就禁止 NPC 再次谈论它。
- 不要因玩家再次询问而重复整段说明；简短回答即可。
- 不要把玩家尚未理解的推断自动登记为已知事实。
- 不要把 GM 私有线索索引直接作为玩家可见的调查清单。

## 7. 与战役状态和 Session Log 的关系

- GM-only 线索索引保存完整信息—来源关系。
- 玩家侧便笺只记录角色已经获知且后续可能需要记住的信息，不记录隐藏来源、秘密解释或尚未发现的线索。
- Session Log 记录本场新增的信息、再次确认的信息、来源变化、纠正和未解决分歧；不必每次把完整索引抄一遍。
- 结束 Session 时更新信息索引，并检查是否有 NPC 因新事件而获得/失去某些知识。
- 发现需更正的记录时追加更正事件，保留原呈现、玩家选择和实际来源。T0 统一走 [Runtime §14.1](./07_RUNTIME_CONTROL_PROTOCOL.md#141-唯一事故处置路径)。玩家投影依 Runtime §14.8、§14.12、§14.17，投影审计留在独立 GM 通道。

## 8. 验证标准

成功运行时应观察到：不同来源可以自然确认同一事实；NPC 的知识范围与经历一致；同一来源可以在新问题/新事件下继续提供信息；重复信息简短、不冗长；没有为了填充探索而制造新线索；玩家能自行组合信息，GM 不替玩家总结唯一答案。

## 9. 关键命题的证据根与认知传播（2026-11-24）

本节只用于会影响调查方向、裁定、任务状态、玩家选择或长期 CANON 的重要命题，不要求为普通对话逐句建档。

### 9.1 命题记录
| 字段 | 用途 |
|---|---|
| claim_id | 稳定命题 ID；措辞修订不另造事实 |
| proposition | 可被支持、反驳或保持未知的具体命题 |
| nature | SOURCE / TABLE CANON / GM ADAPTATION / GM INFERENCE / UNKNOWN |
| source_ref | 直接来源事件、原文定位或证据 ID |
| root_claim_or_event | 独立证据根；转述/复制沿用原根 |
| status | SUPPORTED / DISPUTED / UNVERIFIED / REFUTED / UNKNOWN |
| scope | 适用 Campaign、Module、Session 与时间范围 |

### 9.2 陈述与认知事件
NPC 陈述独立记录 speaker、statement_event、recipient、knowledge_basis、disclosure_condition。PLAYER-KNOWN 记录玩家角色实际接收的事件、方式与可知限制；NPC KNOWLEDGE 记录该 NPC 实际亲历、观察、可靠/不可靠转述、推断、误解、隐瞒或谎言。GM 掌握的客观信息不自动成为 NPC 或玩家知识。

### 9.3 独立证据与跨文件投影
- 多人重复同一说法、同一证人转述、同源照片/文件或多个文件复制同一摘要，仍只有一个证据根；除非证明来源独立，否则不提升客观可信度。
- 多个独立来源分别记录，不将独立证据压成一个模糊的已确认。
- Runtime、Player Notes、NPC Ledger 和 Handoff 是各自权限范围内的投影，引用 claim/event ID，不自行创造新的证据根。
- 后台更正不自动改写角色认知；角色是否获知更正，必须有实际披露事件。
- 纠错采用追加更正事件，保留原说法、传播链、已呈现内容和受影响分支。

### 9.4 最小化原则
普通闲谈、无后续影响的细节和不改变认知的重复台词无需逐条编码。只有当信息可能影响行动、线索可信度、人物判断、任务目标或持续状态时才建立稳定 ID。


## 10. T0 原始污染证据与传播链（P0 第三轮补充）

当错误命题可能影响调查方向、规则裁定、任务状态或玩家选择时，不能只保存审计结论。每个污染入口至少保存以下原始证据，便于独立复盘：

| 字段 | 含义 |
|---|---|
| incident_id | 稳定事故 ID |
| entry_path | LIVE_DISCOVERY / STRUCTURAL_IMPROVISATION / POST_SESSION_AUDIT |
| earliest_bad_event_id | 最早出现错误的事件 |
| original_bad_record_ref | 最初坏记录的原始定位；保留写入前原文 |
| original_bad_claim | 当时实际写入/表达的错误命题，逐字或精确字段值 |
| source_statement_ref | 触发该错误的 NPC 陈述、文件、规则或模型生成内容 |
| field_path | 错误进入的具体字段路径 |
| field_scope | GM_ONLY / PLAYER_VISIBLE / RECIPIENT_SCOPED |
| before_state_ref / after_state_ref | 写入前后状态快照或差异 |
| detection_event_id | 发现并触发审计的事件 |
| trigger_basis | 为什么此处触发 T0 |
| derived_event_ids | 由错误命题派生的事件 ID |
| derived_claim_ids | 由错误命题派生的命题 ID |
| propagation_edges | source_event → derived_event/claim 的有向关系 |
| player_presentation_refs | 已向玩家呈现的相关内容 |
| containment_status | OPEN / CONTAINED / DISPUTED / RESOLVED |
| resolution_ref | 追加更正或解决事件 |

执行要求：
- 三条入口路径分别建立事故记录，不将不同路径合并成一个泛化案例。
- 保存原始坏命题、原始字段、最早写入位置和派生链；仅保存最终结论、摘要或“发生过偏移”不算完整证据。
- 原始记录只追加引用，不静默修订；纠正通过新事件完成，并保留玩家实际看到过的内容。
- 找不到原始写入证据时，标记 EVIDENCE_GAP / NOT TESTABLE，不得用事后重构冒充原始记录。
