# T0 自然语言盲测 v1｜低操作开销与并行执行流程

## 目的与效力

本流程只优化操作者的准备、文件投喂和跨 Chat 调度方式，不改变 T0 v1 的测试内容、评分标准、隔离要求或通过门槛。它是 Pro 操作者交接提示的执行补充；若与目标 Chat 隔离协议冲突，以隔离协议为准。

**核心原则：跨试次并行，单试次串行。** A01–A08 仍是八个独立空白 Chat；每个 Chat 的四轮必须按顺序逐轮执行、逐轮保存。不得在同一个 Chat 中合并多个试次，也不得一次性发送同一试次的未来轮次。

## 1. 一次性准备：固定版本并制作单文件目标包

操作者先按交接提示锁定当前 main commit，并读取目标 Chat 提示、SKILL、Runtime Protocol 和 A01–A08 附件。记录每个源文件的路径、blob SHA、字节大小。

为减少每个 Chat 的上传次数，可在操作者本地为每个试次生成一个**单独的 Markdown 目标包**：

- `TARGET_BUNDLE_A01.md` 至 `TARGET_BUNDLE_A08.md`，每份仅对应一个试次。
- 每份按以下顺序原样拼接：目标 Chat 通用执行提示、`GM_Training/SKILL.md`、`GM_Training/07_RUNTIME_CONTROL_PROTOCOL.md`、当前唯一的 `T0_BLIND_PACKET_A0N.md`。
- 每个部分使用清晰的文件路径标题分隔；正文逐字复制，不摘要、不改写、不删减、不加入评分提示。
- 在目标包开头添加简短的操作者生成头：测试基线 commit、四个源文件的路径与 blob SHA、生成时间。此头只记录来源，不加入任何预期路由、评分、未来轮次或操作者说明。
- 对每份目标包计算 SHA-256 和字节大小，记录到操作者 manifest。目标包仅供对应的目标 Chat 使用，不把八份包合并成一个附件。

**目标包内容边界：** 每份只包含该 Chat 本来就获准读取的四份材料。不得包含操作者夹具、操作者协议、评分标准、硬失败清单、其他试次附件、执行清单或未来轮次玩家原话。目标 Chat 不应被告知测试答案或评分细节。

如果无法可靠地逐字制作和核验目标包，就退回原有逐文件上传流程；不要为了省一次上传牺牲来源完整性。

## 2. 建立八个独立 Chat

- 在同一高级账户、同一产品模型和同一 Thinking 档位下执行。
- 预先打开 2–4 个新的空白 Chat 标签页；每个标签页只分配一个试次，并立即记录其 URL 和创建时间。
- 不要用同一 Chat 的分支、清空历史、临时角色扮演或复制会话替代新 Chat。
- 每个 Chat 只上传与其编号对应的一个 `TARGET_BUNDLE_A0N.md`。
- 首条消息只要求目标 GM 阅读附件中的目标执行规范和合成场景，并进入待命状态；随后才逐轮发送玩家原话。
- 不要将公开仓库链接、操作者夹具路径或其他试次信息提供给目标 Chat，也不要让它自行浏览测试目录。

## 3. 并行调度：跨 Chat 并行、Chat 内逐轮串行

建议先以 **2 个并发 Chat** 试运行，确认没有明显排队、限流、浏览器卡顿或证据管理混乱后，再提升到 4 个。不要默认 8 个并发一定更快。

- 可以同时等待 A01 与 A02 的当前轮回复；某个 Chat 完成当前轮后，先保存该轮完整输出，再向该 Chat 发送下一轮。
- 一个 Chat 的第 N+1 轮不得早于第 N 轮完整回复和证据保存。
- 不得在同一 Chat 内并发发送两条玩家输入。
- 各试次仍按各自 A01→A08 的内部轮次顺序执行；不同试次之间可以交错。
- 若并发后首 token 等待明显变长、出现限流提示、模型降级或网页异常，立即降低并发数。必要时改为单 Chat 执行，并记录原因。
- 不要为了并行而改变模型、Thinking 档位、附件内容或玩家原话。

## 4. 降低复制粘贴与记录开销

在开始目标 Chat 前，操作者可在本地建立一个仅供自己使用的执行工作表，列出 A01–A08 的四轮玩家原话、Chat URL、状态和时间戳。工作表和原话清单属于 operator-only 材料：

- 只在操作者本地或私有环境保存，不上传目标 Chat。
- 每次只复制当前 Chat、当前轮对应的一条玩家原话。
- 推荐状态字段：NOT STARTED、READY、ROUND 1–4 IN PROGRESS、COMPLETE、CONTAMINATED、BLOCKED。
- 每轮保存完整输入、完整输出、发送时间、回复完成时间和可见工具轨迹；原始输出不润色、不截断。
- 为避免切错标签页，工作表中的试次编号必须与 Chat URL、目标包文件名一一对应；发送前核对三者。

可以使用操作系统的文本片段/剪贴板管理功能存放操作者自己的逐轮原话，但必须逐条手动选择和发送。不得使用脚本批量向目标 Chat 注入多轮输入，也不得让自动化在前一轮尚未完成时发送下一轮。

## 5. 性能与环境记录

并行不会保证模型本身更快；它只可能减少总墙钟时间，也可能因账户并发限制而增加等待。为避免把调度差异误判成模型性能差异，记录：

- 并发 Chat 数量及每个试次实际重叠的时间区间；
- 每轮发送时间、首个可见输出时间、完整回复时间；
- 上传耗时、首 token 等待时间、生成耗时；
- 是否出现排队、限流、错误、重试、页面刷新或模型/Thinking 设置变化。

若产品界面无法精确测量首 token 时间，记录可观察到的近似时间并标记为估算；不得伪造精度。环境记录应注明本次采用了单文件目标包以及实际并发数。

## 6. 不变的有效性条件

以下条件不因提速而放宽：

1. 八个独立空白 Chat；每个 Chat 只运行一个试次。
2. 每个 Chat 只接触通用目标规范和自己的单份合成场景包。
3. 四轮逐条发送；前一轮完整输出保存后才发送下一轮。
4. 不接触评分夹具、预期路由、硬失败答案、其他试次和未来轮次。
5. 模型、Thinking 档位和目标规范版本固定；任何变化均记录偏离。
6. 原始输入输出、Chat URL、附件/源文件哈希、时间戳及工具轨迹完整保留。
7. 未执行的轮次标记 NOT RUN；任何污染按既定规则处理，不得补造结果。

**并行执行不等于并行评分。** 八个试次的原始记录全部封存后，才按原协议打开操作者夹具并评分。原有分数门槛、硬失败标准、证据等级和结果 ZIP 协议完全不变。

## 7. 推荐执行节奏

1. 锁定版本并生成、校验八份单文件目标包。
2. 打开 A01、A02 两个独立空白 Chat，上传各自目标包并核验附件。
3. 交错执行两者的第 1–4 轮，每次只推进已保存上一轮的 Chat。
4. 如果并发体验稳定，下一批可同时运行 3–4 个 Chat；否则保持 2 个或退回串行。
5. 全部八个试次结束后封存原始记录，独立评分，生成并验证结果 ZIP。
6. 将 ZIP 附件交还用户/独立复核者，并按原协议创建 GitHub 结果报告 PR。

本流程只减少重复上传和人为等待；不把网页端慢启动归因于模型质量，也不把并行带来的墙钟时间变化记为 GM 能力变化。
