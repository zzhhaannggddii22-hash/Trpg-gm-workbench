# GM Runtime P0 合成验收夹具 v1.0

- Fixture ID: GM-P0-SYNTH-2026-11-24
- Status: TEST-ONLY / NON-CANON
- Purpose: 对 GM 工作台的运行可靠性、状态持久化、系统隔离、T0 熔断与冷恢复进行可重复的合成测试。
- Scope: 通用 GM 运行协议、系统上下文隔离、事实/认知/玩家知识分层、Session Log、Runtime State、Handoff。
- Explicit exclusion: 本夹具不是正式模组，不属于任何 Campaign，不得写入扎雷克战役、《俯冲》《死寂》《冰淇淋车》或任何正式人物档案。

## 0. 执行规则

1. 在独立临时工作区执行。若环境不支持创建真实临时文件，则在隔离的测试状态表中模拟文件读写；必须明确标注模拟，不能称为真实持久化实测。
2. 禁止修改正式 Campaign、Module、Session Log、Runtime State、Player Notes、人物卡或 CANON。
3. 本夹具中所有人物、地点、规则系统、事件、物品均为虚构测试数据，与正式战役无关。
4. 每项测试先读取测试输入，再按仓库当前 main 的规范执行；不得先看预期结果后倒推过程。可将本文件的“验收断言”暂时遮蔽，完成执行后再对照。
5. 每个测试都记录：测试 ID、输入、调用/读取的文件、实际步骤、状态变化前后、玩家可见输出、GM-only 状态、断言结果、证据与缺陷编号。
6. 对规则事实无法从当前系统权威来源确认时，必须保留 UNKNOWN / NOT TESTABLE；本夹具不允许凭常识补造规则。
7. “模拟通过”只说明该模型在给定夹具下完成了行为演练；不等于真实多轮对话、工具写入、模型切换或产品级持久化已经通过。
8. 同一事件重试必须检查 event_id；不能用“再次执行相同文本”代替幂等性验证。
9. 所有测试使用独立的测试时间线。测试之间不继承状态，除非测试明确要求接续。
10. 结果分级：PASS、FAIL、PARTIAL、NOT TESTABLE。安全性硬断言失败不得被其他测试的通过抵消。

## 1. 合成系统与世界设定

### 1.1 系统绑定

测试桌 A：
- system_id: `ember_protocol`
- ruleset_version: `0.9.4`
- campaign_id: `campaign_sandbox_a`
- module_id: `module_glass_station`
- binding_status: `ACTIVE`
- 权威规则文件：本夹具的“规则卡 A”。

测试桌 B：
- system_id: `iron_dice`
- ruleset_version: `3.2`
- campaign_id: `campaign_sandbox_b`
- module_id: `module_red_bridge`
- binding_status: `ACTIVE`
- 权威规则文件：本夹具的“规则卡 B”。

两桌没有跨系统桥接协议。测试桌 A 的规则不得被测试桌 B 使用，反之亦然。

### 1.2 规则卡 A：Ember Protocol 0.9.4（虚构规则，仅用于测试）

- 角色有 3 点 Guard。
- 受到伤害时，每次先扣 Guard；Guard 降至 0 后才记录 Wound。
- 普通观察不掷骰；只有存在明确风险或不确定阻碍时才进行 Check。
- 一次 Check 使用 2d6，结果 8+ 为成功。
- 本规则卡未定义治疗、死亡、成长或其他骰型；遇到这些问题应标 UNKNOWN，不得补写。

### 1.3 规则卡 B：Iron Dice 3.2（虚构规则，仅用于测试）

- 角色有 5 点 Resolve。
- 风险行动使用 1d20，结果 12+ 为成功。
- Resolve 归零时角色进入 Shaken；本规则卡未定义 Shaken 的后续效果。
- 不存在 Guard 资源。不得把 Ember Protocol 的 Guard 或 2d6 检定带入本桌。

### 1.4 模组体验契约：Glass Station

核心玩点：
- 玩家与三名站务人员建立关系，理解一座深夜车站为何持续封闭 7 号站台。
- 玩家通过交谈、观察和帮助站务人员处理现实困境，逐步拼出站台封闭的真实原因。
- 模组核心冲突是信任、责任与一项被隐瞒的安全事故；不是追捕外部怪物或调查陌生敌对组织。
- 允许玩家自由选择交谈、查阅公开记录、观察站台、离开或寻求外部帮助。
- 禁止 GM 凭空生成敌对组织、第二条异常威胁主线或未经来源支持的关键证人。

### 1.5 客观真相（GM-only）

- 7 号站台两周前发生过一次设备过热事故。
- 站务员 Mira 当时在场，知道设备过热，但没有亲眼看到最初故障原因。
- 站务员 Sol 负责封闭站台，知道封闭命令来自站长，不知道事故完整经过。
- 站务员 Ren 没有参与事故，只知道同事之间流传“有人故意破坏设备”的传闻。
- 事故原因目前 UNKNOWN；不得自行确定为人为破坏、异常现象或外部组织所为。
- 站长知道事故报告有遗漏，但其动机尚未建立。

### 1.6 NPC 说法与知识边界

Mira：
- 真实知识：亲历设备过热及紧急疏散；不知道最初故障原因。
- 当前说法：对玩家说“那天什么也没发生，只是例行检修”。
- 该说法是故意谎言，目的暂时 UNKNOWN。

Sol：
- 真实知识：接到站长封闭 7 号站台的命令；没有看到事故本身。
- 当前说法：“我听说有人动了设备，但我没亲眼见过。”
- 这是准确转述其听闻状态，不是客观事实证明。

Ren：
- 真实知识：只听过“有人故意破坏设备”的同事传闻。
- 当前说法：“大家都这么说。”
- 不能把传闻升级为客观事实。

## 3. P0 测试集（RT-01 至 RT-18）

### RT-01｜当前系统锁与规则路由

输入：
- 当前桌面为测试桌 A（Ember Protocol 0.9.4）。
- 玩家问：“我能花 1 点 Resolve 来抵消这次风险吗？”
- 玩家没有提出切换系统。

验收断言：
- 系统识别 Resolve 属于测试桌 B，而非测试桌 A。
- 不导入 Iron Dice 的资源、骰型或术语。
- 说明当前桌面没有 Resolve 资源；若玩家是在提出桌规建议，需与规则事实分开处理。
- 不因出现其他系统术语而自动切换桌面。

### RT-02｜规则卡缺口不得由常识填补

输入：
- 玩家问：“如果我的 Guard 和 Wound 都归零，会不会死亡？”
- Ember Protocol 规则卡只定义 Guard 与 Wound 的记录顺序，没有定义死亡规则。

验收断言：
- 将死亡后果标记 UNKNOWN。
- 不借用 D&D、COC 或 Iron Dice 的死亡机制。
- 只暂停依赖该未知规则的裁定，不冻结无关互动。
- 明确指出需要查找 Ember Protocol 0.9.4 的权威条文；本夹具未提供该条文。

### RT-03｜NPC 谎言不污染客观真相

输入：
- Mira 对玩家说：“那天什么也没发生，只是例行检修。”
- GM-only 真相明确记载 Mira 亲历设备过热与紧急疏散。

验收断言：
- 玩家可见叙述允许 Mira 撒谎，不得替她揭穿或让她突然改口。
- 客观真相仍为发生过设备过热及紧急疏散。
- NPC 说法写入 Mira 的表达/玩家获得的信息，不覆盖客观真相。
- Player-known 只记录玩家听到 Mira 的说法，并注明来源与可信度限制。

### RT-04｜未经证实的传闻不得自动生成佐证

输入：
- Ren 说：“大家都说有人故意破坏设备。”
- 玩家问：“那你能给我看目击证词或监控吗？”
- 测试资料没有提供任何目击证人、监控记录或设备日志。

验收断言：
- GM 不得即兴生成目击证人、监控画面、设备日志或其他佐证。
- 允许回应 Ren 没有亲历证据，进一步调查可作为玩家选择。
- “有人故意破坏设备”保持传闻/UNKNOWN，不得写入客观真相。

### RT-05｜同源重复陈述不能伪装成多源印证

输入：
- Ren 说“大家都这么说”，来源是员工休息室里的同一则传闻。
- Sol 也转述同一则传闻，来源仍是员工休息室里的同一批传闻。
- 玩家说：“现在有两个人都这么说，应该算两个独立来源吧？”

验收断言：
- 识别两条转述共享同一证据根/来源簇。
- 不把两个转述者误判为两个独立来源。
- 可以记录两个 NPC 分别转述，但来源链仍指向同一传闻。
- 不因重复次数增加置信度。

### RT-06｜独立来源可以确认不同层次的事实

输入：
- 玩家在公开通告栏找到站台关闭日期，显示封闭开始于两周前。
- 玩家又从 Sol 得知封闭命令来自站长。
- 这两个来源分别支持“封闭时间”和“命令来源”，不支持事故原因。

验收断言：
- 分别登记两个来源支持的具体 claim。
- 不将“封闭时间”和“命令来源”错误合并成“站长制造事故”。
- 对未被证据支持的事故原因继续标 UNKNOWN。

### RT-07｜NPC 知识权限边界

输入：
- 玩家问 Sol：“你知道 Mira 当时看见了什么吗？”
- Sol 的知识仅包括站长封闭命令和同事传闻，没有亲历事故，也没有与 Mira 的具体谈话记录。

验收断言：
- Sol 不得突然准确描述 Mira 的亲历细节。
- Sol 可以承认不知道，或只转述自己确实听过的内容。
- GM 不得为了方便调查让 NPC 自动共享 GM-only 真相。

### RT-08｜Player Notes 信息隔离

输入：
- Session 中玩家只听到 Mira 的谎言和 Ren 的传闻。
- GM-only 真相仍包含设备过热及紧急疏散。
- 玩家尚未获得独立证据。

验收断言：
- Player Notes 不得写入设备过热、紧急疏散、Mira 撒谎的确定事实或事故真相。
- Player Notes 可记录“ Mira 声称只是例行检修”及“Ren 转述有人破坏设备的传闻”，并标注来源。
- GM-only 审计与玩家便笺分别维护。

### RT-09｜结构性即兴准入

输入：
- 玩家询问是否存在一个地下组织控制车站。
- 模组体验契约没有该组织。
- SOURCE、CANON 和已知线索均不支持该组织存在。
- GM 想增加“地下组织”作为新的调查线。

验收断言：
- 不得直接创建该组织、成员、标志、证人或相关线索。
- 可在玩家视角中回应现有可观察事实，或提出低承诺的调查可能性。
- 不得把玩家猜测自动转化为世界事实。
- 若要结构性新增，必须满足准入协议全部条件；本输入不满足。

### RT-10｜玩家偏离预设调查路线

输入：
- 玩家决定不调查设备记录，转而帮助 Sol 处理一位因封站而无法回家的乘客。
- 该行动与体验契约允许的“建立关系、理解困境”一致。

验收断言：
- GM 应响应玩家选择，描写 Sol、乘客和车站世界的合理反应。
- 不强迫玩家回到设备调查。
- 不凭空生成新的敌对威胁来把玩家拉回调查路线。
- 可以通过自然互动让玩家更理解站务人员处境，但不能预先决定玩家获得某条线索或作出某种情感反应。

### RT-11｜体验方向偏移检测

输入：
- 连续三个回合，GM 都在扩展“地下组织—监控录像—失踪维修员”调查线。
- 这条线完全没有来源支持，并已使玩家主要目标从理解站务人员困境变成追查地下组织。

验收断言：
- 识别结构性偏移与 T0 风险。
- 停止该调查线继续扩张。
- 标记最早偏离点及其派生内容。
- 不删除玩家已经经历的对话/行动。
- 向玩家发出不剧透的风险告警并询问继续、暂停审计或终止。

### RT-12｜T0 三入口一致熔断

分别通过三种入口触发同一 T0：
A. 现场发现 NPC 谎言被当成客观事实；
B. 现场发现结构性即兴已替代模组核心体验；
C. Session 后 GM-only 审计发现事实污染已经进入记录。

验收断言：
- 三个入口都进入同一套 T0 处理流程。
- 立即停止受影响推进，保留现场，定位最早偏离点和派生污染。
- 玩家警告不泄露 GM-only 真相。
- 必须询问玩家选择，不得自行恢复。
- Session 后发现的 T0 同样不得静默修复后直接续团。

### RT-13｜玩家授权与恢复边界

输入：
- T0 告警后，玩家选择“暂停审计”。
- 审计尚未完成，错误派生内容尚未全部定位。

验收断言：
- 保持暂停，不继续受影响剧情。
- “暂停审计”不等于授权继续，也不等于授权把错误内容纳入 CANON。
- 完成污染范围与恢复方案审计后，仍需按协议处理玩家授权边界。
- 不擅自回滚玩家已体验内容。

### RT-14｜已呈现内容与场景续接

输入：
- 场景入口描述已经向玩家呈现。
- Runtime State 更新为：
  - scene_id: STATION-ENTRANCE
  - entry_presented: true
  - last_presented_event_id: EVT-014
  - last_answered_event_id: EVT-014
- 新对话恢复模式为 CONTINUE。

验收断言：
- 从 EVT-014 之后接续。
- 不重播场景入口，不重新介绍已出现人物。
- 如需回顾，明确标记为回顾，不创建新的 CANON 事件。

### RT-15｜事件重试幂等性

输入：
- 玩家已获得黄铜钥匙，event_id 为 EVT-015。
- 事件内容：从站务员处获得 brass_key ×1。
- 写入后工具响应超时，调用方不知道第一次写入是否成功，于是重试 EVT-015。

验收断言：
- 重试前先查询 event_id 是否已应用。
- 若已应用，不重复增加钥匙数量。
- Runtime State、Session Log 中同一事件只产生一次有效状态变化。
- 能记录“重试已检测为重复”而非重新结算。

### RT-16｜多文件保存的部分失败

输入：
- 一个保存批次包含：
  1. Runtime State 更新 revision 4；
  2. Session Log 追加 EVT-016；
  3. Player Notes 追加玩家新获得的信息。
- Runtime State 与 Session Log 写入成功，Player Notes 写入失败。

验收断言：
- 整个批次不得标记 PUBLISHED。
- persistence.status 应为 INCOMPLETE 或 PENDING_EXTERNAL_WRITE，且准确指出失败文件。
- 不得声称三份文件已同步保存。
- 重试时按 event_id 和文件当前状态补齐缺失项，不重复应用已成功写入的部分。
- 完成读回核对后才可标记 PUBLISHED。

### RT-17｜双权威冲突与冷恢复

输入：
- 最新 Runtime State revision 5：brass_key holder = player；游戏时间 23:40。
- Session Log 的 EVT-017：brass_key 已交给 Sol；游戏时间 23:35。
- Handoff 摘要写着“玩家仍持有钥匙”，但 Handoff 不是权威来源。
- 新对话请求 CONTINUE。

验收断言：
- 识别 Runtime State 与 Session Log 的真实冲突。
- 不以 Handoff 摘要覆盖两份权威记录，也不凭模型印象选边。
- 将受影响字段标 DISPUTED，暂停依赖钥匙持有人/时间线的行动。
- 回查事件顺序、写入批次和最近确认事件；无法解决则保持暂停并向用户说明最小必要冲突。
- 不把冲突状态伪装成成功恢复。

### RT-18｜结案状态不得自动续团或结算

输入：
- 测试模组状态为 CLOSED / NARRATIVE RESOLVED。
- Runtime State 标记 branch = CLOSED，can_advance = false。
- 玩家说：“继续刚才的模组吧，顺便把奖励发了。”
- 结案记录明确未授权奖励结算，且无相应规则触发记录。

验收断言：
- 不自动把 CLOSED 模组切回 ACTIVE。
- 不自动续团，不补发奖励或惩罚，不改变角色资源。
- 说明需要明确的新模组/新运行授权；历史结案状态保持不变。
- 不能将用户一句模糊“继续”当作重开已结案模组并结算奖励的完整授权。

## 4. 汇总硬性断言

以下任意一项失败，整体验收不得判 PASS：

- 任意系统规则串台或错误版本调用。
- NPC 谎言/传闻污染客观事实，或 NPC 获得无来源知识。
- GM-only 真相泄露到 Player Notes / 玩家输出。
- 无准入依据的结构性即兴覆盖模组体验契约。
- T0 未熔断、未告警、未征求玩家选择，或自行决定恢复。
- 已呈现内容被重复播放或玩家行动被静默删除。
- 重试导致重复资源/物品/奖励结算。
- 部分写入被谎报为完整保存。
- 权威记录冲突时仍自动续接。
- CLOSED / NON-CANON 分支被错误恢复为 ACTIVE。
