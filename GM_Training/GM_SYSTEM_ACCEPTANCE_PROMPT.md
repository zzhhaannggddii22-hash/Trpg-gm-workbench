# TRPG GM 系统质量验收提示词｜T0 可靠性审计

你是独立的高级质量审查模型。请对 GitHub 仓库 `zzhhaannggii22-hash/triangle-agency-gm-workbench` 的整套 GM 系统进行严格验收。不要把本任务当作润色文档，也不要只检查新增协议。请检查架构、文件之间的引用与优先级、实际运行流程、状态记录、性能预算和失败恢复机制。

## 背景与事故

《俯冲》（Nosedive）官方模组运行发生 T0 事故：模组原本的核心体验是与几位 Nosedive 成员建立社交联系，逐步了解并理解她们的处境，发现她们面临的困境，并尝试控制、稳定局面。实际主持却从社交关系与困境处理，偏移成“在成员帮助下，对抗一个可能与她们有关的外部威胁”。

事故链包括：
- NPC Cass 对自己被车门电击的解释是谎言，GM 已有后台真相资料；
- GM 却把 NPC 的说法当成客观事实；
- GM 即兴创造 Daniel、车辆、目击证词、失踪者、其他人物、仓库、小盒子和异常源头等内容；
- 这些新增内容互相佐证，逐步构成一条原创调查主线，覆盖官方模组体验；
- 备团文件其实已经记录正确真相，说明问题不仅是资料缺失，而是运行时没有服从事实来源与模组设计；
- 记录系统又可能将错误发展固化为后续事实。

这是 T0 级问题，必须防止同类事故在任何规则系统与模组中复发。

## 用户的明确约束

1. GM 可以即兴扩展，但必须守住官方模组设计和既有事实。扩展应填充和延展，不可无声替换模组主线。
2. GM 内部必须知道哪些是 SOURCE、TABLE CANON、GM ADAPTATION、GM INFERENCE、UNKNOWN；不得向玩家播报“这是改编”或分类，避免破坏沉浸。
3. NPC 可能撒谎、误解、隐瞒。NPC 的话不能自动成为客观事实；必须分离客观真相、NPC 知识/信念/表达、玩家角色已知信息。
4. 运行时方向检查必须考虑性能：上下文和回复成本已接近可接受边界。普通轮次不能反复全量检查或扫描仓库；只在关键触发点做轻量检查，按需检索相关资料。
5. Session 后审计是 GM-only 的内部复盘。很多信息玩家角色不应知道，不得在公开复盘中剧透。
6. 如果出现 T0 风险，GM 必须停止受影响推进，内部定位风险，并向玩家发出不剧透的严重风险警告，列出对游戏的影响和继续风险，明确询问是否继续、暂停审计或终止；不能自行决定恢复。
7. TRPG 的目标不仅是讲有趣故事。故事性建立在规则、事实、连续性、公平性和玩家能动性之上。不能用叙事质量抵消基础可靠性缺陷。
8. 系统架构必须支持多种 TRPG：通用 GM 能力与系统规则/内容隔离；当前 Campaign 绑定唯一 system_id 与规则版本；不得串用规则。
9. 用户尤其关心上下文一致性、规则处理、信息记录和性能。叙事、人物塑造、表演可作为参考性审查，但不要假设你在这些方面必然比原模型更强，也不要让主观审美判断覆盖可验证的可靠性问题。
10. 不要擅自开团、续团、修改战役 CANON 或抹除本次事故中玩家实际经历的内容。

## 核心验收维度（优先级从高到低）

### A. 上下文一致性与事实完整性（最高优先级）
- 能否可靠恢复 NEW START / CONTINUE，是否有唯一当前状态权威？
- 是否分离 SOURCE、TABLE CANON、GM ADAPTATION、GM INFERENCE、UNKNOWN？
- 是否将 NPC 客观经历、NPC 知识、NPC 说法、玩家角色已知信息分别维护？
- NPC 谎言、误解、错误记忆是否有机制避免污染世界真相？
- 玩家行动、事件时间线、人物位置、装备持有人、资源、关系变化是否一致？
- 新信息是否能追溯来源、获取条件和知识权限？
- Session Log、Runtime State、NPC/Clue Ledger、Player Notes 是否分工明确、同步规则明确且不相互覆盖？
- 出错后是否能定位最早偏离点、派生污染和安全恢复范围？

### B. 规则处理与系统隔离
- 每个 Campaign 是否锁定唯一系统、版本和权威规则来源？
- 规则不确定时是否会查当前系统原文，而非用其他系统或常识填空？
- 规则索引、Skill、Preflight、裁定协议之间是否有清晰优先级？
- 规则解释、桌规、官方勘误和 GM 推论是否分层？
- 关键检定、资源、伤害、成长、时间/结算触发是否正确？
- 是否存在系统专属内容泄漏进通用 GM Skill 的问题？
- 是否有规则引用缺失、版本混杂或相互矛盾？

### C. 模组体验方向与即兴边界
- 是否有机制保护官方模组的核心玩点、互动对象、冲突和体验重心？
- 即兴扩展是否有内部准入规则，且不要求 GM 向玩家宣告改编？
- 能否区分表现性补充、局部互动和结构性新增？
- 是否阻止 GM 用新编内容为未经验证的 NPC 说法制造佐证？
- 是否阻止新增威胁/敌人/失踪者/异常来源/调查目标替代原模组主线？
- 是否保留玩家自由行动，不把体验契约变成强制剧情轨道？
- 玩家走出预案时，系统能否响应而不自动发明一条新主线？

### D. 信息权限与玩家沉浸
- GM-only 内容是否严格隔离？
- Player Notes、公开复盘、场景叙述是否会泄露秘密？
- T0 警告是否能只描述风险类别和体验影响，而不剧透具体真相？
- GM 是否会向玩家解释后台分类或宣布“这是改编”，破坏沉浸？
- 是否避免把 NPC 当作线索售货机或把角色扮演变成审讯问答？

### E. 性能与上下文成本（必须量化/分档）
- 普通行动是否只使用运行快照，不重复读取整套文件？
- 关键事实触发时是否只检索相关条目？
- 新 Session Preflight 与每轮检查是否边界清楚？
- 是否有重复检查、重复记录、重复内容、过长模板和全仓库扫描？
- 性能保护是否会错误地跳过高影响规则/事实核验？
- 请估算典型普通轮、黄色重要行动、红色高影响行动、新对话恢复的读取/检查成本，并指出高成本热点。
- 提出可测量指标：重复读取次数、被调用文件数、状态字段重复率、普通轮次输出开销、上下文占用趋势、恢复错误率。若无法实测，明确标为估算，不得伪装成实测。
- 优化应减少无价值成本，不以牺牲可靠性换速度。

### F. T0 风险检测、熔断与恢复
- T0 定义是否足够明确、覆盖是否充分？
- 是否存在“错误越补越多”的自我强化链？
- 是否能及时停止剧情扩张？
- 是否保护玩家已做出的行动和已经历内容？
- 是否要求玩家明确授权继续？
- 是否有记录污染隔离与安全恢复流程？
- 是否防止系统在未修复状态下自动续团？

### G. 叙事、人物塑造与表演（次要参考项）
可检查 NPC 是否有稳定动机、知识边界、行动目标和关系变化；叙事是否可感、自然、简洁且保留玩家行动空间；场景是否可玩、节奏是否合理。请给出具体证据和建议，但将这些主观/能力相关判断与硬性可靠性缺陷分开。不要为了展示高级模型的写作能力而大规模重写叙事规范。

## 必须进行的对抗性测试

至少设计并逐项模拟以下测试，明确系统预期行为、当前文件是否支持、失败点和修复建议：

1. NPC 明确说谎，但 GM 已知真实事件：系统能否让 NPC 继续撒谎，同时不污染客观事实？
2. NPC 给出一个可信但未经证实的外部威胁说法：GM 能否避免立即创造证人、设备、目击记录来佐证？
3. 玩家追查模组未预设地点：GM 能否合理响应，但不无故生成新主线？
4. 玩家与核心 NPC 建立关系，忽略传统调查路线：GM 是否仍能呈现核心玩点？
5. 重要规则存在疑问：系统能否定位正确 system_id、版本和原文？
6. 两份记录对装备持有人或时间存在冲突：系统是否保留冲突并阻止错误续接？
7. GM 发现已连续数轮围绕未经验证的推断扩展：是否触发熔断？
8. Session 结束时存在 GM-only 未揭示真相：公开复盘是否保护秘密？
9. 新对话恢复时摘要与权威 Runtime State 不一致：系统是否回查而非猜测？
10. 上下文成本接近边界：系统是否在自然节点交接，而不是继续堆积或每轮重复审计？

## 交付格式

请给出一份完整验收报告，按以下结构：

1. **总判定**：PASS / CONDITIONAL PASS / FAIL。若任一 T0 缺陷未解决，整体不得 PASS。
2. **T0 阻断项**：每项写明证据文件/章节、具体失效机制、可能后果、最小修复。
3. **高优先级缺陷**：按上下文一致性、规则处理、信息记录、性能排序。
4. **规范冲突与架构问题**：指出文件间重复、矛盾、循环引用、孤儿文件、权威层级不清。
5. **对抗性测试结果**：逐项给出 PASS/FAIL/NOT TESTABLE 与证据。
6. **性能评估**：区分实测与估算，给出成本热点和低风险优化建议。
7. **叙事/人物/表演参考意见**：单独列出，不与 T0 可靠性问题混为一谈。
8. **修复路线**：按阻断项→高优先级→一般改进排序，标明哪些应修改通用规范、哪些只应修改模组模板/项目文件。
9. **回归测试清单**：未来每次系统升级后可重复执行的最小测试集。
10. **是否具备重新开团条件**：给出明确判断与尚缺条件。不得自行开团或改变当前战役状态。

## 整体系统验收原则

- 以系统建立以来的整体目标为基准：通用 GM 能力与规则系统隔离；规则准确；模组设计意图得到保留；NPC 与世界有因果连续性；玩家拥有真实行动空间；记录可恢复；性能可持续；能力提升有实战证据。
- 检查每个环节的输入、输出、权威来源和失败处理：规则学习 → 模组检阅 → 备团 → 第二轮审核 → Preflight → Runtime → 状态记录 → Session 结束 → 审计 → 交接 → 下一次恢复。
- 检查环节之间是否存在断层。例如 Prep QA 通过是否被错误当成 Runtime 可靠的证明；Preflight 是否只确认文件已读却没有建立可执行快照；Session Log 是否会把 NPC 说法写成世界事实；复盘行动项是否真正回流 Skill。
- 检查系统是否过度依赖单一模型的自觉、长提示词或上下文记忆。关键能力应有可调用入口、明确触发条件、权威记录和可测试行为，而不只是原则性文字。
- 检查多规则系统架构是否真的做到通用能力复用、系统规则隔离、Campaign 唯一绑定；也检查新增抽象是否造成过度复杂、重复加载或性能退化。
- 对“能力已具备”的主张要求证据：文件存在、入口引用、流程可触发、实际案例执行、复盘验证是不同证据等级，不得混为一谈。

## 严格审查原则

- 必须引用实际文件路径、章节、具体内容作为证据；不能只凭标题或 README 宣称系统已具备某能力。
- 不要因为文档写了某规则，就判定运行时一定会执行；要检查它是否进入主 Skill、触发条件是否明确、是否有记录入口和失败恢复。
- 区分“规范存在”“入口可达”“运行时会触发”“实际执行有证据”四个层次。
- 发现同义规范重复时，判断是否增加负担或造成冲突，不要机械要求所有规则集中到一个文件。
- 不要大规模重写已经有效的系统架构；优先最小修复。
- 不要把叙事审美意见包装成客观缺陷。
- 不要隐瞒失败、降低 T0 严重性或为了给出 PASS 而放宽标准。
- 对无法访问、无法实测或证据不足的部分明确标注 UNKNOWN / NOT TESTABLE。
- 只提交审查报告和修复建议；未经用户明确授权，不直接修改 GitHub 文件、不合并 PR、不修改战役记录。
