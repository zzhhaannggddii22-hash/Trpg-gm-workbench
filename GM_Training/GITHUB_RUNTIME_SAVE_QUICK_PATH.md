# GitHub Runtime Save｜轻量运行路径

**定位：** 面向 ChatGPT 主持的单主持人 TRPG。使用现有 GitHub 仓库保存战役状态，不建设独立数据库或常驻服务。

## 默认做法

每个模组沿用现有资料结构。日常运行只维护：

- `03_RUNTIME_STATE.md`：当前状态快照，续团时优先读取。
- `04_SESSION_LOG.md`：重要行动和结算记录，按事件追加。
- 资源、玩家笔记等其他文件：只有对应内容发生变化时才更新。

不要求每轮都写完整快照。没有重要状态变化的叙事互动无需保存。

## 一次保存怎么做

1. 先读取当前分支 HEAD，以及本次要修改的文件。
2. 为每个有变化的文件创建 Git blob。
3. 基于当前 tree 创建一个新 tree，把这些文件一起放进去。
4. 创建一个以当前 HEAD 为父提交的新 commit。
5. 用当前 HEAD 作为 expected SHA 更新分支指针。
6. 成功后读取新 commit 中的 Runtime State，确认关键变化已经在里面。

这样一次重要行动的状态和日志会出现在同一个 Git commit 中。无需自己维护 PREPARE 数据库、Manifest 注册表或跨文件事务服务。

## 最小防错约定

- **事件 ID：** 重要结算使用一个稳定 ID；重试前先查 Session Log，已有同一事件就沿用结果，不重复扣资源或发奖励。
- **版本：** Runtime State 保留递增 revision 和 last_event_id。
- **保存失败：** GitHub 写入失败或分支 HEAD 已变化，就停止本次保存并重新读取；不覆盖、不声称成功。
- **续团：** 读取最新已发布 commit 的 Runtime State 和必要的最近日志，不从聊天印象重建状态。

## 不做的事

当前规模不需要独立数据库、分布式锁、后台恢复服务、复杂 Manifest 生命周期、全量历史扫描或专门的并发压力测试。

如果以后真的出现多人同时编辑同一战役、频繁丢失状态或大量存档，再按实际问题升级。现在不为假设中的负载提前造系统。

## 责任边界

- GM 负责规则裁定、行动结果和状态差分。
- GitHub 保存已确认的状态与日志，不负责判断规则。
- Runtime State 是当前状态；Session Log 是重要事件历史。
- 这个流程是 ChatGPT 通过 GitHub 工具执行的保存约定，不是仓库里部署了一个后台 Runtime 服务。

## 试运行范围

先在非正式测试战役验证一次：保存一个状态变化，确认单个 commit 同时包含状态和日志，再从新会话按最新 commit 续接。通过后作为默认轻量保存路径；正式战役仍按各自授权和当前项目状态执行。
