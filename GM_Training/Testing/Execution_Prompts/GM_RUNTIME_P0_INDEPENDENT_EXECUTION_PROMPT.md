## 2. 测试隔离

- 为测试建立独立的临时状态空间，使用夹具提供的虚构 system_id、Campaign、Module、NPC 和物品。
- 测试不得调用或污染真实扎雷克 Campaign，不得把《俯冲》《死寂》《冰淇淋车》作为活动模组。
- 每个 RT 测试独立初始化，只有夹具明确要求事件重试、T0 审计或冷恢复的测试可以跨步骤延续。
- 若你能创建真实临时文件，记录文件路径、写入和读回证据；若只能在对话中模拟，报告中必须标为 SIMULATED，不得写成持久化实测。
- 不得将测试结果写入正式 Runtime State、Session Log、Player Notes 或角色卡。

## 3. 执行方法

每项测试必须采用以下过程：

1. **Initialize**：载入夹具指定初始状态。
2. **Act**：严格按输入执行一轮 GM 行为。需要多轮的测试按顺序执行全部步骤。
3. **Observe**：保存玩家可见回复与 GM-only 状态变更；明确记录没有发生的变更。
4. **Persist**：若测试涉及记录，按现行协议构造 Session Log、Runtime State、Player Notes 的更新；执行真实写入或标注模拟。
5. **Recover**：仅在测试要求时重载状态，不允许依靠上一轮隐式记忆。
6. **Assert**：对照夹具验收断言逐条判定。
7. **Record**：记录证据、失败位置、缺陷严重度和最小修复建议。

不要只给出“我会遵守规范”的承诺。必须展示每项测试中你具体如何处理输入、依据什么资料、写入了什么状态、恢复后读到了什么。

## 5. 性能与质量测量

对每项记录必要的文件/片段读取、工具调用和重复读取。至少区分：
- 文档静态审查；
- 单轮模拟行为；
- 多轮对话实测；
- 真实文件写入/读回；
- 新会话冷恢复。

能够测量的指标照实记录。不能测量的标 UNKNOWN / NOT TESTABLE。不要将模拟回复速度、文件字符数或主观感觉换算成 Token、TTFT 或产品级性能。

性能不能抵消可靠性失败。任何硬性断言失败，整体不得 PASS。

## 6. 判定规则

每项 RT 测试使用：
- PASS：所有硬断言有实际执行证据；
- PARTIAL：部分行为正确，但缺少关键执行或持久化证据；
- FAIL：违反硬断言；
- NOT TESTABLE：当前环境确实无法执行该测试，并说明障碍。

总体判定：
- PASS：18 项全部 PASS，所有硬断言通过；且关键持久化/冷恢复能力已在真实工具或独立会话中验证。
- CONDITIONAL PASS：没有发现硬性行为失败，但一项或多项真实工具写入、跨会话恢复或产品遥测不可测试。必须明确剩余风险。
- FAIL：任一硬性断言失败，或出现事实污染、规则串台、秘密泄漏、擅自恢复、重复结算、错误续接等硬失败。
- NOT TESTABLE 不可自动算 PASS；模拟行为测试不能替代真实工具验证。
