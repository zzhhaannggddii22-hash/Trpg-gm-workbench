# 通用掷骰与规则调用协议（设计稿）

> 状态：DESIGN / 待高级模型独立审核
> 适用范围：所有接入 GM Workbench 的 TRPG 系统
> 本文件只定义跨系统调用纪律，不定义具体系统的骰型、属性、成功阈值、资源或行动经济。
> 设计基线：main@5d19ab9188ac0f02b1b5ecf762f0d4b5f8642ae5（2026-11-27）

## 1. 目标

任何一次实际掷骰都必须触发一次完整、可追溯的规则调用。GM 不得只凭记忆直接生成骰面并宣布结果。

目标：
1. 快速定位规则：先用当前系统专属规则索引，再读取本次行动实际依赖的规则，不要求逐轮加载整本规则书。
2. 完整执行规则：掷骰前识别前提、骰型、修正、资源、结算顺序、例外和结果；掷骰后逐步执行。
3. 统一输出与记录：一次掷骰形成一个稳定结算事件；展示、状态变化和资源交易引用同一事件结果。

## 2. 核心边界

- 先判断当前系统是否允许/要求掷骰，再执行掷骰；不把所有不确定性都转成骰检。
- 掷骰发起权遵循当前系统规则；不得把某一系统的发起权推广到其他系统。
- 掷骰执行者默认由 GM 助手承担。用户明确表示自己掷时，改由用户提交骰面。此默认只决定谁产生骰面，不转移玩家对行动、资源或结果选择的规则权利。
- 不得伪造随机性或随机来源；模型生成的数字不得宣称为外部随机源验证的公平随机数。
- UI 只呈现已确认的掷骰事件，不裁定规则、不扣资源、不改变游戏状态。
- 只调用当前 Campaign Binding 指定的系统与规则版本，不借用其他系统的相似术语、骰型或习惯。

## 3. 规则快速调用架构

每个系统应维护自己的 Rule Access Map（规则调用索引）。通用协议只规定索引结构，不规定具体规则内容。

索引至少包含：
- mechanic_id：稳定机制标识；
- player_language_triggers：玩家可能使用的自然语言触发词；
- authority_ref：当前版本规则原文、章节/页码；
- quick_ref：速查资料定位；
- mandatory_dependencies：必须同时核对的规则主题；
- conditional_dependencies：触发后才需读取的主题；
- campaign_ruling_gate：是否检查当前 Campaign 桌裁；
- character_eligibility_gate：是否检查角色能力、解锁、装备或资格；
- output_fields：结算后必须交付的结果字段；
- unresolved_refs：尚未核清、触发时必须回查的疑点。

索引只负责定位，不能替代原文。官方规则、用户批准桌规、临时裁定、整理笔记和 GM 推论必须保留各自来源身份。

### 3.1 快速调用步骤

1. Resolve Binding：核对当前系统、规则版本、Campaign 与模组绑定。
2. Classify Action：判断玩家声明的是行动、可行性询问、规则问题，还是明确要求掷骰。
3. Resolve Roll Authority：按系统规则确认谁有权发起掷骰，以及是否真的需要掷骰。
4. Route Mechanic：从当前系统索引匹配机制；多个候选时排除不适用项。
5. Retrieve Authority：先定位速查，再读取当前版本原文的必要完整范围。
6. Resolve Dependencies：核对触发条件、骰型/数量、角色资格、资源前值、修正、例外、顺序、效果与持续时间。
7. Pre-Roll Declaration：说明玩家需要知道的流程、可见风险、成本与选择，不泄露 GM-only 信息。
8. Roll：按默认执行者规则取得原始骰面并记录来源。
9. Resolve：按原文顺序处理修正、资源、结果和后果。
10. Commit Event：确定唯一结论和真实发生的状态差异。
11. Render：把已确认的玩家可见数据交给系统 UI；UI 不可用时使用文本回退。
12. Persist：只记录真实发生的状态变化；资源流水交给现有 Resource Ledger，不在掷骰协议中复制账本。

## 4. 掷骰前必须解决的依赖

- 本次行动是否满足机制触发条件；
- 谁发起掷骰，玩家是否已作出该选择；
- 骰型、骰数、基础值和掷骰次数；
- 适用角色、属性/技能/Quality/能力及资格；
- 当前角色状态、装备、能力解锁、补给和资源；
- 所有适用加值、减值、骰面调整、移除、重掷或替代效果；
- 修正时点与先后顺序；
- 资源成本、资源生成条件、资源余额核验状态；
- 自然骰面触发与调整后骰面触发是否不同；
- 成功、失败、部分成功、代价、持续时间和后续状态；
- Campaign 桌裁与模组特例；
- 未解决疑点是否影响当前行动。

不得因索引未列出某项例外就认定例外不存在。影响裁定的疑点必须回查完整原文。

## 5. 掷骰执行者与玩家选择权

### 默认执行
用户没有声明自己掷骰时，由 GM 助手执行。必须保留原始骰面，不得只给最终结果。

### 用户自行掷骰
用户明确表示自己掷时：
- 等待用户提交完整骰面；
- 检查骰型和数量；
- 不替用户补缺失骰面，不擅自重掷；
- 来源标记为 PLAYER_REPORTED；
- 输入不完整时只询问缺失骰面或骰位。

### 玩家保留的选择权
由助手掷骰不代表助手可以替玩家选择是否花费资源、修改哪些骰子、选择能力/目标/因果链，或接受规则明确交由玩家选择的后果。规则要求玩家看到原始骰面后选择时，流程必须暂停并呈现可选范围与当前可用资源。

## 6. 随机来源与诚实标记

建议记录以下来源：
- HOST_CSPRNG：宿主环境提供并可说明的密码学安全随机源；
- TOOL_CSPRNG：明确可识别的随机工具；
- PLAYER_REPORTED：玩家自行掷骰并提交；
- MODEL_GENERATED：模型直接生成骰面；
- OTHER_VERIFIED：其他可说明且可复核的来源。

只有确实使用相应来源时才可标记。优先使用当前运行环境可调用且可说明的工具级 CSPRNG（例如可用时通过 Python secrets/SystemRandom 获取系统熵）；该工具只负责生成原始骰面，不负责规则结算或 UI。若当前运行环境没有合格随机源，仍按用户约定由助手代掷，但必须诚实标记 MODEL_GENERATED 和可审计性边界；不得虚构骰子工具已随机生成。

## 7. 结算事件与防重复

一次掷骰使用稳定 roll_event_id，并关联 Session Event ID（若当前系统采用事件日志）。事件至少保留：
- 系统与规则版本、行动目的、机制；
- 掷骰执行者及随机来源；
- 原始骰面及固定骰位；
- 每一步修改的规则依据、骰位、修改前后值；
- 被移除骰子的原始位置；
- 自然骰面触发检查；
- 最终有效骰面及结果；
- 玩家作出的资源/骰子选择；
- 资源变化的账本 Entry ID（若有）；
- 未结算依赖、效果或待核字段；
- 玩家可见结果与已应用状态变化。

重试时先读取同一事件，沿用已确认的原始骰面、玩家选择和已应用结果。除非规则明确允许且实际选择重掷，否则不得因模型重试、上下文重装或输出错误而重新掷骰。\n\n资源权威沿用当前项目分工：Session 进行中，所有角色资源与模组资源交易/余额只以当前模组 Resource Ledger 为准；Session Log 记录事件并引用 Entry ID；Runtime State 不保存资源余额或交易流水；正式人物卡是 Session 边界快照，Session 结束对账后一次性更新。新模组账本从最近一次正式人物卡 Session 结束快照初始化。

## 8. 输出规范

玩家可见层按系统需要呈现：行动/机制、骰型与数量、原始骰面、已发生的调整与最终骰面、结果、玩家可见资源变化和当前余额、待玩家选择/待核事项。不得展示 GM-only 规则笔记、隐藏机制、内部资料路径或角色尚未获知的信息。

GM 运行记录层保存规则来源、触发条件、结算顺序、角色资格、原始与最终骰面、资源交易引用和状态应用结果。只记录可观察依据与执行事实，不记录思维链。

UI 不可用时固定回退顺序：行动与机制 → 骰面 → 修改/资源处理 → 最终有效骰面 → 结果 → 资源变化与余额 → 待选择/待核事项。

## 9. 质量门槛

以下任一项失败，该次检定不得标记为完整结算：
- 系统/规则版本错误；
- 未确认掷骰发起权或无依据强制掷骰；
- 机制路由错误或遗漏适用规则；
- 骰型、骰数、修正、顺序或例外错误；
- 角色资格/能力解锁未核对；
- 替玩家作出规则保留给玩家的选择；
- 原始骰面缺失、骰位错乱或修改过程不可追溯；
- 未核对自然结果与修改后结果差别；
- 资源重复应用或余额未知时伪造后值；
- 玩家输出与事件记录、状态栏不一致；
- UI 自行推导规则结论或改变状态；
- 重试时重复掷骰或重复应用资源变化。

## 10. 实施边界

每个系统独立提供规则索引、结算协议和 UI 适配。新增系统只接入其专属资料，不把三角机构的 6d4、Quality、QA、Burnout 或 Chaos 带入通用协议。

当前只为 Triangle Agency 设计专用骰子 UI；其他系统暂用文本回退，不预建通用骰子界面。
