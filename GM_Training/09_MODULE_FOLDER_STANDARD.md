# 模组文件夹与备团标准

> 本文是所有新模组自动调用的操作标准。与 02_WORKFLOW_AND_PREFLIGHT.md 的 B6 配套；具体系统规则仍由各系统模块决定。

## 1. 目录原则

一个模组/一次正式冒险一个独立文件夹。该模组所有备团、运行、玩家便笺、结算和复盘资料都放在其中；跨模组人物档案与战役交接仍放在战役总目录，不在每个模组里复制多份权威人物卡。

推荐最小结构：

- README.md：入口、文件索引、状态、保密边界。
- 01_GM_PREP.md：GM-only 原文摘要、场景、线索、NPC动机、威胁/现象机制、触发、分支与结局。
- 02_NAME_INDEX.md：唯一名称映射表。
- 03_RUNTIME_STATE.md：当前唯一有效运行快照，按 [RUNTIME_STATE_TEMPLATE.md](./RUNTIME_STATE_TEMPLATE.md) 维护；Session Log 保留历史事件，不与快照重复维护两份当前状态。
- 04_SESSION_LOG.md：只记实际发生的桌面事实。
- 05_PLAYER_NOTES.md：玩家侧可知信息，不含隐藏真相。
- 06_POSTMORTEM.md：复盘、证据、下一轮训练行动。
- 07_SOURCE_AND_RULE_CROSSCHECK.md（适用时）：原文来源、版本、页码、规则核验与差异。

若模组复杂，可增加独立文件，例如 NPC 详细卡、线索账本、地图/地点索引、遭遇表、任务结算；不要把所有内容堆进一个巨型文件。

## 2. 来源与事实分层

每个重要条目标记其性质：
- SOURCE：模组/规则原文明确内容。
- TABLE CANON：本桌已经实际发生并确认的事实。
- GM ADAPTATION：为适配单人桌、玩家人物或桌面需求作出的明确改编。
- GM INFERENCE：从原文与已建立事实推导的主持判断。
- UNKNOWN：尚未核实，不得补写成事实。

外部评测、论坛、Actual Play、其他桌即兴内容只能作为体验参考。不得把其他桌的名字、剧情、规则裁定或即兴结果冒充模组原文。

## 3. GM-only 与玩家侧分离

- GM Prep、隐藏状态、真相、线索答案、触发条件、异常动机、NPC秘密、结局条件放在 GM-only 文件。
- 玩家便笺只记录角色实际知道的信息、来源、时间、可信度与承诺。
- 玩家可见开场简报只提供角色合理获知的任务目标、公开风险和必要操作信息。
- 不依赖同色文字、折叠或视觉遮挡来防剧透；默认不输出隐藏内容。
- 如果某条资料同时包含公开与隐藏信息，拆分记录，不将隐藏部分直接复制到玩家侧。

## 4. 名称索引规范

每个 NPC、地点、组织、关键物品建立稳定规范 ID。推荐：
- NPC-姓名/角色；
- LOC-地点；
- ORG-组织；
- ITEM-物品；
- FACTION-阵营；
- EVENT-事件；
- CLUE-线索。

名称显示规则：
- 首次向玩家呈现：中文名（English Original）。
- 同一对象之后可用中文简称，但 GM 账本仍保留规范 ID。
- 中文名、英文原名、拼写变体、简称、昵称、称谓都映射到同一规范 ID。
- 原文未命名的角色使用中文角色称谓（English Role Label），不得为了“看起来完整”而擅自造专名。
- 若 GM 确实需要新增姓名，先标注 GM Adaptation，再登记唯一 ID 和中英文名；不能让新名字看起来像官方原名。
- 地点的街道地址、建筑、房间、区域、势力辖区或系统定义的特殊场域分开建 ID，避免把同一地点的不同称呼误当成不同地点。
- 名称发生变化时更新索引并保留旧名为别名；不得创建第二条身份记录。

每场开团前进行双向检索检查：用中文名和英文名分别搜索，均应命中同一规范 ID。名称索引未完成时，不向玩家输出未确认专名。

## 5. 模组原文准备步骤

1. 核实模组名称、作者/来源、版本、完整性和可访问性。
2. 完整阅读原文；记录页码/章节/段落定位。摘要不能替代原文。
3. 建立场景结构：开场、调查/探索、遭遇、分支、结局、后果。
4. 建立信息账本：事实内容、来源、来源知识边界、可获得方式、重复确认渠道。
5. 建立 NPC 卡：目标、动机、性格、能力、知识、误解、资源、行动条件、与 PC 的关系。
6. 建立地点卡：可观察特征、出入口、空间关系、互动对象、可能变化。
7. 建立威胁/现象卡：核心特征、行为模式、触发条件、能力/效果、风险与后果、处理/解除/撤退条件。
8. 标注原文明确、GM推断、单人桌适配和未确认内容。
9. 对照玩家指定系统规则，逐项核验当前系统的判定、资源、伤害/压力、装备、特殊能力、奖励、进度/威胁轨道与结算项目。
10. 评估时长与节奏风险，但不为了时长目标擅自删改原文。
11. 完成名称索引、运行状态、玩家便笺模板和无剧透开场材料。
12. 完成备团资源整理与运行索引；按模组复杂度/风险决定是否执行可选 Prep QA（如执行，必须在第一次 Preflight 前完成）。实际开团时在新对话中另行执行 Preflight；Preflight 负责加载本次 Session 所需资源，不属于备团步骤。

## 6. 开团前 Preflight（每次新对话/新 Session 执行）

本清单属于 [工作流程 §A](./02_WORKFLOW_AND_PREFLIGHT.md#a-开团前恢复权威上下文) 的同一次 Preflight。完整路径使用完整原文和本清单；健康续接按该节核对适用就绪条件，裁剪读取深度，仍须保留命名 NPC 首次接触、规则原文和玩家权限闸门。

- [ ] 当前规则版本和权威来源已确认。
- [ ] 本次新对话已恢复当前模组、人物卡、战役交接、最新 Runtime State、最近 Session Log 与本次行动所需的相关资料。
- [ ] 模组完整原文已读取，版本/页码已记录。
- [ ] 当前正式人物卡、当前场次副本、重要 NPC 长期档案和战役交接已恢复。
- [ ] 本场系统资源、伤害/压力状态、装备、持有人、弹药/充能已核对。
- [ ] 单人桌与同行 NPC 适配边界明确；没有偷偷增加 PC、行动经济或能力。
- [ ] NPC 的知识、目标、动机、关系与行动条件明确。
- [ ] 线索有多个合理获取途径；重复来源不会被错误封锁。
- [ ] 威胁/现象机制、触发、效果、危险提示和结局条件已按规则核验。
- [ ] NPC/地点/组织/物品名称索引完成；中文英文双向检索一致。
- [ ] GM-only 和玩家侧文件已分离。
- [ ] 玩家简报不含隐藏真相、答案、秘密触发条件和结局。
- [ ] 等待用户明确开团指令；不因备团完成自动开始。

## 7. 运行与归档

- 游戏中只将实际发生的行动、信息、状态变化写入 Session Log。
- 每个关键变化同步 Runtime State；不得只改叙述不改账本。
- NPC 获得信息必须有实际来源；不能因为 GM 知道就自动知道。
- 长期 NPC 的经历、记忆、物品、系统资源/伤害状态与关系变化必须进入其长期档案或战役交接。
- Session 结束后完成本场资源与状态变化、编号 Session Log、Runtime State、Player Notes，以及必要的战役持续状态同步；系统明确要求按 Session 结算的项目照常结算。
- Module 结团后完成模组级结算记录、系统定义的后续威胁/未决状态、整体奖励与后果、最终 CANON 归档和完整 GM 复盘；单 Session 模组在本场结束时合并执行。
- 将本场复盘行动项转化为下一次 Preflight 检查。
- 完成后回读关键文件，确认链接、状态与索引没有冲突。

## 8. 验证与修订

- 每次复盘检查文件夹是否完整、双语名称是否一致、GM-only 是否泄露、状态是否同步。
- 新标准只在实际发现可复现问题时增加；避免为形式化而增加无用字段。
- 修订标记为补充、细化、修订或替代，并说明影响、验证方法和回退条件。


## 9. 多 Session 模组结构补充（2026-11-22）

一个 Module 可以包含多个 Session。推荐在模组目录内增加 Sessions 子目录，每次游玩创建一个编号文件，如 SESSION_01.md、SESSION_02.md。已完成 Session 日志作为历史记录保留，不用同一文件反复覆盖。

### 文件职责
- README：模组入口、进度、文件索引与下一步。
- GM Prep：模组原文、场景结构、线索与 GM-only 预案。
- Name Index：模组实体规范 ID 与别名；战役级人物引用 Campaign 档案。
- Runtime State：当前模组唯一有效的运行快照；每个 Session 结束更新。
- Sessions/SESSION_XX：每个 Session 的事实日志与结束状态；只追加历史，不重复维护当前状态。
- Player Notes：玩家角色已知信息的累计摘要。
- Postmortem：整个模组结团后的完整复盘；Session 间仅记录即时纠错和待办。
- 可选线索账本、地点索引、模组 NPC 备注，仅在信息量确有必要时建立。

### NPC 归属
- 一次性与模组局部 NPC 归当前模组。
- 跨模组反复出现、对机构或战役有稳定影响的 NPC 归 Campaign/NPC；模组文件通过规范 ID 引用。
- 核心长期搭档保留独立长期人物档案，并在 Campaign NPC 索引中登记入口，不复制完整设定。
- NPC 从模组级升级为战役级时保留原 ID 和首次出现来源，模组索引留下引用。

### Session 生命周期
- Session 开始读取最新 Runtime State 与最近日志，不扫描全部历史。
- Session 结束创建本次编号日志、更新 Runtime State，并同步必要的 Campaign 持续状态。
- Module 结束时才完成整体奖励、系统定义的后续威胁/未决状态、模组结算与完整复盘；系统另有 Session 结算要求时遵循系统规则。
- 验证只检查本次变更涉及的权威字段与 GM-only/玩家侧边界，不做无差别全库全文复读。


## 10. 运行状态文件与场景续接标记

每个多 Session 模组只维护一份当前有效的 Runtime State。推荐按 [RUNTIME_STATE_TEMPLATE.md](./RUNTIME_STATE_TEMPLATE.md) 建立或更新，不在每份 Session Log 中另造一套不同的当前状态格式。

Runtime State 至少标记：
- 本次是 NEW START 还是 CONTINUE；
- 当前场景 ID 与 NOT ENTERED / ENTERED / ACTIVE / CLOSED / NON-CANON 状态；
- 入口描述是否已经向玩家呈现，以及最后一个已确认叙事节点；
- 当前游戏时间、地点、在场者和重要位置关系；
- 玩家最近行动、GM 最近回应和当前待处理意图；
- 角色资源、关键物品持有人、玩家已知信息、NPC 实际知识；
- 活跃事件、触发条件、承诺、待办与最后确认事件 ID。

CONTINUE 不得从模组开场重新生成叙述。先读取最新 Runtime State 和最近 Session Log，确认最后已发生的事件与玩家最后收到的内容，再从尚未处理的节点继续。

Session Log 记录事件历史；Runtime State 记录当前值。某项变化写入 Session Log 后，同步更新 Runtime State。若两者出现冲突，以最新可追溯事件和权威来源修复，不静默选择一个方便继续的值。

新 Session 只有在真正开始一个新的正式场景/冒险时使用 NEW START。新对话、上下文重建或模型切换都不是 NEW START 的理由。

## 2026-11-24｜模组关闭与只读归档状态

模组生命周期状态至少区分 PREP / READY / ACTIVE / PAUSED / CLOSED / ARCHIVED。CLOSED 表示剧情与玩家层结算已由用户/规则确认完成；ARCHIVED 表示不再作为日常活动入口。关闭时追加最终检查点，不覆盖旧 Session、Runtime 或 Handoff 历史。
- 模组 README 的首屏状态、Runtime 最新检查点、Campaign 索引和 Handoff 退役标记必须一致。
- 未执行计划继续标为未执行，不因结案而补写成发生；未知后续保留 UNKNOWN。
- 奖励、惩罚、资源和角色成长逐项按规则与实际事件结算；用户明确指定 NONE 时，不从模板默认流程补发。
- 玩家角色可知内容与 GM-only 后续分开保存。机构接手、场外处置或时间跳跃不得自动进入角色记忆。
- 结案记录只写入用户确认的结果、必要的系统结算和已知信息边界；不为了“补完整故事”虚构空白过程。

## 11. 强制备团闭环：建立—审查—压力测试—修订—复审—归档

本节是所有新模组备团的默认强制工作要求。它是备团本身的质量闭环，不等同于可选的独立 Prep QA／跨模型审查；即使不启动可选 Prep QA，也必须完成本节。不得把“写完第一稿”“做过一次检查”或“列出待办”标记为备团完成。

### 11.1 完整执行顺序

1. **来源与边界确认**：确认模组版本、原文完整性、页码/章节、系统规则版本、战役绑定、角色基线、既有跑团经历与不可继承的测试内容。核实模组是否已跑过；已体验的模组不得作为新模组重复推荐或误当未玩。
2. **第一轮建档**：按本标准建立独立文件夹和最小文件集。整理 SOURCE、TABLE CANON、GM ADAPTATION、GM INFERENCE、UNKNOWN；建立地点、场景、调查链、NPC、威胁/异常、线索、分支、结局和后果资料。
3. **规则与数值核验**：逐项回查当前系统原文和模组原文，覆盖适用的初始资源、资源生成/消耗、能力触发、判定素质、QA/Burnout、Harm、装备、收容/中和、奖励、处分、Loose Ends 与结算。没有明确依据的数字不得猜测；写清来源或标 UNKNOWN。
4. **一致性审查**：检查时间线、空间关系、人物动机/知识/行动能力、物品状态、异常能力与现象之间的因果、线索来源与可获得路径、结局条件和信息权限。确认没有跨模组/跨系统污染。
5. **玩家路径压力测试**：至少检验玩家跳过关键地点、先去任意调查入口、错过/拒绝 NPC、提出错误假设、使用非预设能力、改变顺序、分头/独自行动、尝试暴力或非暴力方案、救人后撤离、撤离后返回、破坏关键物件、绕过预设触发、提前解决或直接失败等适用分支。目标是找出软锁、无回报长支线、单点线索依赖、NPC 全知、无法收束和规则漏洞；不要求为不适用的分支制造内容，但需记录不适用原因。
6. **修订**：逐项处理审查发现的问题。区分必须修复、建议优化、原文刻意保留的风险和无法确认的缺口；任何改编都标记 GM ADAPTATION，不得悄悄改写 SOURCE。
7. **第二轮复审**：针对修订后的完整资料重新检查受影响链路，并从头快速复核关键事实、规则数值、玩家权限边界、路线可行性和收束条件。若发现新问题，返回修订步骤；至少完成一轮实质修订与复审，不能以同一份初稿重复阅读冒充迭代。
8. **运行化与交接**：完成 Name Index 双向检索、Runtime State 空白/基线、玩家侧便笺空白模板、无剧透开场材料、快速调用索引和 Preflight 交接。玩家侧材料必须与 GM-only 资料分开。
9. **归档与回读验证**：将最终文件保存至对应 Campaign 的模组目录；逐个回读关键文件，核对路径、链接、状态、版本、交叉引用与 GM-only/玩家侧隔离。记录本次迭代轮次、检查范围、修订摘要、未解决项和实际验证结果。

### 11.2 完成状态定义

- **DRAFT**：只有第一轮草稿；不得称为备团完成。
- **REVIEWED**：完成检查但尚未完成实质修订与复审；不得称为备团完成。
- **READY**：完成至少一轮实质修订与第二轮复审，所有开团必需信息可调用，关键规则与数值有来源，玩家侧材料无剧透，运行交接齐备；仅此状态可称“备团完成”。
- **READY WITH OPEN ITEMS**：只允许剩余项不影响公平运行、核心规则裁定、玩家选择或安全边界；必须列明限制与现场处理方式。
- **BLOCKED**：原文、规则、角色基线或关键机制缺失，导致无法可靠运行。明确阻塞项，不得假装 READY。

### 11.3 对用户的汇报边界

备团档案默认是 GM-only 内部工作资料。除非用户明确要求审阅，不在聊天中粘贴备团正文、核心真相、NPC 秘密、线索答案、触发条件、遭遇解法、结局或测试用例。过程汇报保持极简；完成后只确认状态、GitHub 路径/提交或 PR 状态、是否存在真实阻塞。只有必须由用户决定的事项才提问。

### 11.4 反形式主义

- 检查和压力测试要针对模组真实结构，不为打勾而制造无关测试。
- 不要求每个模组都写庞大的独立报告；可将简短测试结果和修订记录放在 GM Prep / Source Crosscheck。
- 不把未执行的测试写成通过，不把同模型自审描述成独立模型审查。
- 不因追求完整而臆造原文未提供的机制、数值、NPC 知识或场景后果。
- 不允许流程本身阻碍玩家自由行动；备团应降低现场推演成本，而不是把玩家锁进预设路线。
