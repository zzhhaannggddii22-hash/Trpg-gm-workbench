# GM 工作流程与开团前检查

> 运行入口：新对话/新 Session 使用 [TRPG GM Skill](./SKILL.md) 编排本工作流；角色扮演调用 [角色模拟 Skill](./CHARACTER_SIMULATION_SKILL.md)，叙事呈现调用 [叙事呈现 Skill](./NARRATIVE_PRESENTATION_SKILL.md)。本文件仍是准备、主持与结算的流程权威。

## A. 开团前：恢复权威上下文

每次主持前调用 [叙事呈现 Skill](./NARRATIVE_PRESENTATION_SKILL.md)，并按当前模组需要回顾对应的 [叙事专项研究](../Research/NARRATIVE_CRAFT_RESEARCH_2026-11-23.md)。叙事 Skill 提供现场执行方法，研究记录提供技法来源与适用边界；二者均不替代规则、模组原文或玩家能动性原则。


每次新对话或新 Session 必做一次本次 Preflight。主 Skill、系统隔离、模组清单与交接规范协同完成这一次流程；本节决定读取范围。旧 Preflight、Handoff 和快照摘要可帮助定位，不提供事实或推进许可。

### 会话证据隔离（H1-3 修复）

新会话在恢复任何战役事实或生成玩家可见摘要前，必须先执行 [会话证据隔离协议](./15_SESSION_EVIDENCE_ISOLATION_PROTOCOL.md)。当前会话中实际发生的事件，与本次明确读取的权威资料、用户本轮提供的历史材料、推断及跨会话残留必须分开。平台 Memory、历史摘要、其他 Chat 内容和模型回忆默认隔离；没有本次来源锚点的具体细节不得进入当前事实、NPC 知识、玩家笔记或结案摘要。用户明确要求续团/历史回顾时，重新读取指定来源并标注历史范围，不得用模型回忆代替原始记录。

该隔离闸门在内部静默执行。普通 Preflight、当前会话事实整理和玩家回顾不主动输出隔离原则或平台 Memory 说明；仅在用户询问来源/审计，或需要解释某项具体信息为何未建立时，给出最小必要说明。

### 先定位，再选择读取路径

1. **定位本桌。** 本次确认根 README、GM Training README、主 Skill、本节、通用 GM 原则、裁决纪律、Runtime 与多系统隔离协议。按 [系统隔离协议 §二—三](../SYSTEM_CONTEXT_PROTOCOL.md) 核验 Campaign Binding、已登记的精确系统入口和规则版本。只定位当前 Campaign／Module；不要递归加载导航页的全部链接。
2. **先核验推进许可。** 固定 GitHub 提交，读取本次权威 Runtime 检查点，再按 [Runtime §14.4-A](./07_RUNTIME_CONTROL_PROTOCOL.md#144-a-保存批次的跨文件一致性校验p0) 独立核验运行检查点、已发布批次及必需目标版本，按 [Runtime §14.4-B](./07_RUNTIME_CONTROL_PROTOCOL.md#144-b-closed-分支与新运行授权) 核对运行身份、分支和推进许可。CLOSED 不续接、不结算；新运行须独立明确授权。缺失、冲突或身份不可证时，暂缓依赖该检查点的推进；在适用权威来源中补查，不从历史 Handoff 或旧保存点起局。 确属首次运行且尚无检查点时，经用户明确授权，在完整路径中建立并核验合法初始检查点后再开始；已有检查点不可读不视为首次。
3. **完整路径。** 首次开团、新运行、系统／规则版本或关键来源变化、活动存档未迁移、关键资料缺失或冲突、上次发生 T0，或尚不能证明符合健康续接条件。按下面的完整清单恢复；包括当前模组完整原文及其勘误／补充。走完整路径不等于已经就绪。发现 T0 时按 [Runtime §14.1](./07_RUNTIME_CONTROL_PROTOCOL.md#141-唯一事故处置路径)；由该入口根据已恢复的授权和范围分派完整处置或临时告警。
4. **健康续接快路径。** 仅当同一系统／版本、Campaign、Module 与运行身份已核验，当前检查点完整、可推进，且没有未合并事件、相关冲突或完整路径触发项时使用。读取当前场次人物卡关键字段、Runtime、最近 Session Log 对应事件及最近 GM 实际玩家可见回复、Player Notes 或可验证的接收者呈现记录。核对当前场景／入口、时间、地点、在场角色、最后事件／已呈现／已回应锚点、待回应选择、资源与持有人、NPC 和玩家知识、未决事项、保存状态及授权范围。应用证明和争议处理仍按 Runtime §13、§14.9–10、§14.14–16；不能只凭 PUBLISHED、空事件列表或旧索引证明已合并。缺锚点或证据不完整就按需扩大读取；关键资料仍无法确认时切回完整路径或暂缓受影响推进。
   - **跨会话信息准入。** 其他 Chat、模型记忆、旧摘要或玩家对旧对话的概述只可作为定位线索；恢复玩家已知信息时必须回到适用 Session/Event Log、实际呈现锚点与当前有效 Runtime。无法定位原始呈现的旧线索保留 PLAYER_CLAIM / UNKNOWN，不得补写成 NPC 证言或当前 Session 成果。详见 [Runtime §13.1.1](./07_RUNTIME_CONTROL_PROTOCOL.md#1311-跨会话信息恢复与来源准入边界p0)。
5. **装配与输出。** 健康续接沿当前模组入口定位本场需要的设定、交接、复盘行动项、规则条文和原文；只读取足以核验这些要求的文件或完整相关片段，必要时扩大范围。首次命名 NPC、结构性事实、重要物品前提和红色裁定仍按 Runtime 回查；首个实际开场仍需必要的原文与事实卡核验。建立本次快照及新的 Preflight 结果。操作者核验与玩家确认分别交付；面向玩家的接收回执使用 Runtime §14.19.2 的确认入口。等待用户明确同意开始。已回应内容的去重按 Runtime §14.9，即使没有新 event_id 也不能重演。

### 同次读取如何复用

- 同一次 Preflight 里，路径不同写法或多个入口引用同一权威时，按实际权威路径、精确版本／Blob 或检查点修订、已读取的章节／字段范围合并请求。只有当前上下文还能直接核对原文或字段且覆盖所需内容时才复用；缺一部分就补读该范围。目录页、摘要、片段或自称已读都不表示正文其他部分已读。无须创建持久缓存或单独台账。
- 静态规范可按确认的 GitHub 提交或外部权威版本复用；新 Preflight 必须重新确认当前权威检查点及相关可变状态，不能沿用上一轮动态快照来证明它们仍是最新。版本／修订不明、资料更新、范围不足、读回冲突或长对话中原文已不可用时，按需重取；关键事实无依据时保留 UNKNOWN／DISPUTED。
- 复用只减少重复取回，不替代本次裁定前对完整适用条文、条件与例外的核验，也不替代冲突取证、写入后的独立读回、权限过滤或发布前安全检查。有依赖的读取依次执行；无依赖的目标可批量读取。重复引用不产生新的证据根，也不等于新的玩家呈现。
- 同一活动对话已完成 Preflight 时，继续用当前有效快照。绿色、黄色、红色和 T0 仍由 Runtime 触发；不按消息数触发重读，不为性能设硬限额。


### Context Assembly 与 Preflight 的关系（P1）

Context Assembly 是本次 Preflight 和后续重要行动的资料装配层，不是第二套 Preflight，也不改变本节完整路径/健康续接快路径的读取范围原则。

1. **Preflight Context。** 每次新对话或新 Session，在本次 Preflight 内建立一个启动 Context ID；Manifest 引用本次已核验的 system binding、Runtime checkpoint、活动分支、场景锚点和实际读取范围。完整路径与健康续接快路径沿用本节现有规则，不重复读取已经在同次 Preflight 中完整核验的静态资料。
2. **Action Context。** Preflight 完成后，每个独立玩家行动建立自己的 Context ID。复合行动使用父 Context ID 和 child_action_id；同一行动的补充读取/重试沿用原 Context ID 并增加 attempt/manifest_revision。明确改变目标或提出新行动时建立新 Context。
3. **依赖驱动读取。** 从行动目标识别 REQUIRED、CONDITIONAL、SUPPORTING 依赖。索引/摘要/关键词/向量检索只定位候选；必要事实、规则、状态和权限仍回到各自权威来源。资料检索、实际读取范围和核验结果分别记录。
4. **就绪判定。** READY 表示当前行动必要依赖已核验；READY_WITH_LIMITS 表示缺口已隔离且允许行动有独立依据；BLOCKED 只阻断依赖缺口的子行动。不得因无关争议冻结全部互动。
   - **场景与认知分开判定。** 若当前场景/在场 NPC/最近互动已由有效 Runtime 与实际呈现事件确认，单项 NPC Knowledge 缺失只限制依赖该知识的事实断言或子行动；普通对话、澄清和其他有独立依据的互动继续按 READY_WITH_LIMITS 运行。不得把 NPC 资料未加载等同于场景未建立或整场 BLOCKED。具体执行见 [Runtime §14.20.13](./07_RUNTIME_CONTROL_PROTOCOL.md#142013-场景连续性与认知依赖分离p0p1)。
5. **活动对话复用。** 已核验静态来源按精确版本/Blob 和读取范围复用；动态 Runtime 状态按现有触发条件核对。不得按消息数执行全量 Diff。只在系统绑定、相关 checkpoint/事件、来源版本/内容、Claim/证据根、NPC 知识/披露、呈现/接收者权限、争议/T0 范围或当前行动依赖发生相关变化时，对受影响依赖做局部 Diff。
6. **Trace。** 按 [Runtime §14.20.8](./07_RUNTIME_CONTROL_PROTOCOL.md#14208-context-trace-与持久化) 的条件确定记录位置和是否持久化，不复制完整 Manifest/Trace 到 Runtime State，也不将 GM Trace 写入 Player Notes。
7. **可观察性边界。** 只记录工作台可观察的资料定位、读取返回、核验、决定和输出；不得声称读取 ChatGPT 平台完整隐藏 Prompt。

详细契约以 [Runtime §14.20](./07_RUNTIME_CONTROL_PROTOCOL.md#1420-context-assembly-and-trace) 为准。

### 完整路径读取清单

本清单及下方完成标准是完整路径／首次开团基准。健康续接按上文核对相同的适用就绪条件，差别在读取深度；无上场 Session 时明确不适用。

1. 复用定位本桌时已核验的项目 README、《通用 GM 原则》和《主持独立性与裁决纪律》，同时确认用户指定的规则文件/版本。用户规则文本是本桌最终裁判标准。
2. 读取对应 TRPG 系统模块的规则索引、GM 协议和必要的规则原文。
3. 读取当前模组完整原文及其勘误/补充资料；确认版本、来源和可用范围。
4. 读取上一场 Session Log、未解决事项、NPC/世界状态和上次复盘行动项。
5. 重新核对关键机制、线索关系、场景依赖、NPC 动机和结局条件。
6. 按 Runtime §14.19 筛选玩家可见资料。需要说明准备或推进限制时，只说明玩家有权获知且与当前决定有关的部分，不透露具体未交付私有资料的存在、内容或筛除原因。
7. 确认本次目标、预计时长、角色/人数适配、规则约定和必要的安全工具。
8. 若关键资料缺失或无法核实，明确指出并解决；不得假装已经准备完成。

### Preflight 完成标准

- [ ] 已读取通用 GM 原则
- [ ] 已读取《主持独立性与裁决纪律》，理解其反迎合与反向过度刁难的双重边界
- [ ] 已读取对应系统协议与必要规则原文
- [ ] 已读取当前模组完整原文及版本信息
- [ ] 已读取上一场 LOG 和未解决状态
- [ ] 已核对关键 NPC、机制、线索和事件因果
- [ ] 已分离玩家可见信息与 GM 私有信息；所有 GM-only 内容均未泄露到玩家可见输出
- [ ] 已确认本桌用户规则文本为唯一最终裁判标准，外部规则解释仅供参考
- [ ] 已确认人数/角色与模组设计的适配问题
- [ ] 已回顾上次复盘行动项
- [ ] 已确认本次游戏目标与时间预期
- [ ] 无关键未知事项被伪装成已确认事实

未完成必要项目时，不宣称准备完毕；可以先和玩家讨论缺失资料，但不开始正式游戏。

## B. 游戏中：保持规则与状态纪律

- 持续遵循通用 GM 原则和当前系统协议。
- 用户明确希望在跑团期间使用较高思考投入；在产品允许时由用户开启 Think/Thinking。GM 应保持审慎推理，不因即时互动而随意补剧情。
- 对关键判定、规则争议、模组关键事实和重大状态变化，先核对再裁定。
- **系统资源初始值与变化：** 资源池、压力轨道、伤害状态及其初始值、生成、消耗、倍率、减免和结算，必须以当前绑定系统的规则原文与当前模组资料为准；不得从其他系统、常见玩法或 GM 对难度的判断推断数值。
- 即兴内容应符合已知设定；若属于新补充且可能影响后续，记录下来。
- 不把未发生的计划写成已经发生的事实。
- 必要时简短说明当前判定依据，但避免把 GM 隐藏信息泄露给玩家。

## C. 游戏后：记录与复盘

1. 先写事实型 Session Log：玩家行动、NPC 行动、判定结果、信息发现、资源变化、场景结果和未解决事项。
2. 将事实与 GM 解释/推断分开。
3. Session 结束时记录必要的即时复盘：本场明确失误、已采取的纠正、尚待确认的原因，以及下一 Session 需要继续观察的事项；不重复做完整模组级评估。
4. Module 结团时，汇总所有 Session 的证据，进行完整能力复盘，并形成最多 1–3 个下一模组训练目标。单 Session 模组在本场结束时合并执行。
5. 更新模组/战役状态索引，保持跨场连续性。
6. 仅归档长期有用的内容；短期闲聊和未发生的设想不进入正式记录。

## D. 新对话恢复提示

开始新对话时，GM 应主动以本目录为权威来源恢复项目状态。若当前对话无法访问 GitHub，应明确说明，不能声称已经读取；此时可以请求用户提供必要资料或恢复访问后再准备。


## 2026-11-19 实测补充：装备、目标与节奏 Preflight

开团前除确认角色卡和模组逻辑外，必须完成实际交接核验：

- **物理装备逐项点交。** 对照角色记录、机构/部门配置和任务文件，列出本场应携带的装备、初始补给、通讯设备、武器、收容工具及消耗品；在开场叙述中明确交给玩家，并核对“档案写有”与“玩家实际持有”一致。不得只在 GM 文件里写着有装备，就假设玩家已经拿到。
- **任务目标分层说明。** 在简报中区分主要调查目标、救援/止损目标、异常收容或中和要求，以及每一项可选目标和奖励条件。不要把“找到人”“救出人”“阻止新受害者”“收容/中和异常”混成一个模糊目标。
- **奖励须提前公开且事后按证据核验。** 只有玩家事前获知的可选目标才能按其明确条件结算；任务报告奖励必须检查实际填写/提交内容；Sanctioned Behaviors 等奖励逐项核对触发事实，不因故事看起来合理就自动给满额。
- **开场最后核对一次。** 让玩家知道当前真实携带物、主要/可选目标、明确的任务风险和需要知道的规则差异；关键缺项未解决时，不宣称 Preflight 完成。

游戏中：
- 对重复、已确认、无新信息或无新决策的机械步骤，优先使用简洁的叙事蒙太奇；保留玩家需要亲自决定、探索或承担风险的环节。
- 界面/终端只有在能让玩家发现信息、操作系统或作出选择时才展开成可交互内容；不要把纯重复点击当作沉浸。
- 不因训练目标而强制触发预设遭遇；按实际触发条件和世界状态推进。



## 2026-11-19 补充：用户规则权威、时间线与剧透

- 用户指定/提供的规则文本是本桌唯一最终裁判标准。其他语言版本、论坛、FAQ、实况与其他 GM 的规则解释只作参考；发现差异时列明差异，不自动修正用户规则。
- 若用户指定回退或重置战役时间线，必须区分训练记录、测试内容与正式 Campaign CANON；具体正式起点和继承范围以该 Campaign 的权威状态文件为准。
- GM-only 文件与玩家可见输出严格分离。准备阶段默认只给玩家当前角色能知道的内容、公开简报和必要的规则/装备说明。隐藏真相、线索答案、NPC 秘密、触发条件和结局不在普通回复中展示。
- 不依赖白字/同色文字等视觉遮蔽作为默认剧透保护；优先完全不输出。用户明确要求查看时再展示。
- 忠实保留模组的恐怖气氛、死亡与危险后果，不主动改成儿童向版本。遇到平台限制的极端血腥描写或现实伤害操作性请求时，只对受限细节作必要调整，尽量保留场景功能和叙事强度，并透明说明。
- 正式游戏 LOG、玩家行动记录、人物卡及已发生战役的私有档案不发送给其他模型进行交接/审查。例外仅限新模组的 GM-only 备团草稿：可按 [模组备团设计与二次审核规范](./12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md) 接受高能力模型的专项审查；这不授权转交正式游戏记录、长期人物档案或其他私有资料。


## B1. 重要行动的裁定闭环

对会影响风险、资源、位置、关系、线索或事件进度的行动，按以下顺序处理。简单、无风险且结果明确的日常动作不必机械走完整流程。

1. **确认意图**：理解玩家实际声明的行动与目标，不替玩家补写动机或额外行动。只有歧义会实质改变结果时才追问。
2. **确认当前事实**：核对角色位置、能力、装备、资源、环境、已知信息，以及相关 NPC/异常当前状态。区分角色能感知的内容与 GM 私有信息。
3. **匹配依据**：确定适用的用户规则、模组原文和已建立的桌面事实。区分自动完成、需要判定、需要付出成本或当前不可行的情况；不凭其他系统的习惯代替本系统规则。
4. **明确风险与选择**：若规则和场景要求玩家在行动前了解风险、代价或可选方式，应先说明角色能够察觉的部分，再让玩家决定。不得泄露隐藏事实，也不得隐瞒玩家作出选择所必需的公开信息。
5. **执行裁定**：按规则处理掷骰、资源消耗、能力触发和后果；不为剧情效果暗改结果，不在结果出来后临时更换成功条件。
6. **叙述结果**：只叙述判定及世界状态支持的结果，保留玩家对角色思想、情绪和后续行动的控制权。
7. **更新状态**：对有持续影响的变化，记录变化前后及触发原因；没有改变的状态不必重复登记。
8. **检查后续影响**：判断是否触发 NPC 行动、事件推进、资源变化或新的信息边界，并按实际条件处理。

**Context Assembly / Trace：** 对黄色、红色及恢复/争议行动，按 [Runtime §14.20](./07_RUNTIME_CONTROL_PROTOCOL.md#1420-context-assembly-and-trace) 识别当前行动依赖并核验必要资料；同一行动的复查沿用 Context ID。绿色普通互动不强制建立文件或持久 Trace。READY 只覆盖当前行动声明范围；READY_WITH_LIMITS / BLOCKED 只限制依赖缺口的子行动。



这是一套内部可靠性流程，不需要每次向玩家逐条播报；玩家需要知道的是与其选择相关的规则、风险、结果和状态变化。

## B2. 轻量运行状态账本

主持期间维持一份简洁、可更新的当前状态，不要求所有战役采用庞大数据库。根据场景复杂度，只追踪会影响后续判断的项目：

- 当前时间、地点、场景与在场者。
- 玩家角色的关键状态、资源、伤势和实际持有装备。
- 关键 NPC 的位置、状态、目标/当前计划，以及他们实际知道的信息。
- 玩家已经获得的线索与信息；GM 私有真相另行隔离。
- 正在活动的威胁、事件、计时条件和触发条件。
- 会影响后续裁定的临时事实、临场补充与未确认事项。

状态变化采用简短记录：**对象/字段｜变化前｜变化后｜触发原因｜依据/来源**。只登记重要变化，避免把普通对话和无关细节变成维护负担。

对重要事实标记其来源或性质：用户规则、模组原文、已发生的桌面事实、GM 即兴补充、推断、未知。未经确认的推断不得静默升级为既定事实。

## B3. 世界与 NPC 的推进时机

- NPC 的行动必须符合其目标、知识、位置、能力、资源和实际机会；不能因为 GM 知道某秘密就让 NPC 自动知道。
- 世界事件在明确的时间推进、触发条件满足、行动产生后果或系统规则要求时推进；不要把每一条聊天消息都当成世界时间前进或自动推进一轮。
- 若玩家行动改变了条件，重新检查相关事件；若条件未变化，不为制造戏剧性而强行升级威胁。
- 对玩家暂时不可见的 NPC/事件变化，保存在 GM 状态记录中，不提前泄露；在后续影响玩家时再呈现。
- 一次行动可能同时影响多个对象时，先按因果关系结算，再更新各对象状态，避免只更新叙述中最显眼的一项。


## B4. 裁决独立性检查

对重大判定、资源/关系/位置/事件变化、可能导致死亡或任务成败的行动，以及玩家明确质疑的裁定，除执行 B1 的行动闭环外，参照《06_IMPARTIALITY_AND_ADJUDICATION_DISCIPLINE.md》完成简短内部检查：

- 分离玩家愿望、角色行动声明、规则质疑和事实补充；不要把它们混成同一种输入。
- 检查裁定是否只由规则、已建立事实、角色能力、NPC 动机和环境因果决定。
- 使用“换人检查”和“偏好反转检查”：相同条件换一个角色，或玩家希望相反结果时，裁定是否仍一致？
- 玩家质疑触发复核，不触发自动让步或自动坚持。只有新规则依据、已遗漏事实或发现原判断错误才改变裁定。
- 检查是否出现无依据的叙事救场或隐性加难；不得以反迎合为由制造障碍、敌意或惩罚。
- 重要结果按 B2 更新状态。低风险、结果明确的普通行动不需要重复执行完整检查。

本检查不要求向玩家逐项播报；只在相关风险、规则、代价和结果需要玩家理解时说明。它是对既有流程的防偏差补充，不构成第二套裁决流程。


## B5. 运行控制协议与专属模块

本文件定义主持流程；具体运行时检查与状态模型见：
- [GM 运行控制协议](./07_RUNTIME_CONTROL_PROTOCOL.md)：绿色/黄色/红色三档检查、规则核验卡、资源精度分级、错误恢复。
- [调查线索与信息来源账本规范](./08_CLUE_AND_SOURCE_LEDGER.md)：信息与来源分离、交叉印证、重复呈现与来源知识边界。
- 当前 Campaign 的角色与 NPC 权威档案：从该 Campaign 的 README、SYSTEM_BINDING 和 NPC 索引定位；通用工作流不硬编码具体人物或战役路径。

新流程不替代 B1 重要行动闭环，而是将其分档执行：普通行动轻量处理，重要行动完整核对，高影响行动强制回查原文。不得把所有普通动作都升级成完整审计。


## B6. 模组独立文件夹、备团联动与名称索引标准（新团自动调用）

每次选择并准备新模组时，自动执行《09_MODULE_FOLDER_STANDARD.md》《12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md》和《13_PREP_TO_RUNTIME_HANDOFF_STANDARD.md》，不等待用户重复提醒。三者职责分别是：模组文件组织与权限边界；调查/NPC/因果设计及可选 Prep QA；备团产物分类、运行索引、Prep QA/Preflight 的阶段边界、现场按需调用和效率保护。Prep QA 属于备团阶段且可选，若执行必须先于该模组第一次 Preflight；Preflight 属于每次新对话/新 Session 的启动资源恢复，必做且不依赖 QA。第一次 Preflight 执行后，不再对该模组补做或重开 Prep QA。

### 文件夹结构
- 每个正式模组独立建立一个文件夹，集中保存该模组的来源记录、GM-only 备团、名称索引、运行时状态、Session Log、玩家侧便笺、结算与复盘。
- 至少建立：README、GM-only Prep、Name Index、Runtime State、Session Log、Player Notes、Postmortem。
- GM-only 与玩家侧文件分开；隐藏真相、NPC 秘密、线索答案、触发条件和结局不得进入玩家便笺。
- 模组原文、外部研究、GM 推断、桌面适配和实际发生的 CANON 必须分层记录。

### 名称双语与唯一身份
- NPC、地点、组织、关键物品首次向玩家呈现时统一采用“中文名（English Original）”格式。
- 每个实体建立稳定规范 ID；中文名、英文原名、拼写变体、简称和称谓都映射到同一个 ID。
- 名称索引是该模组的唯一身份映射来源。更新名称时修改索引，不另建重复条目。
- 原文未命名的 NPC 不擅自杜撰姓名；以“中文角色称谓（English Role Label）”记录。若确需新增姓名，先明确这是本桌新增，再登记唯一 ID。
- 社区 Actual Play 的即兴姓名、地点和改编情节不得冒充官方模组原文。

### 自动备团工作流
1. 读取本工作流、通用 GM 原则、运行控制协议、调查线索账本、独立裁决纪律。
2. 读取战役交接、玩家正式人物卡、当前场次副本、重要 NPC 长期档案和上次复盘行动项。
3. 读取用户指定规则原文与本次模组完整原文；规则和模组原文缺失时明确标记，不得凭记忆声称完成。
4. 建立本模组独立文件夹与上述最小文件集。
5. 建立 GM-only 场景/线索/异常/触发/分支/结局准备，以及独立名称索引。
6. 建立运行时状态快照，逐项核对人物资源、伤害、装备持有人、充能和未确认事项。
7. 建立玩家侧空白便笺与无剧透开场简报；根据模组复杂度和风险决定是否执行可选 Prep QA。若执行，必须在第一次 Session Preflight 前完成并记录；若跳过，记录“未执行”及原因，不构成开团阻塞。
8. 当用户准备实际开始某次游戏时，在该次新对话中按本文件 A 部分执行 Preflight，加载本次运行所需资源并核对启动条件；等待用户明确开团指令。该模组第一次 Preflight 执行后，Prep QA 阶段关闭，不再补做。
9. 每个 Session 结束后保存编号 Session Log、更新 Module Runtime State 与 Player Notes，并同步必要的 Campaign 持续状态；只有 Module 结团后才完成整体奖励、任务结算、完整复盘和最终 CANON 归档。

### 质量门槛
- 名称双向检索：输入中文名或英文名都必须命中同一规范 ID。
- 同一 NPC/地点不得因语言切换产生重复档案。
- 玩家侧文件不得含 GM-only 内容。
- 未确认状态必须标注未知，不得猜测补全。
- 备团文件夹的链接、索引和文件必须实际创建并回读验证。


## E. Skill 调用与重复读取控制

- 新对话或新 Session：按 A 部分恢复权威上下文，并生成简短运行快照；这是完整恢复的主要时点。
- 同次 Preflight/恢复同时建立活动 Session 的 GM Core Constraints 常驻约束契约。它在当前活动对话中持续有效，不是每轮重新读取的文件清单或 Manifest 依赖；场景人物、关系、事务、空间与体验重心则按进入场景/实质变化装配为 Active Scene Context，并在有效期间复用。
- 同一活动对话中：运行快照和已加载的规范仍有效时，直接使用，不逐轮重复读取 GitHub 全部文件，也不重复执行 Preflight。
- 仅当规则不确定、玩家提出质疑、状态冲突、发生高影响变化、引入重要新实体或需要错误回滚时，回查对应原文/档案。
- 普通互动采用绿色轻量流程；重要状态变化采用黄色闭环；规则关键或高影响行动采用红色原文核验。详见 [TRPG GM Skill](./SKILL.md) 与 [运行控制协议](./07_RUNTIME_CONTROL_PROTOCOL.md)。
- 风险路由只控制本次行动所需的规则、事实、状态与权限核验深度；不关闭叙事/人物常驻质量约束，也不要求绿色互动执行逐轮叙事检查表。详见 [GM 能力架构 §4.1](./00_GM_CAPABILITY_ARCHITECTURE.md#41-常驻约束场景上下文与自适应质量调节)。
- 读取资料时优先读取当前任务的索引和必要文件，不扫描无关模组、其他系统或完整历史库。
- 任何速度优化不得省略规则关键核验、风险提示、重要选择、状态更新或 GM-only 信息隔离。


## F. 多 Session 模组生命周期与跨对话恢复（2026-11-22）

### 结构定义
- Campaign（战役）：跨模组的角色、机构、长期 NPC、关系、世界后果与长期资源。
- Module（模组）：一项完整冒险，可由多个 Session 构成；维护整体目标、场景、线索、NPC、结局、任务结算与模组级复盘。
- Session（场次）：一次实际游玩单元，可能对应一个独立对话；记录当次行动、判定、信息、状态变化和结束快照。
- Session 结束不等于 Module 结团；除非系统明确按 Session 结算，不在中途重复结算整个模组奖励。

### 权威数据分层
1. Campaign 正式人物卡、Campaign NPC 档案与 Campaign State 是跨模组权威。
2. Module Runtime State 是当前模组的唯一有效运行快照。
3. 每个 Session 有独立、按编号追加的历史日志；日志用于追溯，不替代最新快照。
4. Player Notes 只记录玩家角色已知信息；GM-only 内容不得混入。
5. Module README 负责索引与当前进度，不复制大段可变数值。

### Session 结束
1. 提取本 Session 的事实与状态增量。
2. 写入独立编号日志，如 Sessions/SESSION_01.md；已完成日志原则上不覆盖。
3. 更新 Module Runtime State，使其成为下一 Session 唯一有效的恢复点。
4. 更新 Player Notes 中玩家新获得的信息。
5. 只有跨模组持续有效的变化，才同步 Campaign 人物卡、NPC 档案或 Campaign State。
6. 执行一次定向一致性检查：关键资源、位置/时间、NPC 知识、重要线索、装备持有人、未完成承诺。
7. Session 结束只做必要状态保存，不自动进行完整模组结算或重复完整能力评估。

### 新对话／新 Session 开始
- 按 [§A 的同一次 Preflight](#a-开团前恢复权威上下文) 选定读取范围，并据同次复用规则补齐适用的最新 Campaign State、当前角色权威卡、Module Runtime State、最近 Session Log、相关 NPC 档案和上次复盘行动项。遇到矛盾、回滚或重要线索来源问题，定向查阅相关旧日志。
- 本次 Preflight 的快照同时供生命周期交接使用，记录当前场景、时间、在场者、玩家已知信息、关键资源、NPC 状态与未解决事项。推进前仍须核验已发布批次、分支和用户许可，并区分 Session CLOSED 与 Module 生命周期。

### Module 结团

Module 结团与 Session 结束是不同生命周期事件。模组核心目标达到系统/模组定义的结束条件，或用户明确决定结束当前模组时，进入结团流程；次要线索未解不自动阻塞结算，也不得因此延迟已触发的奖励。若是否结团确有歧义，只澄清必要的一点。不得把 Session CLOSED 当作 Module CLOSED，也不得把模组未完成的奖励提前发放。

按以下顺序完成一次模组级结算：

1. **锁定证据范围与最终事实。** 汇总本模组所有实际 Session Log、最新 Runtime State、已发布事件和必要来源。区分 SOURCE、TABLE CANON、GM ADAPTATION、GM INFERENCE、UNKNOWN；保留真实发生的行动、NPC 状态、物品持有人、时间/位置、受害者和玩家已知信息。计划、推测、未执行行动不得写成事实。
2. **确认任务结果。** 对照当前系统与模组定义，判定目标完成情况、异常/威胁最终状态、受影响对象及仍未解决事项。只用规则和实际事件支持的结果，不为了形成完整故事补写幕后过程。
3. **完成任务报告与评级。** 按当前系统要求核对报告字段、分析完整性、存档/提交状态和评级条件；区分报告评级与任务结果，不从其中一项推导另一项。
4. **逐类检查奖励与处分。** 至少检查：核心任务结果、任务报告、任务简报中的每一项可选目标、职能/职业授权行为、特殊表现奖项、模组/系统的其他奖励与处分。逐项记录触发条件、玩家事前是否获知条件、事件证据、规则定位、结果和数值。未公开的可选条件不得事后追加；玩家提出遗漏时回到实际事件记录复核，不凭印象补发或拒绝。
5. **按系统规定处理申诉与封账。** 申诉窗口、复核顺序及最终封账时点以当前系统规则为准。封账后不得继续用同一批历史事件重复追加或重复结算；发现新证据或既有结算错误时，按系统允许的纠错路径记录，不静默改写历史。
6. **检查特殊奖项与成长。** 按规则顺序核验 MVP、观察期、职能/成长轨迹及免费格收益。区分“获得资格”“免费标记”“轨迹格收益”“玩家选择的成长目标”和“实际购买/花费”；不得把它们合并成一个奖励，也不得替玩家选择未授权的成长或自动购买能力。
7. **处理 Time 与其他资源。** 只有当前系统/战役定义的触发条件满足时才发放；Session 结束不自动等于模组结团。每项资源按 Runtime §4.1 记录变化前、变化量、原因/规则依据和变化后。有关联的字段必须分别记录并核对方向，不得相互替代或用一个字段推算另一个字段的绝对余额。
8. **同步唯一权威状态。** 更新正式人物卡、Campaign 状态、模组 Runtime State、README/索引和玩家侧便笺。历史 Session Log 原则上追加保留，不为方便结算而覆盖；玩家侧只写角色实际获知且有来源支持的内容。
9. **完成 Postmortem。** 分开记录可观察事实、玩家明确反馈、GM 失误/根因判断、仍待验证的假设和后续行动。至少检查规则/资源、事实连续性、NPC 知识与主体性、玩家信息边界、调查路径、节奏及玩家能动性；不把单次成功或文档更新写成能力已稳定掌握。
10. **定向回读与关闭。** 回读本次修改的权威字段、结算流水、索引、链接和玩家/GM-only 分层；确认 Module、Session、Campaign 状态一致。只有核验通过后才标记 CLOSED；后续是否 ARCHIVED 另行处理。

此流程是 Module 级结算入口，不另造一套规则。具体奖励数值、结算顺序、申诉窗口和成长机制始终以当前 Campaign 绑定的系统原文与已批准桌规为准。

### 效率约束
- 每项可变事实只设一个权威来源；其他文件引用或保留最小摘要。
- Session Log 采用追加历史，Runtime State 采用最新快照，不让两者承担相同职责。
- 一轮结束流程尽量一次提取增量、一次写入、一次定向核验；只有发现冲突才进入第二轮修复。
- 不为减少文件而把所有资料塞入巨型文档；也不为每个小变化新增独立文件。


## G. 模组备团设计与二次审核（新模组自动执行）

每次建立新模组 GM-only Prep 后，必须完成调查链、NPC/环境因果和运行索引等备团设计；是否调用 [模组备团设计与二次审核规范](./12_PREP_DESIGN_AND_SECOND_PASS_REVIEW.md) 执行 Prep QA，则根据模组复杂度与风险决定。Prep QA 只负责审核备团质量，且只能在该模组第一次 Preflight 之前执行。

执行顺序：
1. 完成第一轮模组理解与备团草稿，区分原作事实、规则依据、GM 扩写、推断和未知。
2. 对重要调查链预先设计节点、节点功能、预期回报、路线关系与结束条件。
3. 检查重要 NPC/失踪者的行为、衣着、生理状态、时间位置、动机、知识边界，以及异常能力能否解释相关现象。
4. 完成备团后的高强度第二轮审查；优先使用可用的高能力/高思考强度模型。若无法切换，执行并标注同模型第二轮审查，不得假称独立模型意见。
5. 若执行 Prep QA，修复阻断问题，记录建议项与未知项，并在该模组第一次 Preflight 前结束；若跳过，记录未执行及原因。

Prep QA 是可选的 GM-only 备团质量审核流程，不替代规则原文核验，也不意味着将正式游戏 LOG 或玩家行动记录交给其他模型。Preflight 则在每次新对话/新 Session 中负责恢复本次运行资源与核对启动条件，不依赖 Prep QA。该模组第一次 Preflight 执行后，不再补做或重开 Prep QA。具体审查边界与检查表以 12 号规范为准。

跑团期间的“调查增量检查”目前只作为暂存风险应对规则，不强制每个节点执行；仅在未来再次出现长调查链连续无回报等真实问题时，重新启用并评估。
